# 03. 무엇을 만들었나

## 판단이 어디에 있나

이것 하나가 이 앱의 설계 전부다.

```
MOA 본 서비스              모아(토스)

   화면                      화면
    │                         │
    ↓ HTTP                    ↓ 함수 호출
  서버                      같은 번들 안
    │                         │
    ├→ 분류 사전 (DB)          ├→ 분류 사전 (JSON 52KB)
    ├→ 국세청 조회 (HTTP)       │   ✗ 못 가져옴
    ├→ LLM 추정 (HTTP)         │   ✗ 못 가져옴 → 사용자가 고른다
    └→ EBM 모델 (JSON)         └→ EBM 모델 (JSON 52KB)
```

서버 쪽 상자 둘이 빠진 대신 **네트워크가 통째로 빠졌다.**

## 판단 순서 — 한 곳에만 적는다

`src/engine/classify.ts` 하나에만 있다. 두 곳에 적으면 한쪽만 고쳐져 조용히 갈라진다.

```
가맹점명
 ① 이 기기가 기억한 것          사람이 고친 것이라 가장 세다
 ② 확정 사전 — 이름            522행 중 356
 ③ 확정 사전 — 사업자번호       432. PG 번호는 건너뛴다
 ④ 브랜드 → 소분류 → 중분류     표기표 1,248 · 소분류표 1,060 · 중분류표 170
 ⑤ 명세서의 업종코드 → 중분류    505. 카드사가 실어 줄 때만
 ⑥ 카테고리없음                모르면 모른다고 둔다
```

**⑥에서 지어내지 않는다.** 서버에는 ⑤와 ⑥ 사이에 모델이 있지만 여기엔 없다.
그 자리를 규칙으로 메우면 틀린 분류가 확정처럼 보이고, 사용자는 그것이 짐작인 줄 모른다.

### 운영에서 고쳤던 것이 그대로 따라왔다

브랜드 맞추기 규칙 둘은 **운영에서 실제로 틀린 뒤에** 생긴 것이라 같이 옮겼다.

| 규칙 | 안 옮겼으면 |
|---|---|
| 라틴 표기는 낱말 경계에서만 | `고속철도(KTX)서울-포항` 이 브랜드 **KT** 가 된다 (2026-08-07, 7곳 40건) |
| 세 글자 미만 한글은 뒤에 한글이 오면 불인정 | `토스트커피하우스` 가 브랜드 **토스** 가 된다 (2026-08-21) |

`test/smoke.ts` 가 이 둘을 확인한다.

## 낭비 판정

학습된 EBM 을 그대로 돌린다. `logit = 절편 + Σ 특징별_표_조회`, 임계값 0.479.

특징 11개(`src/engine/features.ts`)는 학습 코드와 **한 글자도 달라지면 안 된다.**
요일이 월=0 인 것, 금액에 `log1p` 를 쓰는 것, `amt_vs_typical` 을 20 에서 자르는 것 —
전부 학습에서 온 값이다. 어긋나도 예외가 안 나서 판정만 조용히 틀린다.

### 명세서에는 시각이 없다

특징 넷(`hour_sin`·`hour_cos`·`night`·요일 일부)이 시각을 보는데, 카드 명세서에는
날짜만 있다. 정오로 고정하면 그 넷은 모든 결제에서 같은 값이라 **판정에 기여하지 않는다.**
남은 일곱(금액·카테고리·요일·그 사람의 평소)으로 판정한다.

억지로 그럴듯한 시각을 지어내지 않는다 — 지어낸 시각으로 "밤 소비였어요"라고 말하면
그건 근거가 아니라 거짓말이다.

## 저장

`src/engine/store.ts`. **사실만 담고 판단은 안 담는다.**

날짜·가맹점명·금액만 담고, 카테고리도 낭비 여부도 읽을 때마다 다시 계산한다.
그래야 표가 좋아졌을 때 옛 소비도 같이 좋아지고, 같은 데이터에서 늘 같은 답이 나온다
(설계 원칙 3 — 재현성).

예외가 하나다. **사용자가 고친 것**은 계산으로 되살릴 수 없으므로 따로 담는다.

같은 결제를 두 번 넣지 않는다 — 날짜·가맹점·금액이 같으면 같은 결제로 본다.
명세서를 두 달 겹쳐 받는 일이 흔하고, 겹친 줄을 쌓으면 합계가 부푼다.

## 파일

```
src/
  data/          표 넷 — 188 KB. scripts/build-toss-*.py 가 만든다
  engine/
    tables.ts    표를 읽고 인덱스를 세운다
    brand.ts     가맹점명 → 브랜드 (MerchantBrandService.fromCatalog 이식)
    classify.ts  판단 순서 ①~⑥ — 여기 한 곳에만
    ebm.ts       EBM 점수기 (SpendingClassifier 이식)
    features.ts  특징 11개 (WasteFeatureExtractor 이식)
    store.ts     기기 저장 — 사실만
    report.ts    분석 한 번 → 네 화면이 나눠 쓴다 (설계 원칙 2)
  lib/
    statement.ts 명세서 CSV 파서 — 본 서비스의 사본
  screens/       다섯
  components/    Empty · Source 배지
test/smoke.ts    엔진만 따로 두드리는 것
```

`lib/statement.ts` 는 사본이다. 카드사별 머리글 별칭표는 화면이 아니라 **규격**이라
두 앱이 같은 파일을 받아야 한다. 다만 사본은 갈라지므로, `COLUMN_ALIASES` 는
`frontend/src/lib/statement.ts` · `scripts/import-realperson.py` 의 `NAMES` 와
**셋이 같은 내용이어야 한다.**
