## 0. 용어 확정

| 용어 | 소유 | 뜻 |
|---|---|---|
| **기준 소비** | ① | 카테고리별 평소 소비 수준. 최근 3개월 월평균 잠정. (A)의 `baseline` · ②의 `baselineAmount` · `11_지킴이_Agent_설계.md`의 `기준 지출`이 모두 같은 값이다 |
| **절약 후보** | ① | AI가 이번 챌린지에 줄여볼 대상으로 제안한 카테고리 |
| **권장 강도** | ① | AI가 제안하는 절약 강도 초기값 |
| **가치 소비 보호 신호** | ① | 반복되는 취미·가족·건강 소비 등을 절약 후보에서 보호하기 위한 신호 |
| **선택 카테고리** | ② | 사용자가 이번 챌린지에서 줄이기로 확정한 카테고리 |
| **절약 강도** | ② | 사용자가 카테고리별로 확정한 지킬 비율 |
| **30일 챌린지** | ② | 캐릭터가 지킬 돈을 지키는 여정 구간. **달력 월이 아니다** |
| **지킬 돈** | ② | 챌린지 시작 시 확정한 목표 절약액 (`targetSaving`) |
| **챌린지 한도** | ② | `기준 지출 − 지킬 돈`. 노출하지 않는 내부값 (`challengeCap`) |
| **집계 지출** | ② | 챌린지 선택 카테고리에서 집계된 카드 승인 금액 합계 (`spentAmount`) |
| **남은 한도** | ② | `한도 − 집계 지출`. 노출하지 않는 내부값 (`remainingCap`) |
| **확보 절약액** | ② | `min(지킬 돈, max(0, 기준 지출 − 집계 지출))`. **③이 서술에 쓰는 금액** (`securedSaving`) |
| **달성률** | ② | `확보 절약액 ÷ 지킬 돈` (`achievementRate`) |
| **챌린지 확정 지킨 돈** | ② | 챌린지 종료일에 원장을 마감한 뒤 확정한 확보 절약액 |
| **누적 지킨 돈** | ② | 확정 지킨 돈의 합계. 감소하거나 리셋되지 않음. **현재 (C) 미포함 — §8 참조** |
| **성장 레벨** | ② | 누적 지킨 돈 구간으로 계산한 캐릭터 성장 단계. **현재 (C) 미포함 — §8 참조** |
| **소비 흐름 집계** | ③ | ③이 마이데이터에서 직접 집계한 서술용 소비 요약. 금액 판정에 쓰지 않음 (R10) |
| **소비 성향 프로필** | ① | 소비 성향 요약과 충동 구매 지수 |
| **라이프스타일 분석** | ③ | 소비 패턴을 축으로 나눠 본 것. **자금 흐름 축(L1~L5)**은 상품 매칭에, **취향 축**(카테고리·가맹점 빈도)은 연간 리포트에만 쓴다. 취향 축은 매칭 입력으로 넘기지 않는다(R9 가드레일) — `12_리포트_라이프스타일_설계.md` §4 |
| **금융상품 정보성 추천** | ③ | 실제 상품 정보를 **자금 흐름 축과 우대조건 충족 여부**에 맞춰 개인화한 정보성 비교. 판매·중개 없음 |
| **주간·월간·연간 리포트** | ③ | 주간=관찰 · 월간(=챌린지 종료)=회고 · 연간(달력 연도)=정체성. 역할과 금지 항목은 `12_리포트_라이프스타일_설계.md` §3 |

절약 강도 100%를 고르면 챌린지 한도가 0원이 되어 카테고리 전체 절감과 같아진다.

> ②의 `확보 절약액`은 챌린지 진행 중 거래에 따라 바뀌는 현재값이고 `누적 지킨 돈`은 확정값만 쌓인 장기 성장값이다. 둘 다 ②가 소유하며, ③은 이를 읽어 리포트로 서술한다.

## 1. 전체 관계

```text
                     (A) 분석 결과
┌──────────────────┐ ───────────────▶ ┌──────────────────┐
│ ① 소비 분석      │ ── (F) 재분류 ──▶ │ ② 지킴·성장      │
│    (상현)         │ ◀── (G) 종료 실적 │    (윤정)         │
└──────────────────┘                  └──────────────────┘
        │                                     │
        │ (B) 소비 분석 요약                    │ (C) 지킴·성장 상태
        ▼                                     ▼
┌───────────────────────────────────────────────────────┐
│ ③ 취향·추천 (가원)                                      │
│   ◀── (D) 외부 실제 금융상품 정보                        │
│   ◀── (H) 마이데이터 거래 원본 (집계·취향 분석 전용)      │
│   ──▶ 사용자: 주간·종료 리포트 + 맞춤 금융상품 정보성 추천 │
└───────────────────────────────────────────────────────┘
```

| 연결 | 방향 | 성격 | 주기 |
|---|---|---|---|
| A | ① → ② | 배치·이벤트 | 챌린지 시작 1회 · 신규 거래 분류 시 |
| B | ① → ③ | 배치 | 챌린지 시작·주간·종료 |
| C | ② → ③ | 상태 이벤트 | 지킴·성장 상태 변경 시 · 챌린지 종료 |
| D | 외부 → ③ | 데이터 | 갱신 시 |
| F | ① → ② | 이벤트 | 오분류 수정 시 |
| G | ② → ① | 배치 | 챌린지 종료 1회 |
| **H** | **마이데이터 → ③** | **조회** | **리포트 생성 시 (2026-07-28 신설, R10)** |

돈에서 성장으로 이어지는 처리는 ② 내부에서 끝난다. 이전 (E) ③→① 성장 요약과 (D) ②→③ 성장 반영은 폐기하고, (D)를 외부 금융상품 정보 연결로 재정의했다. ③에서 ①·②로 상태를 바꾸는 역방향 연결은 없다.

## 2. 영향 규칙

### R1. ③은 ②의 금액·성장과 ①의 선택을 바꾸지 않는다

③은 ①의 분석과 ②의 지킴·성장 상태를 읽어 리포트·추천으로 표현할 뿐이다.

```text
허용  "지금 100,000원을 지키는 중이에요."
허용  "아낀 돈을 둘 곳으로 이런 예·적금이 있어요. 가입은 각 사로."

금지  강도·지킬 돈·지킨 돈·성장 레벨을 임의 변경
금지  특정 상품 가입을 위해 목표 금액·페이스를 만들어 유도
```

### R2. 계산은 규칙 엔진, 표현은 LLM

| 규칙 엔진 | LLM |
|---|---|
| 기준 지출·챌린지 한도·지킬 돈·확보 절약액 계산 (②) | 실시간 차감 설명 (②) |
| 챌린지 확정·중복 반영 방지 (②) | 추천 근거·성향 문장 (①) |
| 누적 지킨 돈·성장 레벨 계산 (②) | 주간·종료 리포트·성장·회고 서술 (③) |
| 리포트 소비 흐름 집계 (③, **마이데이터 직접 집계로 확정**) · 상품 매칭·정렬 (③, 방식 미정) | 추천 사유 문장 (③) |

LLM은 금액·레벨·판정을 생성하거나 수정하지 않는다.

### R3. ②는 사실을 만들고 ③은 소통한다

| 시점 | ② 지킴·성장 | ③ 취향·추천 |
|---|---|---|
| 챌린지 시작 | 지킬 돈·내부 챌린지 한도 확정 · 새 챌린지 시작 | — |
| 진행 중 | 거래 자동 반영·초과분 차감·실시간 알림 | — |
| 주간 | 지킴 상태 제공 (C) | 마이데이터 직접 집계 + (C) 금액으로 판정 없는 주간 리포트 |
| 챌린지 종료 | 확정 지킨 돈·성장 누적·챌린지 기록 | 종료 리포트·성장 서술·맞춤 금융상품 정보성 추천 |

### R4. 금액 복구 경로는 재분류와 취소·환불뿐이다

맥락 태그, 캐릭터 상태, 챕터 연출은 ②의 금액에 영향을 주지 않는다.

### R5. 챌린지 진행 중 기준은 소급 변경하지 않는다

진행 중인 기준 지출·선택 카테고리·절약 강도는 챌린지 종료까지 고정한다. 다음 제안은 새 챌린지 선택 화면에서 사용자가 확정한다.

### R6. 다음 챌린지 분석은 종료 마감을 기다린다

```text
1. ② 챌린지 지킨 돈 확정·성장 누적 → G 발행
2. ①이 G를 수신 → 다음 챌린지 분석 → A와 B 발행
```

③의 리포트·추천은 사용자 산출물이며 다음 챌린지 분석을 막지 않는다.

### R7. 소비 집계는 카드 승인내역만으로 한다 (2026-07-28 현실 반영)

②의 집계 지출은 카드 승인내역만으로 계산한다. 카드 대금 출금의 이중 계상을 막기 위해서다.
**③의 직접 집계에도 같은 규칙이 적용된다(R10)** — 카드 승인 22만원과 그 대금이 빠져나간 계좌 출금 22만원을 함께 더하면 리포트가 소비를 두 배로 말하게 된다.

#### 계좌에서 실제로 쓰는 것

이전 판은 `계좌 거래는 고정지출·구독 탐지에 사용한다`였으나 **구현과 달랐다.** 실제는 다음과 같다.

| 계좌에서 쓰는 것 | 쓰지 않는 것 |
|---|---|
| 급여액 · 급여일 · 잔액 | 계좌 거래를 통한 고정지출·구독 탐지 |

- 백엔드는 계좌를 조회하되 **급여만 꺼내 쓰고 거래내역은 적재하지 않는다**(`MyDataLinkService`).
- **고정지출·구독은 100% 카드 결제에서 탐지된다**(`RecurringPaymentDetector`는 `UserPayment`만 본다).
- 따라서 (A)의 `fixed_expenses[].source`는 `bank`가 아니라 `card`이고, `day_of_month`는 계좌 인출일이 아니라 **카드 결제일**이다.

> 더미 계좌의 입금은 **급여 한 종류뿐**이고(`type = DEPOSIT(월급) | WITHDRAWAL(카드 출금)`), 계좌 자동이체 거래는 존재하지 않는다. 계좌 기반 탐지를 되살리려면 더미 생성기에 해당 거래를 먼저 추가해야 한다.

### R8. 성장은 챌린지 확정값만 먹고 뒤로 가지 않는다 (②)

성장 계산·누적은 ② 내부에서 처리한다.

```text
이번 챌린지 성장 반영액 = 챌린지 확정 지킨 돈
누적 지킨 돈 += 이번 챌린지 성장 반영액
성장 레벨 = 누적 지킨 돈 구간
```

- 챌린지 진행 중의 지킨 돈 변동은 성장에 반영하지 않는다.
- 동일한 `idempotency_key`는 한 번만 반영한다.
- 지킨 돈이 0원인 챌린지에는 성장값이 유지된다.
- 누적 지킨 돈·레벨·외형을 차감하거나 리셋하지 않는다.
- 챌린지 종료 이후 늦게 들어온 취소·정정은 별도 보정 정책으로 처리하되 이미 확정된 성장값을 소급 차감하지 않는다.

### R9. 소비 목표·보상은 배제, 금융상품은 정보성만 (D)

목적지·목표 금액·도착률·예상 페이스·소비형 보상·상점 데이터는 어느 Agent 스키마에도 두지 않는다. 지킨 돈의 사용처는 사용자의 자유다.

금융상품은 예외다. 실제 상품 정보는 외부 연결 (D)로 ③에만 들어오며, ③은 개인화된 **정보성 비교**로만 사용한다. 판매·중개·가입 대행 데이터, 상품에 맞춘 목표 금액·달성 페이스는 두지 않는다.

### R10. ③의 직접 집계는 서술용이며 ②의 금액을 대체하지 않는다 (2026-07-28 신설)

③은 리포트를 만들기 위해 마이데이터 거래를 직접 집계한다. ②가 챌린지 선택 카테고리만 알고 있어 전체 소비 흐름을 낼 수 없기 때문이다. 대신 경계가 분명해야 한다.

| ③이 직접 집계해도 되는 것 | 반드시 ②의 (C) 값을 그대로 쓰는 것 |
|---|---|
| 기간별·카테고리별 소비 합계·건수 | `securedSaving` — 지킨 금액 |
| 시간대·요일 분포, 반복 결제 | `achievementRate` — 달성률 |
| 선택하지 않은 카테고리를 포함한 전체 흐름 | `daysLeft` — 남은 일수 |
| 취향·선호 특징 | `state` — 챌린지 상태 |

```text
허용  "이번 주 카페에서 4번, 21,000원 썼어요. 지금 100,000원 지키는 중이에요."
       └─ 앞은 ③ 집계, 뒤는 ②의 securedSaving 그대로

금지  ③이 집계한 지출로 지킨 돈·달성률을 다시 계산해 표시
금지  ③ 집계값과 ②의 spentAmount가 어긋날 때 ③ 쪽을 사실로 제시
```

**두 숫자는 원래 다르다.** ②의 `spentAmount`는 성역·무관 카테고리를 빼고(C4), 24시간 되돌리기와 면제권을 반영한(§4.2) 값이다. ③의 집계는 그런 보정을 하지 않은 원본 흐름이다. 같은 화면에 두 숫자를 나란히 놓아 사용자가 대조하게 만들지 않는다.

`spentAmount`가 필요하면 ③이 다시 세지 말고 (C)에서 읽는다.

#### 자금 흐름 축(L1~L5) 재료 — 2026-07-28 신설

`income_profile`·`fixed_expense_summary`·`preferential_material`·`recurring_payments.day_of_month`는 ③의 라이프스타일 5축 계산에 쓴다. **③이 직접 뽑지 않고 ①이 넘기는 이유는 R7이다** — 급여·고정비는 계좌를 봐야 알 수 있는데 ③은 계좌 원본을 만질 수 없다.

`cash_buffer`는 L3(안정성) 재료다. **AoM(Age of Money)** = `평균잔고 ÷ 월평균지출`로, "지금 소득이 끊겨도 며칠 버티나"를 잰다. 옛 L3(`kept_cv` 지킨 돈 변동성)는 저축 여력이 아니라 사용자의 챌린지 목표 변경 빈도를 재는 결함이 있어 폐기했다 — `12_리포트_라이프스타일_설계.md` §4.1.
잔고는 계좌를 봐야 알 수 있으므로 R7에 따라 ①이 계산해 넘긴다.

`category_tree_version`은 ①과 ③이 같은 분류 기준을 쓰도록 고정한다. 연간 리포트의 취향 축(영화·전시 집계)이 ①의 카테고리 트리에 의존하기 때문이다.

> **산출 가능성 확인 완료 (2026-07-28, 코드 대조)**
>
> | 필드 | 상태 |
> |---|---|
> | `monthly_income_est` | 이미 `AppUser.monthlyIncome`에 저장돼 있다 |
> | `salary_day_of_month` | 마이데이터 `mydata_account_payday`에 있으나 백엔드가 아직 가져오지 않는다 |
> | `card_spend_monthly` (카드사별) | **가능.** `UserPayment.cardCode` → `UserCard.companyName`. `MyDataLinkService`가 이미 카드별 당월 실적을 계산 중이라 그룹핑만 바꾸면 된다 |
> | `salary_transfer` | 가능 |
> | ~~`auto_debit_count`~~ | **제외.** 더미 계좌에 자동이체 거래가 없다(R7). 우대조건에서도 뺀다 |
>
> `income_method`가 `provided_by_source`인 이유: 더미 계좌는 급여를 **선언값으로** 갖고 있어 추정이 필요 없다.
> 입금 내역에서 급여를 골라내는 것 자체는 어렵지 않지만(정기성 + 금액 유사 + 급여일 ±3일), 더미의 입금이
> **급여 한 종류뿐**이라 만들어도 검증할 수 없다. 실제 마이데이터로 확장할 때 더미 생성기에 급여 아닌
> 입금(이체·환급·보너스)을 먼저 섞어야 한다.

- 원본 거래 전체가 아니라 분석 요약을 전달한다. **원본 거래가 필요한 취향 분석·리포트 집계는 ③이 마이데이터에서 직접 읽는다(R10).** (B)는 ①이 이미 낸 분석을 재사용하기 위한 것이지 ③의 유일한 입력이 아니다.
- 보호 신호를 소비형 목표·보상 추천으로 사용하지 않는다.

### (D) 외부 → ③ · 실제 금융상품 정보

아낀 돈의 보관처(저축)를 정보성으로 비교하기 위한 실제 상품 정보다. 데이터 출처와 상품군 범위는 **미정**이며, 필드는 예시다.

```json
{
  "fetched_at": "20260731",
  "products": [
    {
      "provider": "○○은행", "name": "○○적금", "type": "적금",
      "base_rate": 3.2, "max_rate": 4.0, "term_months": 12, "reserve_type": "정액적립식",
      "preferential_raw": "당행 카드 월 30만원 이상+급여이체 (최고 0.8%p)",
      "preferential_conditions": [
        { "code": "card_spend", "threshold": 300000, "issuer_scope": "own_bank", "rate_bonus": 0.5, "source": "parsed" },
        { "code": "salary_transfer", "rate_bonus": 0.3, "source": "parsed" }
      ],
      "join_channel": "각 사", "source_url": "..."
    }

```

- 금리는 실제 값이며 `가입은 각 사로` 안내와 함께 정보성으로만 표시한다.
- 판매·중개·가입 편의 필드(제휴 링크, 신청 폼 등)는 두지 않는다.
- ③은 이 정보를 **자금 흐름 축(L1~L5)과 우대조건 충족 여부**에 맞춰 정렬·비교한다. 취향은 매칭 입력이 아니다(`12` §4.3).

> **`preferential_conditions[]`는 파생값이다.** 실제 출처(금감원 추정)는 `baseRate`/`primeRate`(기본/최고)만 구조로 주고 **우대조건은 자연어 `spclCnd` 문자열로만** 준다. 조건별 `rate_bonus`는 그 문자열을 파싱해 채운 것이라 정확도를 보장할 수 없다.
> 그래서 원문 `preferential_raw`를 필수로 두고 `source: "parsed"`로 파생임을 명시한다. 파싱 신뢰도가 낮은 동안에는 **전부 충족 → `max_rate` / 하나라도 미충족 → `base_rate`** 이분 표시만 쓰고, 조건별 부분 가산은 보류한다.
> `base_rate`·`max_rate`는 실제 `baseRate`·`primeRate`에 1:1 대응하므로 즉시 쓸 수 있다.

- `flow`·`time_patterns`·`category_share`·`highlights`는 ③이 마이데이터에서 직접 집계한 값이다(R10). 선택하지 않은 카테고리도 포함한다.
- `vs_previous_challenge`는 달력 월이 아니라 **직전 챌린지** 대비다.
- `identity_label`은 `highlights`의 집계 숫자와 **함께** 노출한다. 숫자 없이 라벨만 쓰면 성향 단정이 된다(`12` §5).
- `growth_narrative`는 **현재 항상 `null`이다.** 누적 지킨 돈·레벨이 (C)에 없어서 만들 수 없다(§8).
- `lifestyle_profile`은 **자금 흐름 축(L1~L5)** 요약이다. 취향 축은 여기 넣지 않는다 — `annual_report`로만 간다(`12` §4.3).
- `effective_rate_basis`는 `all_met` · `base_only` · `partial_est`. 우대조건 파싱 신뢰도가 낮으면 `partial_est`를 쓰지 않고 이분만 쓴다.
- 다음 챌린지 분석은 ②의 (G)만으로 시작한다. ③ 산출물은 게이팅에 쓰지 않는다.

### (F) ① → ② · 재분류

```json
{
  "approved_num": "0021458823001",
  "from_category": "taxi",
  "to_category": "transport_fixed",
  "amount": 23500,
  "action": "revert_and_reassign"
}
```

②는 원 카테고리 집계 지출을 복구한다. 새 카테고리가 선택 대상이면 다시 가산하고, 아니면 추적 대상에서 제외한다.

### (G) ② → ① · 챌린지 종료 지킴 실적

> ⚠ **미개정 — ①(상현) 확인 대기.** 아래 스키마는 옛 금액 모델(`spend_limit`·`protect_amount`·`kept_amount`) 그대로다.
> `11_지킴이_Agent_설계.md` §0.2가 **산출 주기를 달력 월 → 챌린지 종료일로** 바꾸라고 요구하고 있으나,
> (G)는 ②→① 계약이라 ③이 임의로 고치지 않았다. `result`의 full/partial/missed 정의는 유지된다.

```json
{
  "period": "2026-07",
  "baseline_total": 230000,
  "spend_limit": 115000,
  "protect_amount": 115000,
  "accumulated_spend": 140000,
  "kept_amount": 90000,
  "result": "partial",
  "context_tags": {
    "taxi": { "planned": 1, "tried": 1, "unavoidable": 3 },
    "delivery": { "planned": 2, "tried": 1, "unavoidable": 0 }
  },
  "misclassify_rate": {
    "taxi": 0.0,
    "delivery": 0.08
  }
}
```

- `result`: `full` | `partial` | `missed`
- `full`: `accumulated_spend ≤ spend_limit`
- `partial`: `spend_limit < accumulated_spend < baseline_total`
- `missed`: `accumulated_spend ≥ baseline_total`
- `result`는 다음 달 분석용 내부 값이다.

검산:

```text
kept_amount
= max(protect_amount − max(accumulated_spend − spend_limit, 0), 0)
= 115,000 − 25,000
= 90,000
```

## 5. 타이밍

| 시점 | 실행 | 산출 |
|---|---|---|
| 최초 1회 | 연동 → ① 전체 분석 → ② 캐릭터 이름 설정 | 기준 지출·후보·캐릭터 |
| 챌린지 시작 | ① 재분석 → A·B → 사용자 카테고리·강도 선택 → ② 확정·챌린지 시작 | 이번 챌린지 지킴 계획 |
| 거래 수신 | ① 분류 → ② 집계·확보 절약액 갱신·실시간 알림 → C | 현재 지키는 금액 |
| 오분류 수정 | ① 재분류 → F → ② 정정 → C 재발행 | 금액 복구 |
| 매주 | ② 상태(C) + **③ 마이데이터 직접 집계** → ③ 주간 리포트 | 판정 없는 주간 리포트 |
| 종료 ① | ② 최종 집계·지킨 돈 확정·성장 누적 → C·G | 챌린지 확정·성장 |
| 종료 ② | ③ B·C·D + 직접 집계로 종료 리포트·맞춤 추천 생성(E) | 종료 리포트·추천 |
| 종료 ③ | ①이 G 수신 → 다음 챌린지 분석 → A·B | 다음 챌린지 추천 |

주기의 기준은 달력 월이 아니라 **챌린지 시작일·종료일**이다(②의 `startDate`·`endDate`).

## 6. 사용자 표현 원칙

| 시점 | 사용자 표현 |
|---|---|
| 진행 중 · 한도 이내 | 알림 없음 · Home `115,000원 지키는 중` |
| 진행 중 · 한도 초과 | `정해둔 범위를 15,000원 넘었어요. 100,000원 지키는 중이에요.` |
| 주간 | `이번 주 카페에서 4번, 21,000원 썼어요. 지금 100,000원 지키는 중이에요.` |
| 챌린지 종료 | `이번 챌린지에서 90,000원을 지켰어요.` |
| 레벨 상승 | `누적 420,000원과 함께 모아가 Lv.3으로 성장했어요.` — **현재 사용 불가(§8)** |
| 2차 가상 이체 후 | `지킴 계좌에 90,000원을 담았어요.` |
| 상품 추천 | `아낀 돈을 둘 곳으로 이런 예·적금이 있어요. 가입은 각 사로.` |

다음 표현은 금지한다.

- `오사카까지 27%`, `584,000원 남았어요`
- `목표 실패`, `보상을 골라보세요`
- `이 상품에 지금 가입하세요`, `여기서 바로 신청`(판매·중개 유도)
- `이 적금 채우려면 매달 얼마`(목표·페이스 재도입)
- `캐릭터가 약해졌어요`, `레벨이 내려갔어요`
- `출근 때문에 택시를 많이 타시네요`(소비 이유 단정) · `이건 필수 소비예요`(소비 성격 단정)
- `영화가 삶의 중요한 취미인 것 같아요`(취향 단정 — MVP는 사실 단계까지)
- 주간 리포트의 `80% 달성`·`이 페이스면`(관찰 단계에 평가 혼입)
- `줄여보세요`, `참아보세요`(행동 교정)

마지막 네 줄의 근거는 `12_리포트_라이프스타일_설계.md` §7이다. **AI는 소비를 설명하고, 소비의 의미는 사용자가 결정한다.**

## 7. 2차 구현 — 가상 금융 서버

②는 챌린지 확정 후 지킨 돈을 변경하지 않고 가상 금융 서버에 전달한다.

```json
{
  "idempotency_key": "user-001:2026-07:kept-amount",
  "from_account_id": "virtual-spending-001",
  "to_account_id": "virtual-protect-001",
  "amount": 90000,
  "reason": "monthly_kept_amount"
}
```

- 이체액은 ②의 챌린지 확정 지킨 돈과 같아야 한다.
- 0원은 이체하지 않는다.
- 같은 챌린지의 멱등키로 중복 이체를 막는다. (예시의 `2026-07` 자리는 챌린지 식별자로 바뀐다 — 2차 구현 시 확정)
- 계좌에는 누적 잔액만 표시하며 소비 목표 진척률을 계산하지 않는다.

### 8.1 열린 질문 — 누적 성과를 무엇 단위로 말할 것인가

> `커피값 아낀지 3개월째, 벌써 20만원 아꼈어요` 형태의 서술을 쓸 것인가? (2026-07-28 제기)

| | 정본 현재 | 위 서술이 요구하는 것 |
|---|---|---|
| 집계 단위 | **캐릭터 하나에 전부 합산.** 감정 이입 대상이 하나여야 해서(`10_여정과_성장` §2.1) | **카테고리별 누적** |
| 기간 표현 | 챌린지 기록 목록(CH-02)만 있고 지속 기간 개념 없음 | `N번째` 같은 연속 횟수 |
| 소유 | ② (누적 지킨 돈·레벨) | ③이 직접 집계해야 함 — ②는 카테고리별 누적을 갖고 있지 않다 |

카테고리 단위로 가면 **캐릭터 하나에 감정을 모으는 정본 원칙과 부딪힌다.** "커피 3개월째"와 "배달 1개월째"가 따로 놀면 캐릭터가 아니라 카테고리에 애착이 생긴다. 반대로 캐릭터 단위만 유지하면 `커피값을 줄이기로 했다`는 사용자의 원래 동기와 리포트가 겉돈다.

결정 전에는 **어느 쪽도 구현하지 않는다.** ③이 직접 집계하므로 카테고리별 누적은 기술적으로 가능하지만, 정본 개정 없이 만들면 R1(③은 성장을 바꾸지 않는다)과 충돌한다.
