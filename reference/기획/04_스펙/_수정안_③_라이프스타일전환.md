## 1. 요약

1. ③의 분석 축을 **취향(선호)** 에서 **라이프스타일(자금 흐름 구조)** 로 교체한다(D1). 정의가 R9 가드레일을 겸한다.
2. FP-01의 매칭 근거를 취향 → **우대조건 충족 판정에 기반한 실수령(예상) 금리**로 전환한다(D2).
3. 스키마: **(B)** 에 우대조건·소득 판정 재료를 신설(①→③, R7 준수), **(D)** 는 기본/최고금리 분리 + 조건 구조를 요구, **(E)** 는 `taste_summary` → 라이프스타일 프로필 + `reason`을 우대조건 근거로 재정의.
4. 라이프스타일 5축(L1~L5)은 **규칙 엔진이 계산**하고 LLM은 문장만 만든다(R2). L3 변동성이 상품군 1차 분기점.
5. **미해결 핵심**: 실제 출처(금감원 API 추정)는 우대조건을 **자연어 `spclCnd`** 로만 주므로, D2의 "조건별 가산금리" 정밀 산출은 현재 불가 — "충족 시 최고금리 / 미충족 시 기본금리" 수준이 한계. 취향(선호) 회고 용도·상품 출처는 열어둠(D3·미정).

```

### 변경 후
```
| **소비 성향 프로필** | ① | 소비 성향 요약과 충동 구매 지수 (변경 없음 — ①이 절약 후보 판정에 쓰는 값) |
| **라이프스타일 분석** | ③ | 사용자가 *무엇을 좋아하는가(선호)* 가 아니라, 돈이 *언제·얼마나·어떤 규칙성으로 들어오고 나가는가(자금 흐름 구조)* 를 도출한 것. 선호를 다루지 않으므로 "좋아하는 것을 위해 모으세요"가 구조적으로 생성되지 않는다(R9 가드레일 겸함). 5축 L1~L5로 구성. |
| **금융상품 정보성 추천** | ③ | 실제 상품 정보를 사용자의 **라이프스타일(자금 흐름 구조)과 우대조건 충족 여부**에 맞춰 개인화한 정보성 비교. 판매·중개 없음 |
```

**주의(용어 충돌 방지)**: `소비 성향 프로필`(①)과 `라이프스타일 분석`(③)은 다르다. ①은 *무엇을 어떤 성향으로 쓰는가*(절약 후보용), ③은 *자금이 어떤 구조로 흐르는가*(상품 매칭용). 둘을 혼용 금지.

      "preferential_conditions": [
        { "code": "card_spend",     "threshold": 300000, "issuer_scope": "own_bank", "rate_bonus": 0.5, "source": "parsed" },
        { "code": "salary_transfer",                                            "rate_bonus": 0.3, "source": "parsed" },
        { "code": "auto_debit",     "threshold": 2,                             "rate_bonus": 0.2, "source": "parsed" }
      ],
      "join_channel": "각 사",
      "source_url": "..."
    }
  ]
}
```

**변경 이유 / 현실 제약**
- D2를 구현하려면 조건을 판정 가능한 **구조**로 받아야 한다(자연어만으로는 규칙 엔진 매칭 불가, R2).
- **그러나** 기존 코드(`SavingsCompareService.Account`)가 쓰는 실제 출처(금감원 추정)는 `baseRate`/`primeRate`(기본/최고)만 구조로 주고, **우대조건은 자연어 `spclCnd` 문자열로만 온다.** 즉 위 `preferential_conditions[]`(조건별 `rate_bonus`)는 출처에 없는 값이며, `spclCnd`를 파싱해 채워야 한다.
- 그래서 `preferential_raw`(원문 자연어)를 필수로 두고, `preferential_conditions[].source: "parsed"`로 **파생임을 명시**한다. 파싱 정확도가 낮으면 조건별 가산은 신뢰 불가 → **폴백: `max_rate`(전부 충족 시)/`base_rate`(미충족 시) 이분 표시**만 확정 사용, 조건별 부분 가산은 파싱 신뢰도 확보 후.
- `base_rate`/`max_rate`는 실제 `baseRate`/`primeRate`에 1:1 매핑되므로 **이 두 필드는 즉시 사용 가능**.

## 5. 매칭 로직 규칙표 (규칙 엔진)

### 2026-07-28 개정

기존 `kept_cv`(지킨 돈 변동성) 기반의 "정액 vs 자유" 분기 로직은 폐기했다. `kept_cv`는 실제 저축 여력이 아니라 사용자의 챌린지 목표 변경 빈도를 반영하는 경향이 있었기 때문이다.

대신 재정 안정성은 **AoM(Age of Money)** 으로 판단한다.

또한 MOA의 지킨 돈은 월마다 금액이 달라지는 구조이므로 상품 추천의 중심축은 **정액적립식 ↔ 자유적립식**이 아니라 **파킹통장 ↔ 자유적립식**으로 본다.

### AoM(Age of Money) 정의

AoM은 사용자의 자금 버퍼 두께를 나타내는 지표다.

간이 계산식:

```text
AoM = 평균잔고 ÷ 월평균지출
```

예시

| AoM | 의미 |
|---|---|
| 0.5 | 약 2주치 생활비 보유 |
| 1.0 | 약 1개월치 생활비 보유 |
| 3.0 | 약 3개월치 생활비 보유 |

AoM이 높을수록 당장 사용할 가능성이 낮은 여유 자금이 많고, 낮을수록 유동성 확보 필요성이 크다.

AoM 구간 기준

```text
AoM < θ_buffer   → 버퍼 얇음
AoM ≥ θ_buffer   → 버퍼 두꺼움
```

※ θ_buffer는 실데이터 검증 후 확정

### 5.1 입력값

규칙 엔진은 아래 값을 계산한다.

| 항목 | 변수 | 의미 |
|---|---|---|
| 납입 규모 | `kept_mean` | 월 확정 지킨 돈 평균 |
| 안정성(버퍼) | `aom` | AoM(Age of Money) |
| 유동성 필요도 | `large_expense_cycle`, `predictable` | 큰 지출 주기와 예측 가능 여부 |
| 우대조건 | `met` | 카드 실적·급여이체 충족 여부 |

데이터 출처

| 변수 | 출처 |
|---|---|
| `kept_mean` | finalized_kept_amount 이력 |
| `aom` | cash_buffer |
| `large_expense_cycle` | recurring_payments + 대규모 지출 |
| `met` | preferential_material × 사용자 데이터 |

### 5.2 판단 로직

**M1. 상품 그룹 분류**

상품은 적립 방식별로 분리하여 제시한다.

- 파킹통장
- 자유적립식
- 정액적립식

전체 상품을 하나의 순위표로 합치지 않는다. 그룹 순서 자체가 추천 결과가 되므로, 적립 방식은 먼저 분리한다. (거울 원칙, 12 §1·§2)

**M2. 유동성 우선**

조건
- AoM 낮음(버퍼 얇음)
- 또는 `predictable = false`
- 또는 `large_expense_cycle`이 짧음

결과 → 파킹통장 그룹 상단 배치

**M3. 수익률 우선**

조건
- AoM 높음(버퍼 두꺼움)
- 그리고 큰 지출 예측 가능

결과 → 자유적립식 그룹 상단 배치

**M4. 정액적립식**

정액적립식 상품도 항상 노출한다.

표시 내용: `매달 고정 금액 납입 필요`만 제공한다.

금지 — `MOA 흐름과 맞지 않음` · `부적합` · `추천하지 않음` 등의 판단 표현.

적합 여부는 사용자가 결정한다.

**M5. 납입 규모 필터**

`kept_mean`을 활용하여 최소 가입금액·권장 납입금액 조건에 맞는 상품만 남긴다.

※ 규모는 필터 기준일 뿐 추천 방향을 결정하지 않는다.

**M6. 실수령 금리 계산**

- 우대조건 모두 충족 → `effective_rate = max_rate`
- 하나라도 미충족 → `effective_rate = base_rate`

현재 반영하는 우대조건: 카드 실적 · 급여이체
※ 자동이체는 데이터 부족으로 제외
※ 조건별 부분 가산은 상품 데이터 파싱 신뢰 확보 시에만 적용

**M7. 그룹 내 정렬**

각 그룹 내부에서만 정렬한다. 정렬 기준: `effective_rate` 내림차순. 그룹 간 우열은 매기지 않는다.

**M8. 우대조건 표시**

상품에는 실수령 금리(`effective_rate`) · 최대 금리(`max_rate`) · 현재 미충족 우대조건을 함께 노출한다.

예시:

```text
실수령 금리 3.2%
(조건 충족 시 최대 4.0%)
현재 미충족
- 카드 실적
```

사실 정보만 제공하며 가입 유도·행동 유도 표현은 사용하지 않는다. (R9)

**M9. 동점 처리**

같은 그룹 내에서 `effective_rate`가 동일할 경우

1. 미충족 우대조건 수가 적은 상품
2. 만기가 짧은 상품
3. `base_rate`가 높은 상품
4. 금융사명 가나다순

### 5.3 LLM 역할 범위

LLM은 상품 판정 · 그룹 분류 · 금리 계산 · 정렬 순서에 관여하지 않는다. LLM이 생성하는 영역은 `reason`과 `lifestyle_profile.narrative` 두 가지뿐 — 설명 문장 생성만 담당한다.

### 요약

AoM으로 사용자의 자금 버퍼를 판단한다. AoM이 낮거나 큰 지출 변동성이 크면 → 파킹통장 우선. AoM이 높고 지출 예측 가능성이 높으면 → 자유적립식 우선. 상품은 적립 방식별로 그룹화하고, 그룹 내에서는 실수령 금리 기준으로만 정렬한다. 정액적립식은 판단 없이 사실 정보만 제공한다.

**자문·중개 경계 판단(핸드오프 추가 확인사항)**
- "실제로 받으실 수 있어요"는 **사용자 마이데이터 사실(조건 충족)을 서술**하는 것이라, 특정 상품 가입 권유가 아니면 정보 제공 범위로 볼 여지가 크다. 기존 계약도 `가입은 각 사로`·판매/중개 금지로 이 선을 이미 지킨다.
- 다만 "이 조건을 채우면 +0.x% 더 받아요"는 **행동 유도**로 읽힐 수 있어 R9/판매유도 경계에 근접 → **사실 서술("○○ 조건은 아직 충족되지 않았어요")까지만, 명령형·페이스 금지**로 한정 권장.
- 확정이 어려우므로 위 미정표에 **`실수령 금리 제시의 자문·중개 경계`** 로 올리고 법무 확인 대상으로 둔다.

## 8. 확신이 낮은 지점과 그 이유

1. **(D) 조건별 가산금리 구조의 실현성 (가장 큼)** — 실제 출처(금감원 추정)는 우대조건을 자연어 `spclCnd`로만 준다(코드 `SavingsCompareService.Account.spclCnd` 확인). 조건별 `rate_bonus`는 파싱 산물이라 정확도 보장 불가. → 확정 사용은 "전부 충족=최고 / 미충족=기본" 이분까지. 부분 실수령 금리는 파싱 신뢰 확보 전까지 보류.
2. **AoM 계산의 데이터·정의** — AoM엔 평균잔고(계좌 잔액)가 필요한데 ③은 계좌 원본을 못 만져 ①이 (B) `cash_buffer`로 넘겨야 한다(R7). 카드 결제 시점과 실제 대금 출금 시점이 어긋나 순정 AoM은 왜곡될 수 있어 간이식(평균잔고÷월지출)으로 시작. 구간 임계 θ_buffer도 실데이터 검증 전 placeholder. (카드사별 실적 분리는 ①(상현)이 `cardCode`→`companyName`으로 가능 확인 완료)
3. **취소·환불의 `kept_mean` 영향** — `kept_cv`는 폐기했지만 규모 지표 `kept_mean`은 여전히 취소·환불에 흔들린다(실데이터: 환불 1건으로 월 총액 음수). 규모 필터(M5)가 튈 수 있어 취소 정규화 규칙 필요.
4. **L4의 1회성 지출 누락** — 고유 가맹점 284곳 중 75%가 1회성이고 금액의 44%를 차지. 반복 결제만으로 유동성(L4)을 잡으면 소비 절반이 누락 → "큰 1회성 지출" 포착 방식이 관건(반복성 기준만으론 부족).
5. **실수령 금리 표현의 법적 경계** — "실제로 받으실 수 있어요"가 자문·추천으로 읽힐 여지. 사실 서술로 한정하면 방어 가능하다고 보나 법무 확인 전까지 확신 낮음(§6 미정·판단 참조).
6. **정액적립식 무판정 노출의 부작용** — 정보성으로 노출하되 판정을 안 붙이므로(M4), 최고금리 상품이 정액이면 유저가 구조 부적합을 모르고 고를 수 있다. "매달 고정 금액 납입 필요" 사실 표시만으로 충분한지 UX 검증 필요(거울 원칙 vs 실질 도움의 긴장).
