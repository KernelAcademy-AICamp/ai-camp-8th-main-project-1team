## Part 1. 데이터 전제 — 소비 데이터는 어떻게 들어오는가

### Q1. 데이터 연동 방식은 무엇인가?

- 실제 마이데이터 사업자를 연동하지 않는다.
- 카드 승인내역과 은행 계좌 거래내역 응답 스키마를 모사한 더미 서버를 구축한다.
- 페르소나별 3개월 이상 거래로 분석·분류·차감·월말 리포트를 재현한다.
- 동의 플래그·페이지네이션·부분 실패·취소·정정을 실제처럼 처리한다.
- 계좌는 **급여·급여일·잔액만** 쓰고 계좌 거래는 적재하지 않는다. 누적 소비에도 반영하지 않는다.

> **정정 (2026-07-29).** 옛 판은 `계좌 거래는 고정지출·구독 탐지에 사용한다`였으나 **구현과 달랐다.**
> 고정지출·구독은 100% **카드 결제**에서 탐지된다(R7). 더미 계좌의 입금은 급여 한 종류뿐이고
> 자동이체 거래가 아예 없어, 계좌 기반 탐지를 되살리려면 더미 생성기를 먼저 고쳐야 한다.
> 계좌 적요의 규칙 분류(PRD §10.4)도 같은 이유로 미착수다.

### Q2. 실제 API 연결이 MVP의 전제인가?

- 아니다. 더미 서버가 1차 구현의 기본 플랜이다.
- 표준 필드와 pull 방식 제약은 문서로 검증한다.
- 실연동에서 결제 직후 데이터 수신을 보장할 수 없으므로 MVP 설명에도 `실시간 금융 알림`이라고 쓰지 않는다.

### Q3. 인증과 개인정보의 경계는?

- 가상 CI와 더미 이름·전화번호로 인증 화면만 시뮬레이션한다.
- 더미 이름·전화번호는 CI 반환 즉시 파기한다.
- 실제 CI 생성·검증, 실제 개인정보 수집·저장, 인증서 검증은 하지 않는다.

### Q4. 연동이 실패하면?

- 기관별 성공분을 먼저 반영하고 실패한 기관만 재시도한다.
- `/demo/*`에 시계 이동·거래 주입·초기화 기능을 둔다.
- 발표에서 `한도 이내 → 침묵`과 `한도 초과 → 초과분 차감·알림`을 모두 재현한다.

## Part 2. 자동 판정 — 시스템은 어떻게 지킴 상태를 아는가

### Q5. 선택 카테고리 소비는 어떻게 반영하는가?

```text
신규 카드 거래 (5분 증분 동기화)
→ 카테고리는 이미 붙어 있다 (Q6)
→ 환불이면 원 거래를 찾아 한도 복원 · 조용히
→ 분류 미확정이면 집계하지 않고 되묻기만
→ 성역·무관 카테고리면 원장에만 남기고 침묵
→ 선택 카테고리면 **즉시 집계 + 24시간 되돌리기**
   ├─ 페이스 이내: 침묵 (사물은 지급)
   └─ 페이스 초과·한도 80%·한도 초과: 케이스 우선순위대로 하나만 발화
→ 초과 확정(EXCEEDED)은 유예 만료 후 **새벽 배치**가 한다
```

- 사용자는 거래마다 확인하지 않는다. **"확인받고 차감"은 매번 버튼을 눌러야 해서 알림 피로가 커진다.**
- 금액을 되돌리는 경로는 넷이다 — 재분류 · 취소·환불 · `챌린지랑 상관없어요`(24시간) · 면제권.
- 맥락 태그는 다음 챌린지 분석용이며 금액을 면제하지 않는다.
- 상세는 `06_지킴이_Agent_설계.md` §3·§4.

### Q6. 거래와 카테고리는 어떻게 매핑하는가?

**매핑하지 않는다. 마이데이터가 이미 붙여서 준다** (2026-07-29 개정 · `07` R11 · `13` §3).

결제마다 대분류(식비·교통)와 중분류(카페·배달·택시)가 함께 내려온다. 실제 카드사 마이데이터도 가맹점 업종을 함께 주므로 이 구조가 비현실적인 것은 아니다. 옛 3단 파이프라인(키워드 사전 → ML 텍스트 분류 → LLM)은 **구현되지 않았고 지금 구조에서는 필요하지 않다.**

분류가 실제로 필요한 자리는 **PG 결제 하나뿐**이다.

```text
가맹점명 = "토스페이먼츠" · 대분류 = "온라인" · 중분류 = "미분류"
→ 무엇을 샀는지 알 수 없다
```

현재 처리는 **판정 제외**다. 절약 후보에서 빼고, 낭비/필수도 찍지 않는다. 정확도 때문이 아니라 태도 때문이다 — 무엇을 샀는지 모르는 결제에 성격을 붙이면 사용자가 근거 없이 평가받는다.

- **ML은 카테고리가 아니라 낭비/필수를 판정한다.** 이 프로젝트에서 ML을 쓰는 근거가 옮겨갔다(`13` §5).
- 사용자 수정은 **낭비/필수 재지정**(`본인에겐 필수`)으로 남아 있고, 카테고리 변경 경로 (F)는 미구현이다.
- **미해결**: 미분류 결제의 신뢰도가 1.0으로 고정돼 ②의 되묻기(C7)가 발화하지 않는다 — `13` §3.2.

#### 대분류와 중분류는 하는 일이 다르다

| | 대분류 | 중분류 |
|---|---|---|
| 예 | 식비 · 교통 · 온라인 | 카페 · 배달 · 택시 · 스트리밍 |
| 쓰는 곳 | 기준 지출 · 과소비 · 이상소비 탐지 · **②의 선택 카테고리** | 반복 결제 · **절약 후보** · 낭비 판정 |

**여기서 이음매가 어긋난다.** AN-01은 중분류 후보(`배달`)를 보여주는데 CT-01에서 ②로 넘어가는 선택 카테고리는 대분류라, `배달`을 고르면 `식비` 전체가 챌린지 대상이 되어 기준 지출이 훨씬 커진다. 층위 통일은 미결이며 ②의 스키마에 영향이 있다.

### Q7. 합계 차감인가, 카테고리별 차감인가?

- 사용자 차감은 **선택 카테고리 합계 기준**이다.
- 카테고리별 한도 상태는 내부 분석에만 보관한다.
- 한 카테고리가 자체 한도를 넘었어도 전체 합계 **챌린지 한도** 안이면 확보 절약액은 줄지 않고 알림도 없다.
- 한도(`기준 지출 − 지킬 돈`)와 남은 한도는 **사용자에게 숫자로 노출하지 않는다.** 말해야 하면 ②가 이미 문장으로 만든 표현을 쓴다.

## Part 3. Agent 정의서

### 3-1. 소비 분석 Agent

> 내부 명세 정본: `05_소비분석_Agent_설계.md`

- **트리거**: 온보딩 · 신규 거래(5분 증분 동기화) · 챌린지 시작 · 화면 진입(온디맨드)
- **입력**: 마이데이터 **카드 승인내역**(대·중분류가 붙어서 옴) · 계좌의 급여·급여일·잔액
- **출력**:

| 모듈 | 산출 | 단위 |
|---|---|---|
| 공유 분석 엔진 | 카테고리 집계 · **기준 지출** · **평균 결제액** · 과소비 · 장기 변동성 | 대분류 |
| 반복 결제 탐지 | 고정형(가맹점·주기·다음 예상일) · 루틴형(시간대·대표금액·빈도) | 중분류 |
| 소비 패턴 | 요일 × 시간대 히트맵 · 최대 지출 칸 | — |
| 소비 프로필 | **이상소비지수**(0~100) + 성분별 기여 점수 4종 | 대·중분류 |
| 절약 후보 | 3등급 규칙 후보 · **예상 절약액** · 근거 문장 | 중분류 |
| 단기 이상소비(FDS) | Modified Z + 룰 AND 결합 경고 | 대분류 |
| 낭비/필수 판정 | 거래별 낭비 확률 + **왜 낭비인지**(특징 기여) | 중분류 |

- **ML**: **낭비/필수 판정**(EBM — 해석가능 가법 모델). 카테고리 분류가 아니다.
- **LLM**: 절약 후보 권유 문장 · 성향 요약 문장. **숫자를 만들지도 바꾸지도 않는다.** 실패 시 템플릿 폴백(`AI` / `TEMPLATE` / `TEMPLATE_FALLBACK`을 응답에 표시).
- **규칙**: 집계·평균·빈도 · 반복 주기 판정 · 3등급 절약 후보 · z-score·룰 결합
- **하지 않음**: **카테고리 분류**(제공자 소관) · 카테고리 자동 확정 · **권장 강도 산출**(현재 ②의 `기준 지출 ÷ 3`) · 소비 목표 추천 · 취향 분석(③)
- **미구현**: 계좌 적요 분류 · 가치 소비 보호 신호 반영 · (B) 발행 · (F) 재분류 · (G) 수신

### 3-2. 지킴·성장 Agent

> 내부 명세 정본: `06_지킴이_Agent_설계.md` (v1.2 · 백엔드 구현 완료)

- **트리거**: 챌린지 시작 · 신규 거래 · 되돌리기·환불 · **새벽 배치** · 챌린지 종료 · 캐릭터 생성
- **입력**: ①의 기준 지출·평균 결제액 · 사용자 선택(카테고리·지킬 돈·성역) · 신규 카드 거래
- **출력**:
  - 챌린지 한도(내부값·비노출) · 지킬 돈 · 집계 지출 · 남은 한도
  - **확보 절약액 · 달성률** — ③이 서술에 쓰는 두 숫자
  - 상태 9종(`SETUP`→`ACTIVE`⇄`AT_RISK`→`EXCEEDED`→`SETTLING`→ 결과 4종)
  - 일 판정(무지출·페이스 이내·페이스 초과) · 사물·포인트 · 개입 알림
- **LLM**: 비난 없는 차감·회복 문구. **규칙이 "보낼지"와 "무슨 숫자를"까지 다 정한 뒤에야 불린다.**
- **규칙**:

```text
챌린지 한도 = 기준 지출 − 지킬 돈
남은 한도   = 한도 − 집계 지출
확보 절약액 = min(지킬 돈, max(0, 기준 지출 − 집계 지출))
달성률      = 확보 절약액 / 지킬 돈
허용 비율   = 판정 대상 일차 / 총 일수 + 버퍼      버퍼 = min(0.20, 평균 결제액 / 한도)
성장 반영액 = 챌린지 확정 지킨 돈 (멱등)
```

- **개입은 케이스 C1~C14 중 먼저 걸린 하나만.** 하루 푸시 2건 · 야간 22~08시 침묵 · 침묵도 사유와 함께 기록한다(`11` §3).
- **하지 않음**: LLM 금액·상태 계산 · 태그에 따른 면제(되돌리기·면제권만) · 리포트·추천 생성(③)

### 3-3. 취향·추천 Agent

> 내부 명세 정본: `07_취향분석및추천_Agent_설계.md` (v1 · 미구현)

- **트리거**: 주간 · **챌린지 종료** · 달력 연말 · 리포트·추천 화면 진입
- **입력**: **마이데이터 직접 집계**(R10) · ①의 소비 분석 요약 (B) · ②의 지킴·성장 상태 (C) · 외부 실제 금융상품 정보 (D)
- **출력**:

| 리포트 | 주기 | 성격 | 금지 |
|---|---|---|---|
| 주간 | 챌린지 시작일 기준 7일 | **관찰** — 무슨 소비가 있었나 | 달성률·페이스 평가 |
| 월간 | **챌린지 종료일(30일)** | **회고** — 어떤 흐름이었나 | 실패·합격 불합격 · 취향 해석 |
| 연간 | 달력 연도 | **정체성** — 올해 나는 어떤 사람이었나 | (여기서만 제한적 취향 서술 허용) |

- 라이프스타일 분석 = **자금 흐름 축(L1~L5)** + **취향 축**. 두 축은 직교하며 경로가 다르다.
- 맞춤 금융상품 정보성 비교(FP-01, 근거는 자금 흐름 축) · 카드 비교(FP-03, 근거는 취향 축)
- **LLM**: 리포트·회고 서술 · 추천 사유 문장
- **규칙**: 리포트 집계 · 5축 분류 · 상품 매칭·정렬(M1~M9)
- **하지 않음**: ②의 금액·성장 값 변경 · **취향을 저축 상품 매칭에 넣기**(입력에서 구조적으로 제외) · 목적지·소비형 보상 · 판매·중개·가입 대행 · 목표·페이스 재도입

## Part 4. Agent 간 연결

| 연결 | 전달 데이터 | 갱신 주기 | 구현 |
|---|---|---|---|
| 분석 → 지킴 (A) | 기준 지출 · **평균 결제액** · 절약 후보 · 추천 근거 | 챌린지 시작 · 거래 증분 | ⚠️ 스키마가 아니라 **인프로세스 함수 호출** |
| 분석 → 취향·추천 (B) | 소비 분석 요약(월평균·반복 결제·패턴·후보+예상액·이상소비지수·자금 흐름 재료) | 챌린지 시작·주간·종료 | ❌ 미발행 — ③이 계좌 요약을 직접 읽는 중 |
| 지킴 → 취향·추천 (C) | 확보 절약액 · 달성률 · 남은 일수 · 상태 | 상태 변경 시 · 챌린지 종료 | ✅ `GET /api/guardian/home` |
| 외부 → 취향·추천 (D) | 실제 금융상품 정보(실 금리 등, 정보성) | 갱신 시 | △ 금감원 오픈API 연동됨, 매칭 미구현 |
| 마이데이터 → 취향·추천 (H) | 거래 원본(집계·취향 분석 전용, R10) | 리포트 생성 시 | ✅ 조회 가능 |
| 분석 → 지킴 (F) | 오분류 재분류 결과 | 수정 즉시 | ❌ 미구현 — 경로 없음 |
| 지킴 → 분석 (G) | 챌린지 종료 실적·맥락 태그·오분류율 | 챌린지 종료 | ❌ 미구현 · 스키마도 미개정 |

- **성장은 ② 내부에서 처리한다** (별도 ②→③ 성장 반영·③→① 요약 없음).
- 주기의 기준은 달력 월이 아니라 **챌린지 시작일·종료일**이다.
- 종료 순서는 `② 지킨 돈 확정·성장 누적 → (G) → ① 다음 챌린지 분석`이며, ③의 리포트·추천은 사용자 산출물이라 게이팅에 쓰지 않는다. **다만 (G)가 없어 이 순서는 현재 강제되지 않는다.**
- **카테고리 분류는 어느 Agent도 소유하지 않는다** — 마이데이터 제공자가 준다(R11).
- 상세 스키마와 쓰기 권한은 `02_에이전트_연결부.md`를 따른다.

## Part 6. 월간 상태와 성장 전이

```text
카테고리·강도 선택 중
→ 지키는 중
→ 월말 지킨 돈 확정
→ 캐릭터 성장·챕터 기록
→ 다음 달 카테고리·강도 선택
```

내부 분석 상태:

| 결과 | 조건 |
|---|---|
| full | 누적 소비 ≤ 사용 한도 |
| partial | 사용 한도 < 누적 소비 < 기준 소비 |
| missed | 누적 소비 ≥ 기준 소비 |

사용자 리포트는 내부 상태를 실패 낙인으로 전면 노출하지 않고 `이번 달 {금액}원을 지켰어요`를 중심으로 구성한다.

### Q10. 중간에 소비한 사용자에게 무엇을 보여주는가?

- 한도 이내면 Home 금액을 유지하고 알리지 않는다.
- 한도를 넘겼어도 현재 지키는 금액이 남아 있으면 그 금액을 계속 보여준다.
- 0원이 되어도 월간 경험을 조기 종료하지 않는다.
- 불가피 태그가 반복되면 다음 달 다른 카테고리나 낮은 강도를 제안한다.

### Q11. 부분 달성 금액은 어떻게 처리하는가?

- 1차: 월말 확정 지킨 돈으로 리포트와 성장 원장에 반영한다.
- 2차: 0원보다 크면 내부 결과 상태와 관계없이 가상 지킴 계좌로 옮긴다.

### Q12. 성장은 언제 확정하는가?

- 월중 상태는 캐릭터 연출에만 사용한다.
- 월말 원장 마감 뒤 확정 지킨 돈을 한 번 누적한다.
- 같은 월의 멱등키는 재반영하지 않는다.
- 성장·레벨·외형은 감소하거나 리셋되지 않는다.

## Part 7. 소비 목표 비개입과 가상 계좌

### Q13. 사용자의 목표는 무엇인가?

- 서비스가 여행·물건 목표를 제시하지 않는다.
- 제품 안의 목표는 `아낄 수 있는 돈을 아끼는 행위` 자체다.
- 이를 캐릭터가 돈을 지키며 성장하는 여정으로 동기 치환한다.

### Q14. 지킨 돈의 사용처는 어떻게 다루는가?

- 사용자의 자유다.
- 소비형 보상·상점을 추천하지 않는다. 금융상품은 정보성 비교만 제공한다(판매·중개 없음, `가입은 각 사로`).
- 사용처를 캐릭터 성장 조건과 연결하지 않는다.

### Q15. 가상 지킴 계좌는 언제 붙는가?

- 2차 구현에서 별도 가상 금융 서버로 구현한다.
- 월말 지킨 돈 확정 후 멱등키를 포함해 이체한다.
- 누적 잔액만 표시하며 목표 진척률은 만들지 않는다.

## Part 8. 데이터·데모 준비

### Q16. 시연용 거래는 어떻게 만드는가?

- 페르소나별 3개월 이상 소비 패턴을 설계한다.
- 택시·배달 등 줄이기 후보와 건강·가족·취미 등 보호할 가치 소비를 함께 넣는다.
- 가맹점명은 명확·PG사·애매한 이름을 섞는다.
- 계좌 거래에는 급여·카드 대금·고정지출·구독 자동이체를 넣는다.
- 시드를 고정해 추천과 월말 결과를 재현한다.
