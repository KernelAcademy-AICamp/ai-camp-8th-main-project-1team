# MOA 용어 사전 v1.10

기획·디자인·개발이 같은 것을 같은 이름으로 부르기 위한 기준 문서.

**사용 규칙**
- 화면 문구는 `사용자 노출` 열의 표현만 사용한다. 새 표현이 필요하면 이 문서에 먼저 추가한다.
- API 응답 필드명은 `내부 필드` 열을 따른다.
- 여기 없는 개념이 화면에 등장하면, 그 화면은 정의되지 않은 상태다.

> **필드명 표기 규칙 (v1.9)** — 이미 이름이 있는 개념은 **현행 정본의 이름을 그대로 쓴다.**
> `02_에이전트_연결부.md`의 (C) 계약은 camelCase, ①의 (A)·(G) 계약은 snake_case라 두 표기가 섞인다.
> `expected_saving` 하나만 snake_case인 것은 오타가 아니라 (A) 계약 소속이기 때문이다.
> 현행에 이름이 없던 개념(`cutRate`·`overspend`·`originalBaseline`·`spendTag` 등)만 이 문서에서 새로 붙인다.

## 1. 돈

| 정식 명칭 | 사용자 노출 | 내부 필드 | 정의 |
|---|---|---|---|
| 기준 소비 | 지난달 ○○원 썼어요 | `baselineAmount` | 절약 카테고리의 **직전 1개월** 실지출액 |
| 최초 기준 소비 | 원래 쓰던 금액 | `originalBaseline` | 첫 챌린지 시작 시점의 기준 소비. 이후 갱신하지 않음 |
| 새는 돈 | 줄일 수 있는 돈 | `expected_saving` | 낭비 판정이 찾아낸 절감 가능액 **전체 후보** |
| 절약 강도 | 조금 20% / 적당히 50% / 확실히 100% | `cutRate` | 프리셋 3종 + 직접 조정 |
| **지킬 돈** | 이번 달 목표 | `targetSaving` | **새는 돈 × 절약 강도** |
| **한도** | 이번 달 쓸 수 있는 돈 | `challengeCap` | 기준 소비 − 지킬 돈 |
| 사용액 | 쓴 돈 | `spentAmount` | 절약 카테고리 소속 결제 합계 |
| 남은 한도 | 남은 돈 | `remainingCap` | 한도 − 사용액 |
| 초과분 | 넘긴 돈 | `overspend` | `max(0, 사용액 − 한도)` |
| **지킨 돈** | 지킨 돈 | `securedSaving` | 지킬 돈 − 초과분 |
| 전체 소비 | 전체 소비 | `totalSpend` | 전 카테고리 결제 합계. **조회 전용** |

> **새는 돈 ≠ 지킬 돈.**
> 새는 돈은 후보군, 지킬 돈은 그중 사용자가 고르고 강도를 곱한 계약분이다.
> `새는 돈` → 사용자 선택 → `× 절약 강도` → `지킬 돈`
>
> **강도의 분모는 기준 소비가 아니라 새는 돈이다.**
> 제거가능 등급은 두 값이 같지만, 최적화가능 등급은 새는 돈이 중앙값 초과분뿐이라 크게 다르다.
> 한식 지출 300,000 / 새는 돈 80,000에 강도 50%를 적용하면 목표는 40,000이지 150,000이 아니다.
> 한도는 기준 소비에서 뺀다. 위 예에서 한도는 260,000 — "지난달보다 4만원만 덜 쓰기"가 된다.

## 4. 거래 태그

**범위 — 절약 카테고리 소속 거래에만 부착한다.**
보호·성역·판정 밖·미선택 카테고리에는 태그 UI를 노출하지 않는다.

| 태그 | 값 | 의미 |
|---|---|---|
| 계획했던 | `PLANNED` | 의도한 지출 |
| 줄이려던 | `REGRET` | 줄이려 했으나 쓴 지출 |
| 불가피한 | `UNAVOIDABLE` | 상황상 어쩔 수 없던 지출 |

**저장** — 전역 `waste_label`(ML 정답지, 앱 미노출)과 분리하여 별도 테이블에 적재한다.
전역 라벨은 판정용, 태그는 개인화용으로 역할이 다르다.

**활용 단계**

| 단계 | 범위 | 시점 |
|---|---|---|
| 1 | 수집만. 판정에 영향 없음 | MVP |
| 2 | 태그 누적에 따라 다음 챌린지 **후보 순위 낮추기** (아래 기준) | MVP |
| 3 | 개인 가치소비 모델 학습 | MVP 이후 |

### 후보 순위 낮추기

3/4 화면의 후보 목록은 절감액 순으로 정렬되고 상위 항목에 `AI 추천` 배지가 붙는다.
개인 태그로 "이 사람에겐 낭비가 아니다"가 확인된 카테고리는 이 목록에서 **아래로 내린다.**
목록에서 제외하지는 않으므로 사용자는 여전히 고를 수 있다.

**발동 기준**

> 최근 **3개 챌린지** 안에서, 해당 중분류의 태그가 **3건 이상**이고
> 그중 `UNAVOIDABLE` 비율이 **60% 이상**이면 1단계를 적용한다.

건수가 아닌 비율을 쓰는 이유는, 결제가 잦은 카테고리(카페 등)가 구조적으로 불리해지지 않게 하기 위함이다.
태그 집계 창을 챌린지 단위로 잡으므로, 태그 저장 시 **챌린지 ID를 함께 적재**한다.

**적용 방식 — 가중치 계수**

```
정렬 키 = expected_saving × 0.7 ^ (적용 단계)
```

한 칸씩 밀어내는 방식은 금액 격차를 반영하지 못한다(25만원짜리와 6만원짜리가 똑같이 한 칸).
계수 방식은 격차가 크면 내려가도 상위에 남고, 비슷한 항목끼리만 순서가 바뀐다.
여러 항목이 동시에 걸려도 결과가 하나로 정해진다.

> **정렬 키는 표시값이 아니다.** 화면에 보이는 절감액은 계수를 곱하지 않은 원래 `expected_saving`을 쓴다.

태그는 후보 **순위**에만 영향을 주고 후보 **자격**은 박탈하지 않는다.
`UNAVOIDABLE` 남발로 후보가 비는 상황을 막기 위함이다.

**한계** — 태그가 선택한 카테고리 안에서만 쌓이므로, 아직 고르지 않은 카테고리에는 개인 이력이 없다.
선택 카테고리가 매달 바뀌며 커버리지가 넓어지는 것에 의존한다.

## 5. 계산 순서

```
① baselineAmount   = 직전 1개월 카테고리 실지출
② targetSaving     = expected_saving × cutRate
③ challengeCap     = baselineAmount − targetSaving
④ overspend        = max(0, spentAmount − challengeCap)
⑤ securedSaving    = targetSaving − overspend
⑥ achievementRate  = securedSaving ÷ targetSaving
```

**표시 규칙**
- `securedSaving`이 음수여도 계산에는 그대로 사용하고, **화면에는 0으로 표시**한다.
  - 문구: `지킨 돈 0원 — 지난달보다 32,000원 더 썼어요`
- `achievementRate`도 같은 방식으로 하한 0%.
### 진행 중 표시 (실시간)

`securedSaving`은 결제 즉시 갱신되지만, **한도를 넘기 전까지는 값이 변하지 않는다.**
강도 100%(한도 0)에서만 결제마다 움직이므로, 낮은 강도에서 게이지가 멈춰 보이는 것을 전제로 설계한다.

화면은 두 층으로 나눈다.

| 층 | 표시 | 성격 |
|---|---|---|
| 상단 | `targetSaving` + 초과 여부 | 계약 — 잘 안 변함 |
| 하단 (카테고리별) | `remainingCap` 게이지 | 소모 — 매 결제 반응 |

- 카테고리 게이지는 **남은 쪽을 채운다.** 줄어들면 위험 신호가 되어 방어율과 방향이 일치한다.
- 카테고리 정렬은 **초과한 것 우선**. 사용자가 봐야 할 것은 잘 되는 쪽이 아니라 터진 쪽이다.

### 월 중도 진입 (일할 계산)

```
일할 기준 소비 = baselineAmount ÷ 해당 월 총일수 × 남은 일수
targetSaving  = 일할 기준 소비 × cutRate
```

- 지킨 날 판정식의 `챌린지 총일수`도 남은 일수를 쓴다.
- 결산 화면에 기간을 명시한다. 예: `16일 챌린지`
- 분모가 같이 줄어들므로 한 달 전체를 채운 챌린지와도 방어율 비교가 가능하다.

## 6. 기준 소비 갱신 규칙 (2회차 이후)

직전 1개월을 그대로 물려받으면 성공할수록 기준이 내려가 결국 실패하는 구조가 된다.
따라서 **자동 하향하지 않고 사용자가 고른다.**

| 옵션 | 기준 소비 값 | 기본값 |
|---|---|---|
| 지난달처럼 유지하기 | 직전 챌린지의 `challengeCap` | ● |
| 원래대로 되돌리기 | `originalBaseline` | |

더 줄이는 것은 프리셋으로 제공하지 않고, 4/4 화면의 `−` 버튼으로 사용자가 직접 조정한다.

'유지'도 성공으로 인정한다. 결산 문구에서 하향만 칭찬하지 않는다.

## 7. 진입 조건과 예외

**데이터 요건** — 3개월 이상 데이터 보유자만 챌린지를 시작한다. 1개월 미만 사용자는 상정하지 않는다.

**중도 진입한 첫 달** — 일할 계산으로 목표를 잡되, 이력에는 **정식 챌린지로 남긴다.** 워밍업으로 별도 표기하지 않는다.

**후보가 비는 경우** — 성역 지정 후 남은 후보가 없으면:

1. 후보 순위를 더 내려가 목록을 다시 채운다
2. 그래도 비면 `이번 달은 지켜보기만 할게요` 출구를 제공한다
3. 2/4 화면으로 되돌려 성역 해제를 요구하지 않는다 (온보딩 이탈 방지)

## 8. 화면별 노출

| 화면 | 다루는 대상 | 주 지표 |
|---|---|---|
| 1/4 (= 월간 리포트) | 새는 돈 전체 후보 | `expected_saving`, 3개월 월평균 |
| 2/4 | 성역 지정 | — |
| 3/4 | 절약 카테고리 선택 | `expected_saving` 순위 |
| 4/4 | 지킬 돈 확정 | `baselineAmount`, `cutRate`, `targetSaving` |
| 홈 | 카테고리 현황 (일) | `remainingCap`, `securedSaving`, `achievementRate` |
| 주간 리포트 | 카테고리 현황 (주) | `securedSaving`, `defendedDays` + 전체 소비 진입 링크 |
| 챌린지 결산 | 카테고리 성과 (월) | `achievementRate`, `defendedDays`, `maxStreak` |
| 소비 내역 | 전체 거래 원장 | `totalSpend` (조회만), 절약 카테고리 소속 거래에 `spendTag` |

**금액 라벨 규칙**
- 1/4 화면 금액 → `3개월 월평균`
- 4/4 화면 금액 → `지난달`
- 두 화면의 같은 카테고리 금액은 다를 수 있다. 라벨 없이 노출하지 않는다.

**해석 금지 규칙**
- 전체 소비에 순위·비중·기간 비교를 붙이지 않는다. 그건 1/4 화면(월간 리포트)의 역할이다.
- 주간 리포트의 전체 소비는 금액 한 줄 + 소비 내역 진입 링크까지만.

## 9. 상품

**기준은 「금융소비자 보호에 관한 법률」이다.** (2026-08-11 확정)

`금융상품`은 예금·대출·투자·보험을 아우르는 **법정 상위어이고, 신용카드도 그 안에 있다**
(금소법 §2①, 시행령 §3에서 신용카드는 **대출성 상품**). 그러므로 `금융상품`은 카드의 반대말이 아니다.

### 9.1 법정 유형과 우리 범위

| 금소법 유형 (§3) | 우리가 다루는 상품 | 호칭 | 비교공시 대상 | 데이터 경로 |
|---|---|---|---|---|
| **예금성** | 정기예금·적금 | `예적금` | ○ | 금감원 오픈API 실시간 조회 — **DB에 안 쌓는다** |
| **대출성** | 신용카드 | `카드` | ✕ | 카드사 상품공시 원문 → **우리 DB** (V36, 표 9개) |
| 투자성 | **제외** | — | ○ | 펀드 — 다루지 않는다 (2026-08-12 결정) |
| 보장성 | **제외** | — | ○ | 보험 — 다루지 않는다 (2026-08-12 결정) |

**상품군은 카드·예적금 둘뿐이다.** 투자성·보장성은 보류가 아니라 스코프 밖이고, 실 데이터를 끌어올
API 경로도 없다(finlife 오픈API는 예금·적금·대출만 제공). 마스터 §제외 항목 🔁 개정 2026-08-12.

화면 문구는 예적금이 `아낀 돈 보관처`, 카드가 `카드`다.

> **예적금 화면이 둘이라 "실제냐 더미냐"가 갈린다.** 같은 예적금인데 경로가 다르다.
>
> | 화면 | 서비스 | 데이터 |
> |---|---|---|
> | 정보성 비교 (`Compare`) | `SavingsCompareService` | **실제** — 금감원 오픈API 실시간 |
> | 맞춤 상품 비교 (`MyProducts`) | `RecommendService` → `FinancialProduct` 표 | **더미** — 시드 7개 |
>
> 후자에는 펀드 더미도 한 건 섞여 있는데, **펀드는 스코프에서 빠졌으므로 제거 대상**이다.

### 9.2 부를 때 규칙 — 유형명이 아니라 구체명으로

- 개별 상품은 **`예적금`·`카드`**로 부른다. `예금성 상품`·`대출성 상품`은 **규제를 이야기할 때만** 쓴다.
  유형마다 상품이 하나씩뿐이라 유형명이 곧 상품명이 되어, 어려운 말로 같은 것을 가리키게 될 뿐이다.
- **`금융상품`을 단독 호칭으로 쓰지 않는다.** 둘 다 가리킬 때만 상위어로 쓴다.
  "금융상품 DB 구축됐나?"가 카드와 예적금 중 무엇을 묻는지 갈렸던 것이 이 규칙의 이유다.
- 법정 유형은 이름이 아니라 **상품 레코드의 칸**으로 둔다(`product_type`).

### 9.3 둘을 실제로 가르는 축은 유형이 아니라 조달 경로다

비교공시(`금융상품한눈에`) 범위는 예금·적금·대출·집합투자증권·보험·연금저축·퇴직연금이고
**신용카드는 빠져 있다** (금소법 시행령 §29① — 대출성 중에서도 '대출'만 대상).

```
예적금   비교공시 대상  → 금감원이 모아서 API로 준다   → 우리가 쌓을 이유가 없다
카드     비교공시 밖    → 아무도 안 모아준다          → 카드사 공시를 우리가 수집해 쌓는다
```

"DB 구축"이라는 작업이 카드에만 있는 이유가 이것이다. 우연이 아니라 제도가 갈라놓은 것이고,
예적금 쪽에는 앞으로도 DB 구축 단계가 생기지 않는다.

### 9.4 규제 근거 (마스터 §4 원칙 5)

```
예적금   추천·판매 흐름은 더미. 정보성 비교 화면에서만 실 금리 (예외 ①)
카드     실제 상품을 쓴다 (예외 ②) — CTA·제휴·수수료·광고비 순위 넷 다 금지
공통     수집 기준일(as_of) 병기
```

> **체크카드** — 시행령 §3의 대출성 열거(신용카드·시설대여·연불판매·할부금융·소액후불결제)에 체크카드는
> 없다. 소액후불결제가 붙은 것만 대출성이다. `card_product`의 신용/체크 칸이 이미 이 구분을 담고 있다.

> **알려진 불일치 (정합 대상)** — 코드의 `Enums.ProductType`은 `DEPOSIT·SAVINGS·FUND·CASHBACK_CARD`
> 넷을 한 `FinancialProduct`에 담는데, 이 축은 법정 유형도 조달 경로도 아니다. 카드는 V36 표로
> 옮겨가는 중이므로 `CASHBACK_CARD`는 제거 대상이다. 기존 문서의 `금융상품` 150여 곳도 순차 정정 필요.

## 10. 폐기 용어

| 폐기 | 대체 | 사유 |
|---|---|---|
| 금융상품 (단독 호칭) | 예적금 / 카드 | 카드도 법정 금융상품이라, 단독으로 쓰면 무엇을 가리키는지 갈림 (§9.2) |
| 달성률 | 방어율 | 같은 값의 다른 이름 |
| 남은 예산 | 남은 돈 (`remainingCap`) | '예산'은 한도와 목표를 모두 연상시킴 |
| 목표 저금액 | 이번 달 목표 (`targetSaving`) | 표현 통일 |
| 많이 쓴 곳 | 카테고리별 사용 | 전체 소비 해석 어휘 |
| 지킨 금액 / 지켜낸 금액 | 지킨 돈 | 표현 통일 |
| 저금통 | 절약 카테고리 | 같은 것의 다른 이름 |
| ○○% 사용 | 남은 돈 + 방어율 | 방향이 반대인 중복 지표 |
