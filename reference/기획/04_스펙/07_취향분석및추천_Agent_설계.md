## 1. 제품 철학

가계부 앱은 보통 사용자를 교정하려고 한다. 우리는 교정하지 않는다.

**서비스의 역할은 판단자가 아니라 거울이다.** 사용자가 데이터를 보고 스스로 의미를 발견하도록 설계한다.

---

## 2. 핵심 원칙

> **AI는 소비를 설명하고, 소비의 의미는 사용자가 결정한다.**

```text
O  "이번 달 택시비 8만 원 중 5만 원이 평일 오전에 발생했어요."
O  "올해 가장 많이 택시를 탄 시간대는 오전 8~9시였어요."

X  "출근 때문에 택시를 많이 타시네요."
X  "지각 방지 택시가 반복되고 있어요."
X  "이 소비는 필수 소비예요."
```

### 2.1 왜 해석하지 않는가

AI의 정확도 문제가 아니다. **사용자가 "평가받고 있다"고 느낄 위험** 때문이다.

같은 데이터가 전혀 다른 사정을 담는다.

```text
데이터    오전 8~9시 택시 12회
해석 시도  "지각 방지 택시가 반복되고 있습니다"
실제 이유  출근 · 등원 · 병원 · 미팅 · 그날만의 사정 …
```

하나를 골라 말하는 순간 나머지 사정을 가진 사용자는 오해받는다. 그래서 **현 단계에서는 의미를 단정하지 않고 사실만 전달한다.**

## 3. 리포트 3종

### 3.1 주간 = 관찰

**이번 주 어떤 소비가 있었는지.**

| | |
|---|---|
| 포함 | 카테고리별 소비 · 시간대 패턴 · 요일 패턴 · 소비 흐름 |
| 포함 | **지키는 금액 — 사실로서만** |
| 금지 | 목표 달성 여부 · 잘했다/못했다 · 페이스 평가 · 행동 교정 |

```text
O  "배달 3건이 화·목·금 밤에 있었어요."
O  "이번 주 카페에서 4번, 21,000원 썼어요. 지금 100,000원 지키는 중이에요."

X  "이번 주 목표의 80%를 달성했어요."
X  "이 페이스면 이번 챌린지는 어려워요."
X  "주말엔 배달을 줄여보세요."
```

> **금액과 평가의 경계.** `100,000원 지키는 중`은 **상태 사실**이라 넣는다. `방어율 80%`·`이 페이스면`은 **평가**라 뺀다. 금액을 숨기면 사용자가 홈에서 본 숫자와 리포트가 어긋나 오히려 혼란스럽다.
> ②의 `achievementRate`·`paceRatio`는 주간 리포트에 쓰지 않는다.

### 3.2 월간 = 회고

**이번 챌린지에 어떤 흐름이 있었는지.** 주기는 **챌린지 종료일 = 달력 월말**이다(`01_prd.md` v10 §5).

| | |
|---|---|
| 포함 | 지킨 금액 · 소비 카테고리 비중 · 직전 챌린지 대비 변화 · 반복적으로 나타난 패턴 |
| 포함 | **취향 축의 집계 사실** — `이번 챌린지 카페 12번 · 영화 2편` |
| 금지 | 실패 · 합격/불합격 · 절약을 못했다는 평가 |
| 금지 | **취향 해석** — `당신은 미술 애호가` 같은 정체성 서술은 연간에서만 |

```text
O  "이번 챌린지 택시비의 62%가 평일 오전에 발생했어요."
O  "지난 챌린지보다 카페 소비가 3건 줄었어요."

X  "목표 달성에 실패했어요."
X  "절약이 부족했어요."
```

②의 `state`가 `SHORTFALL`·`FAILED`여도 그 이름을 노출하지 않는다. 사실(지킨 금액·흐름)만 말한다.

### 3.3 연간 = 정체성

**올해 나는 어떤 사람이었는지.** Spotify Wrapped와 유사한 경험.

| | |
|---|---|
| 포함 | 연간 소비 사실의 집계 — 횟수·장소 수·시간대 |
| 포함 | **제한적 취향 서술 (§5)** — 세 리포트 중 여기서만 허용 |
| 주기 | **달력 연도.** 챌린지 경계와 맞추지 않는다 |

```text
영화 32편 관람 · 전시 9회 방문 · 새로운 식당 47곳 방문
→ "올해의 영화 러버"
→ "새로운 경험을 즐긴 한 해"
```

연간은 챌린지 실적이 아니라 **소비 사실**을 재료로 하므로 챌린지 주기에 맞출 이유가 없다. 챌린지를 하지 않은 기간의 소비도 포함한다.

> **카드 구성은 `04_IA.md` §4.3이 정본이다** (2026-08-03 팀 확정). 주간 3카드 / 월간 6카드이며, 월간 4번(금융상품)은 **지킨 돈 > 0일 때만** 노출한다.

### 3.4 주기 정리

| 리포트 | 주기 | 성격 | ②의 금액 |
|---|---|---|---|
| 주간 | **달력 주 (월~일)** | 관찰 | `securedSaving`만 |
| 월간 | **달력 월말** (= 챌린지 종료일) | 회고 | 확정 지킨 돈 |
| 연간 | 달력 연도 | 정체성 | 쓰지 않음 |

## 4. 라이프스타일 분석 — 한 이름, 두 축

③의 분석 축은 **라이프스타일 분석** 하나다. 그 안에 성격이 다른 두 축을 둔다.

```text
마이데이터 · ①의 (B)
  ├─ 금액 · 시점 · 규칙성   →  자금 흐름 축 (L1~L5)  →  저축 상품 매칭 (FP-01)
  └─ 카테고리 · 가맹점 빈도  →  취향 축  ┬──────────▶  월간 리포트 (집계 사실)
                                        ├──────────▶  연간 리포트 (정체성)
                                        └──────────▶  카드 추천 (FP-03)

  자금 흐름 축(얼마나) + 취향 축(무엇을) ──────────▶  목표 추천 (FP-04)  ★2026-08-04 신설
                                                       ②의 확정 지킨 돈이 선행 조건 (§4.6)

                              취향 축 ──✕──▶ 저축 상품 매칭
```

**두 축이 만나는 자리는 목표 추천 하나뿐이다.** 저축 매칭에 취향이 들어가지 않는다는 §4.3의 격리는 그대로 유지된다 — 목표 추천은 저축과 **다른 산출물**이다.

### 4.1 자금 흐름 축 (L1~L5)

| 축 | 계산값 | 출처 |
|---|---|---|
| L1 소득 | `salary_regular` · `salary_day` | (B) `income_profile` ← ① |
| L2 고정비 | `fixed_total` · 인출일 분포 | (B) `fixed_expense_summary` ← ① |
| L3 안정성 | `aom`(Age of Money = 자금 버퍼) · 규모는 `kept_mean` | (B) `cash_buffer` ← ① · kept_mean은 (C) ← ② |
| L4 유동성 | `large_expense_cycle` · `predictable` | (B) `recurring_payments` + 큰 1회성 지출 ← ① |
| L5 우대조건 | **카드 실적 · 급여이체** 충족 여부 | (B) `preferential_material` × (D) ← ①·외부 |

**대부분 ①에게서 온다.** ③이 직접 계산하지 않고 (B)로 받는 이유는 R7이다 — 급여·고정비·잔고는 계좌를 봐야 알 수 있는데 ③은 계좌 원본을 만질 수 없다. L3(AoM)도 ①이 (B) `cash_buffer`로 넘긴다. 규모용 `kept_mean`만 ②의 확정 이력에서 온다.

매칭 규칙 M1~M10은 §4.5가 정본이다. 규칙 엔진이 판정·정렬을 하고 LLM은 문장만 만든다(R2).

**L5는 세 축을 본다 — 카드 실적 · 급여이체 · 당행 보유**(2026-08-11 개정). 앞의 둘은 충족·미충족을 확정하고, 셋째는 **미충족만** 확정한다(§4.5 M6).

> 🔁 **개정 (2026-08-11).** 예전 문장은 *"L5는 카드 실적·급여이체 둘만 본다 … 실제 적금 우대조건에서 가장 흔하고 가산폭도 큰 두 가지가 남았으므로 D2는 그대로 성립한다"* 였다. **실측이 이를 반증한다** — 금감원 적금 58건에서 급여이체는 7건(12%), 카드 실적도 7건(12%)이고, 최빈은 우리가 못 보는 **자동이체 24건(41%)** 이다. 둘 중 하나라도 언급하는 상품은 10건뿐이라 **나머지 48건(83%)에는 우리 판정이 닿지 않는다.** 자동이체를 뺀 이유(더미에 계좌 자동이체 거래가 없다 · R7)는 그대로지만, "그래서 남은 둘이면 충분하다"는 결론이 틀렸다. 대응은 축을 억지로 늘리는 것이 아니라 **모르는 것을 모른다고 말하는 것**이다 — M6을 3분기로 바꿨다(§4.5).

> ### ✅ L3 재정의 — kept 변동성 → AoM(Age of Money) (2026-07-28 해결)
>
> 옛 L3(`kept_cv` 지킨 돈 변동성)는 저축 여력이 아니라 **사용자의 목표 변경 빈도**를 재는 결함이 있었다 — 지킬 돈은 매 챌린지마다 사용자가 카테고리·강도를 새로 골라 달라지므로, 소비 습관이 그대로여도 `kept_cv`가 크게 나온다. 결과적으로 M2(정액 적금)가 죽은 규칙이 되던 문제.
>
> **해결**: 안정성은 목표 선택과 무관한 **AoM(자금 버퍼)** 으로 잰다 — 간이식 `평균잔고 ÷ 월평균지출`. 실제 입출금 현금흐름으로 계산돼 챌린지 선택에 오염되지 않고, 마이데이터로 **가입 첫날부터** 계산되어 콜드스타트도 완화된다. `kept_mean`은 *납입 규모* 산정에만 쓴다.
>
> 더불어 MOA의 지킨 돈은 매달 금액이 다르고 덩어리로 들어와 **정액적금과 구조적으로 안 맞으므로**(고정 납입 강제 = R9 페이스 유도 위험), 중심축을 "정액 vs 자유"가 아니라 **파킹통장 ↔ 자유적립식**으로 바꾼다(AoM·L4 주도). 상세 규칙은 §4.5(M1~M9).
>
> **남은 미정**: θ_buffer(버퍼 구간)·간이 vs 정통 AoM·카드-현금 시점 차이 보정 → §8.

### 4.2 취향 축

카테고리·가맹점 빈도에서 나오는 것.

```text
영화관 결제 32회 · 전시 9회 · 처음 가본 식당 47곳
```

**재료와 해석을 나눈다.** 같은 축이지만 어디까지 말하느냐가 다르다.

| 쓰이는 곳 | 어디까지 |
|---|---|
| 월간 리포트 | **집계 사실까지** — `이번 챌린지 카페 12번` |
| 연간 리포트 | **정체성 서술까지** — `당신은 미술 애호가` (§5) |
| **카드 추천 (§4.4)** | 소비처별 혜택 매칭의 입력 |
| ~~저축 상품 매칭~~ | **금지** (§4.3) |

### 4.3 왜 경로를 나누는가

취향이 **저축** 상품 매칭 입력으로 들어가는 순간 이런 문장이 만들어진다.

```text
X  "영화를 좋아하시니, 영화값 모으는 적금 어떠세요?"
```

**소비 목표를 만들어 유도**하는 것이라 R9 위반이다. 규칙으로 "쓰지 말자"고 막는 대신 **입력에서 빼서 구조적으로 불가능하게** 만든다. 규칙은 잊히지만 없는 데이터는 쓸 수 없다.

두 축은 포함 관계가 아니라 **직교**다. 취향이 같아도 자금 흐름이 다르면 추천이 갈린다.

```text
둘 다 영화 32편을 본 사람 —
  A  급여 25일 규칙적(L1) · 큰 지출 없음(L4)   → 만기 긴 상품도 가능
  B  수입 불규칙(L1) · 분기마다 큰 지출(L4)    → 만기 짧은 상품·파킹통장
```

### 4.4 카드 추천 (FP-03)

취향 축이 상품 매칭에 쓰이는 **유일한 자리**다. 저축(FP-01)과 근거가 반대다.

| | FP-01 저축 | FP-03 카드 |
|---|---|---|
| 매칭 근거 | 자금 흐름 축 + 우대조건 | **취향 축 — 소비처별 혜택** |
| 상품 정보 | 금감원 오픈API (실데이터) | 카드사 자사 공시 수집 (**실데이터**, 2026-08-10 개정) |
| 사용자에게 주는 것 | 실수령 예상 금리 | **예상 절약액** |

#### 혜택 축 — 중분류가 아니라 별도 축이다 (2026-08-10)

소비분석의 **15 중분류로는 카드 혜택이 계산되지 않는다.** 그 축은 낭비 판정을 위해
설계됐고, 카드 혜택이 걸리는 단위와 다르다.

```text
교통/자동차 58코드   주유(505001) · 시내버스(602103) · 택시(602201) · 자동차 구매 · 타이어
                     → 카드는 전부 다르게 취급한다. 리터당 할인 / 10% / 별도 또는 없음
주거/통신  53코드    통신비(실적 인정) + 공과금(대개 실적 제외)
```

BC 공시가 실물로 증명한다 — `BC 바로 ZONE` 의 실적 제외 목록에 *"대중교통(시내버스·지하철),
고속버스, 고속도로 통행료, 후불하이패스"* 가 있는데, 같은 중분류의 주유소는 실적에 들어간다.

그래서 `scripts/industry/nts-mid.tsv` 에 **4번째 칸(카드혜택 축)** 을 붙였다.
534행 전부 채웠고, 원천은 하나다 — **소비분석은 2번째 칸, 카드추천은 4번째 칸**을 읽는다.
축의 정본은 카드 검색 서비스가 실제로 쓰는 분류를 따랐다(우리가 새로 지으면 카드사 공시의
묶음과 어긋나 매칭이 안 된다). 빌드가 빈칸·오타를 `sys.exit(1)` 로 막는다.

**판정은 브랜드가 1순위, 이 표가 2순위다.** 업종코드로 못 푸는 축이 있기 때문이다.

| | 왜 업종코드로 안 되나 | 어떻게 푸나 |
|---|---|---|
| 배달 | 배달의민족이 **통신판매업**으로 등록돼 '쇼핑'이 된다 | 브랜드 (자체 사전에 확정으로 박는다) |
| 디지털구독 | 넷플릭스와 PG(NHN KCP)가 **같은 코드 724000** | 브랜드 |
| 온라인쇼핑 | 채널은 업종이 아니다 | 브랜드 |
| 간편결제 | **결제수단**이라 승인내역에 칸이 없다 | **판정 불가 — 표시만 하고 계산에서 뺀다** |

브랜드 목록은 새로 만들 필요가 없다 — **카드 공시가 혜택 대상 브랜드를 직접 나열한다**
(스타벅스·배달의민족·넷플릭스·CU·CGV…). 카드를 파싱하면 브랜드 표가 저절로 쌓인다.

> **`보험` 축은 두지 않는다**(사용자 결정 2026-08-10). 카드에는 보험 혜택이 실재하지만
> (예: 모니모A 카드 "보험 추가 9%") **우리 카드이용내역에 보험 결제가 없어** 계산에 영향을
> 주지 않는다. 축을 늘리는 값이 없다. 나중에 보험 결제가 들어오면 그때 다시 본다.
>
> `혜택축없음`(173행)은 **"소비가 아니다"가 아니다.** 그 업종에 걸리는 카드 혜택 축이 없다는
> 뜻이고 **전월 실적에는 그대로 들어간다** — 동네 정육점은 혜택은 못 받아도 실적에는 든다.
> 이 구분을 헷갈리면 실적에서 173행이 통째로 빠진다.

#### 왜 카드는 취향을 써도 되는가

저축에 취향을 쓰면 **없던 소비 목표를 만든다.** 카드는 반대로 **이미 하는 소비를 덜 나가게** 한다.

```text
X  "영화 좋아하시니 영화 적금 어떠세요?"        ← 목표를 새로 만든다 (R9 위반)
O  "이미 배달에 월 25만 쓰시는데, 이 카드면 연 9.6만 덜 나가요"
```

절약 서비스와 방향이 같다. 다만 선이 미묘해서 **표현을 강제한다.**

- 반드시 **사용자의 실제 소비 상위 카테고리**를 근거로 말한다(`회원님 지출 상위 2개 카테고리에 겹쳐요`).
- `이 카드로 배달 더 시키면 이득` 류의 **소비 증가를 전제한 문장은 금지**한다.
- 절약액은 **현재 소비를 그대로 유지했을 때**의 값이다. 늘렸을 때를 가정하지 않는다.

#### 무엇을 대상으로 삼는가 — 낭비 판정이 아니라 **지속성**이다 (2026-08-10)

한때 "낭비로 판정되지 않은 소비만 카드 추천 대상"으로 잡으려 했는데 **틀렸다.**
`카페/간식`은 낭비 판정에서 상위(cat2 형상값 +0.9907, 15종 중 4위)라, 그 규칙이면
**커피가 통째로 빠진다** — 카드 추천이 제일 잘 맞는 자리인데도.

기준은 *낭비냐*가 아니라 **계속 나갈 돈이냐**다. 신호는 이미 DB에 있다.

| 신호 | 어디에 | 단위 | 뜻 |
|---|---|---|---|
| `UserMerchantStance.stance` | `business_number` | 가게 | `EXCLUDED` = 이 가게는 성역 |
| `UserMerchantStance.keptCount` | 같은 행 | 가게 | "낭비 아님"을 몇 번 눌렀나 = 확신의 크기 |
| `UserSpendingOverride.forcedWaste=false` | `category2` | 중분류 | "카페는 나에겐 필수" |

**성역은 카드 혜택 매칭의 최상급 신호다.** "스타벅스는 못 끊어"는 과거 6개월 추정이
아니라 **본인이 한 미래 선언**이고, 가게 단위(`business_number`)라 브랜드 축과 바로 잇는다.
성역을 안 누른 사용자는 **반복 빈도**로 대체한다 — 커피는 정기결제(28~31일 주기)가
아니라 잦은 소비라, 기존 정기결제 탐지로는 안 잡힌다.

```text
낭비 판정 (waste)   → 줄일 돈  → 카드 추천에서 뺀다
성역 (EXCLUDED)     → 지킬 돈  → 가중치를 올린다
```

#### 절약액 계산

```text
1  전달 승인내역 → 실적 제외 항목 빼기(업종코드 6자리)   → 전월실적 [하한, 상한]
2  실적으로 카드의 구간(tier) 결정                     → 어떤 한도가 열리나
3  전달 소비를 혜택 묶음별로 분배 (브랜드 1순위 · 24축 2순위)
4  묶음마다  min(그 묶음 소비 × 요율, 구간별 월한도)
5  통합한도로 한 번 더 자름                            ← 페이북 실측: 개별 합 15,000 > 통합 13,000
6  Σ × 12 − 연회비                                  → 연 순혜택 [하한, 상한]
```

**이전율 α 같은 임의 상수가 없다.** 예전 설계는 "아직 발급 안 한 카드에 전월실적이
있을 리 없다"는 순환 때문에 α(=0.7 같은 값)를 두려 했는데, **전달에 실제로 쓴 돈이
곧 전월실적**이라 추정할 것이 없다(사용자 결정 2026-08-10). 여러 카드에 나뉘어 있는
문제는 α로 추정하지 않고 **가정을 밝혀서** 푼다 — "이 소비를 이 카드로 모으면".

주의할 것 셋.

- **1번을 빼먹으면 실적이 과대 계산된다.** 총소비 45만이어도 아파트관리비·공과금·
  대중교통이 13만이면 실적은 32만이다. 이건 24축이 아니라 **카드별 실적 제외 목록**으로
  뺀다(카드마다 다르다).
- **실적 충족은 한도를 여는 것이지 한도를 받는 게 아니다.** 실적 30만을 채워 EAT 한도
  5,000원이 열려도, 커피에 2만원 썼으면 받는 건 1,400원이다.
  `혜택 = min(내 소비 × 요율, 한도)`.
- **미분류는 계산에서 뺀다.** 실적도 혜택도 과소 계산되지만 **둘 다 하한 방향**이라
  "채운 줄 알았는데 못 채웠다"가 구조적으로 안 난다. 다만 실측상 카테고리없음이
  금액의 40~46%였으므로, 미분류 비율이 높은 사용자는 숫자를 아예 안 보여주는 편이 낫다.

#### 화면에 무엇을 쓰는가

사용자는 계산 과정을 궁금해하지 않는다. **결과만 준다**(사용자 결정 2026-08-10).

| 안 쓴다 | 쓴다 |
|---|---|
| "총소비 45만 중 관리비·교통비 13만 제외" | **"지난달 실적 32만원 · 충족"** |
| "실적 채우면 월 5,000원" | "커피 혜택이 **열림** → 고객님 지출 기준 월 1,400원" |
| "5,000원 받으려면 커피에 7만원" | (쓰지 않는다 — 소비를 부추긴다) |

#### 규제 — 저축보다 더 조심해야 한다

> 2021년 금융위·금감원은 플랫폼의 금융상품 비교·추천을 단순 광고가 아닌 **중개 행위**로 판단했고,
> **신용카드 추천도** `잠재고객 발굴·가입 유도 과정`으로 보아 문제 삼았다.

저축은 정보성 비교 예외(금융위·금감원 유권해석 2022.6.15)를 근거로 실 금리를 쓴다.

> 🔁 **개정 (2026-08-10) — 카드도 실제 상품을 쓴다.** 예전 문장은 *"카드는 그 예외를
> 검증받은 적이 없으므로 더 보수적으로 간다"* 였고 상품은 전부 더미였다. 그런데 카드 추천은
> 이 프로젝트의 **필수 기능**이고 더미 카드로는 성립하지 않는다(사용자 결정).
> 마스터 원칙 5를 재개정했다 — 근거와 남는 위험은 `reference/finntech_things.md`
> §제외 항목의 🔁 개정(2026-08-10).
>
> **근거는 약관 정본 제7조다.** 운영사는 대리·중개 **권한이 있으나** 그 권한을 행사하지 않고
> 정보 제공 업무만 한다고 약관이 약속했다 — 저축 화면과 같은 근거다.

**약관이 한 약속을 지키기 위해 넘지 않는 선 넷.** 기능을 늘릴 때 이 목록을 먼저 본다.

1. 카드사와 제휴·광고 계약을 맺는 것
2. 수수료를 받는 것
3. **카드사로 넘어가는 CTA 버튼·신청 링크를 두는 것** — 여기는 혜택 비교까지다
4. 순위를 광고비에 연동하는 것 — 정렬은 매칭 점수 순이고, 화면에 그렇게 밝힌다

③번이 특히 두 겹으로 일한다. 아래 '카탈로그가 낡는다'의 방어가 ③에 얹혀 있다.

**가장 약한 고리는 개인화 절약액이다.** 저축은 금리라는 만인 공통 수치를 보여 주지만
여기는 "당신은 연 얼마"를 낸다 — '단순 정보제공'보다 권유로 읽힐 여지가 있다. 그래서
단일값이 아니라 **밴드**로 말하고, 근거(내 소비 요약)를 같은 화면에 두고, 기준일을 적는다.

#### 카탈로그 규모로 경쟁하지 않는다

카드 비교 서비스(예: 카드고릴라)는 카드사와 제휴해 1,500여 종을 유지한다. 수집으로는 그 규모를 따라갈 수 없고, 따라갈 이유도 없다.

```text
그들   1층(공시) + 2층(카드 혜택)          → "이 카드는 카페 5%"
우리   2층 + 3층(마이데이터 소비 흐름)     → "당신은 카페에 월 8만 → 연 4.8만"
```

**3층이 있어야 나오는 문장이 우리 자리다.** 카탈로그가 20~30장이어도 성립한다.

그리고 3층이 있으면 2층만 가진 곳이 **못 하는 말**을 할 수 있다.

```text
카드 비교 서비스   "전월실적 30만원 이상"          ← 카드의 조건을 그대로 옮김
우리              "지난달 실적 32만원 · 충족"      ← 내 실제 소비로 판정
```

같은 이유로 **"월 최대 혜택"으로 정렬하지 않는다.** 그건 카드를 100% 활용했을 때의 값이라
카드 목록 서비스에는 맞지만 우리와는 안 맞는다(사용자 결정 2026-08-10). 다만 **내부
검증용으로는 쓴다** — 같은 카드를 비교 서비스가 얼마로 표시하는지 대조하면 우리 파싱이
맞았는지 채점된다.

#### 데이터 출처

`scripts/collect-cards/` 참조. 요지만 적으면 —

- 여신금융협회 **카드다모아는 데이터 API가 403**이라 쓰지 않는다. 운영자가 프로그램 접근을
  막아 둔 것이라 **우회하지 않는다** — 이 선은 지킨다.
- 출처는 각 카드사 자사 사이트의 **상품공시정보**다. **집계처를 거치지 않은 1차 원천**이라
  신고 부실이 끼어들 여지가 없다 — 금감원 통합비교공시 같은 곳은 금융사가 신고한 값을 모은
  2차라 오히려 부실이 그대로 올라온다(저축 쪽에서 겪었다: 아동·청년 전용 상품이
  `join_deny=1`(제한없음)로 올라오는 경우). **남는 과제는 출처 신뢰도가 아니라 추출 정확성**이다.
- **9개 카드사(신한·삼성·현대·롯데·하나·국민·BC·우리·농협)의 공시 경로를 확보했다**
  (2026-08-10, `개인카드-로컬전용/카드사별-수집경로.md`). 수집 중 **차단·캡차를 만난 곳은
  한 곳도 없었다.** 카드사별 진입 방법·갱신일 필드·페이지네이션 제약이 그 문서에 있다.
- 혜택 문구를 우리 축으로 나누는 일은 자동화하지 않는다(§4.2 — 판단이 필요하다).

> **개정 (2026-08-10).** 예전 문장은 *"`robots.txt`가 명시 허용한 곳만 수집한다(신한·KB·우리).
> 삼성은 `Disallow: /`라 제외한다"* 였다. 그 뒤 9개사 전부의 공시 경로를 확보하면서 삼성도
> 포함됐으므로(사용자 결정: 실행한 것을 기준으로 간다) 그 문장을 지웠다.
> **다만 우회는 안 한다는 선은 그대로다** — 카드다모아처럼 운영자가 명시적으로 막아 둔 곳은
> 쓰지 않는다.

#### 카탈로그는 낡는다 — 갱신을 안 하기로 했다 (2026-08-10)

카드 부가서비스는 **3년 이상 유지 의무**가 있고 변경 시 **6개월 전 고지** 의무가 있어
(신용카드 표준약관) 빨리 낡지는 않는다. 그래도 개정은 일어난다.

**혜택 개정 추적은 스코프 밖이다**(사용자 결정). 진짜 핀테크라면 필수 기능이지만
(공시 URL 해시 감시 → 재파싱 → 검수 큐) 이 프로젝트는 거기까지 가지 않는다.

그래서 카드 정보는 **수집 시점에 고정된 스냅샷**이고, 방어는 자동화가 아니라 **정직한 표기**다.

- 화면에 **수집 기준일을 반드시 병기**하고 "이 시점 공시 기준"임을 밝힌다.
- 기준일의 근거는 공시에 찍힌 **여신금융협회 심의필 날짜**다(BC 3장 실측: 전부 추출됨).
- **비교만 하고 가입으로 넘기지 않으므로** 낡은 값이 곧바로 계약 손해가 되지 않는다 —
  위 규제 절의 ③ CTA 금지가 이 방어의 전제다. CTA 를 다는 순간 "낡은 정보로 가입을
  유도한 것"이 되어 둘이 함께 무너진다.

```text
카드사 상품공시 PDF                         ← 저장소 밖. 용량 때문이다(142장 313MB)
  │  pdftotext -layout · 사람이 원문 대조
```

**표가 아홉인 이유**는 길이가 카드마다 다른 것이 셋이기 때문이다 — 실적 구간(2~4단),
구간별 월한도, 통합한도. 고정 배열로 두면 안 되고, **한도를 구간 행에 FK 로 매달면
"없는 구간의 한도"가 구조적으로 못 들어온다**(게이트 규칙 하나가 스키마가 된다).
설계 근거 전문은 마이그레이션 `V36__card_product.sql` 머리말에 있다.

**혜택 대상은 국세청 6자리가 아니라 카드혜택 축으로 받는다.** 6자리로 받으면 카드 한 장이
코드 수십 개를 이고 있게 된다. 잇는 길은 `ksic_code → cardAxisByIndustry → 축 → 카드`다.

| 게이트 | 무엇 | 비용 |
|---|---|---|
| 1 · 스캔 판별 | 쪽당 200자 미만 → PDF 포기, HTML 공시로 | 0 |
| 2 · LLM 추출 | **전문**을 넣는다(카드당 약 5K 토큰). ★ grep 발췌 금지 — 3단 편집이라 첫 매치 주변에 다른 칼럼이 섞인다(실제로 이것 때문에 KaPick 실적제외 12개를 1개로 읽었다) | 낮음 |

실패시키지는 않는다 — 카드가 수천 장이 될 때 한 장의 결함이 전체 적재를 막으면 안 된다.

##### 셀 수 없는 혜택은 표시만 한다

공시의 혜택 중 **금액으로 옮길 수 없는 것**이 섞여 있다. BC 3장 실측으로 19개 중 10개가
여기 해당했다. 빼면 절감액이 **하한 방향**으로 틀리므로 이 방향을 고른다.

| 왜 못 세나 | 예 |
|---|---|
| 금액 환산 자체가 안 됨 | 무이자할부 · 비금전(라운지·발렛·카드등급 서비스) |

있지만, 현금서비스·카드론·수수료·상품권·무이자할부는 승인내역에 그 칸이 아예 없다.
**못 빼면 실적이 과대 계산된다** — 하한이 아니라 나쁜 방향이라, "빼먹은 것"과 "못 빼는 것"을
`exclusionAxes` 에 빈 목록으로 구분해 남긴다.

### 4.5 저축 상품 매칭 (FP-01) — M1~M10

자금 흐름 축(§4.1)을 실제 상품 추천으로 바꾸는 규칙이다. **판정·정렬은 규칙 엔진이 하고 LLM은 문장만 만든다**(R2).

> 🔁 **개정 (2026-08-12) — 예적금은 개인화 대신 비교만 한다** (사용자 결정).
>
> 사용자 데이터는 **가입 가능 여부를 거르는 데까지만** 쓴다(나이 자격 · 가입 금액). **순위를 개인화하지
> 않는다** — "당신에게 맞는 순서"가 아니라 "고를 수 있는 상품의 비교표"다.
>
> **왜.** 판정 가능한 축이 카드 실적·급여이체 둘뿐이라 실측상 **상품의 17%에서만 발화한다**(96건 중
> 하나라도 걸리는 것 17%). 나머지 83%는 상품 데이터를 더 모아서 풀리는 게 아니다 — 막힌 쪽은 사용자
> 재료이고, **더미 마이데이터에는 입출금 통장이 사용자당 하나뿐**이라(`backend-mydata` 의 `V6__account.sql` — backend 의 V6 는 다른 표다) 주택청약·예적금
> 보유 같은 축은 계좌 목록을 받아 와도 꺼내 올 것이 없다. 자동이체를 뺀 것과 같은 사유다(§4.1).
> 발화하지 않는 개인화를 유지하느니 **비교를 정확하게** 하는 쪽이 낫다.
>
> **덤으로 규제 부담 하나가 사라진다.** §8.1의 `실수령 금리 표현의 자문·중개 경계`는 "당신은 연 3.2%"라는
> **개인화된 숫자**가 권유로 읽힐 여지 때문이었다. 만인 공통 수치(기본·최고금리)만 보이면 그 위험이 없다.
>
> **아래 M1~M10 중 개인화 부분의 처리는 미정이다** — 폐기·보류·문서 보존 중 무엇으로 갈지는 **예적금 추천
> 로직 개편이 끝난 뒤** 정한다(사용자 진행 중). 그때까지 이 절은 옛 설계 그대로 둔다.
>
> | | 상태 |
> |---|---|
> | M2·M3 (AoM으로 그룹 순서) · M6 (실수령 금리) · M9 ① (미충족 수) | 개인화 — **처리 미정** |
> | M5 하한 미달 제외 | **남는다** — 가입 가능 여부를 거르는 것이라 비교의 전제 |
> | 자격 라벨링(나이) | **남는다** — 같은 이유 |
> | 우대조건 라벨링 · 가입 금액 · 중도해지이율 | **전부 남는다.** 쓰임이 *판정*에서 **필터·표시**로 바뀔 뿐이다 |
>
> **상품 재료 작업은 하나도 버려지지 않는다.** 우대조건 라벨은 뱅크샐러드가 우대조건을 필터 칩으로 쓰는
> 것과 같은 자리에 들어가고, 금액·중도해지이율은 비교표의 칸이 된다.

> **2026-07-28 개정.** 기존 `kept_cv`(지킨 돈 변동성) 기반의 "정액 vs 자유" 분기는 폐기했다 — `kept_cv`는 실제 저축 여력이 아니라 **사용자의 챌린지 목표 변경 빈도**를 반영하는 경향이 있었다. 재정 안정성은 **AoM(Age of Money)** 으로 판단한다.
> 또 MOA의 지킨 돈은 매달 금액이 달라지고 덩어리로 들어와 정액적립식과 구조적으로 맞지 않으므로, 추천의 중심축은 **정액적립식 ↔ 자유적립식**이 아니라 **파킹통장 ↔ 자유적립식**이다.

**최빈 조건이 우리가 못 보는 축이다.** 급여이체·카드 실적은 12%씩으로 최빈이 아니었다 —
§4.1이 그 둘을 고른 근거("가장 흔하고 가산폭도 큰 두 가지")가 실측과 다르다.

**조건별 가산폭은 파싱하지 않는다 — 이제 근거가 있다.** `%p`가 숫자로 적힌 25건에서 가산폭을 전부
더해 `(최고금리 − 기본금리)`와 맞춰 보면 **일치가 4건(16%)** 이다. 나머지는 합이 격차의 꼭 2배쯤으로
뜬다(2.4 vs 1.2 · 3.8 vs 1.9 · 1.0 vs 0.5) — 조건이 **배타적이거나 기간별로 다르게** 붙는다는 뜻이다.
§8.1의 (D) 부분 가산 보류는 옳았다. 다만 이 검산식을 버리지는 않는다 — **파싱 신뢰도 게이트**로 쓴다(M6).

#### AoM(Age of Money)

사용자의 자금 버퍼가 얼마나 두꺼운지를 재는 지표다. "지금 소득이 끊겨도 며칠 버티나"에 해당한다.

```text
AoM = 평균잔고 ÷ 월평균지출
```

| AoM | 의미 |
|---|---|
| 0.5 | 약 2주치 생활비 보유 |
| 1.0 | 약 1개월치 생활비 보유 |
| 3.0 | 약 3개월치 생활비 보유 |

AoM이 높을수록 당장 쓸 일이 없는 여유 자금이 많고, 낮을수록 유동성 확보가 급하다.

```text
AoM < θ_buffer   → 버퍼 얇음
AoM ≥ θ_buffer   → 버퍼 두꺼움
```

※ `θ_buffer`는 실데이터 검증 후 확정 — §8 미정.

#### 입력값

| 항목 | 변수 | 의미 | 출처 |
|---|---|---|---|
| 납입 규모 | `kept_mean` | 월 확정 지킨 돈 평균 | `finalized_kept_amount` 이력 |
| 안정성(버퍼) | `aom` | AoM(Age of Money) | `cash_buffer` |
| 유동성 필요도 | `large_expense_cycle` · `predictable` | 큰 지출 주기와 예측 가능 여부 | `recurring_payments` + 대규모 지출 |
| 우대조건 | `met` | 카드 실적 · 급여이체 · **당행 보유** 충족 여부 | `preferential_material` × 사용자 데이터 · 마이데이터 계좌의 `bank`와 카드의 `companyName` |

#### 판단 로직

**M1. 상품 그룹 분류** — 적립 방식별로 분리해 제시한다: 파킹통장 · 자유적립식 · **정기예금** · 정액적립식.
전체 상품을 하나의 순위표로 합치지 않는다. **그룹 순서 자체가 추천 결과가 되므로** 적립 방식을 먼저 가른다 (거울 원칙 — §1·§2).

> **정기예금은 넷째 그룹이다**(2026-08-11 문서 반영). 원래 M1은 세 그룹만 적었는데 §10 3단계의 추천 대상이
> `적금 · 예금 · 파킹 전부`라 예금이 갈 자리가 없었다. 적립식(매달 조금씩)과 예금(목돈 한 번에)은 납입 구조가
> 아예 달라 한 그룹에 섞을 수 없다. 코드는 이미 넷으로 가르고 있다(`AccrualType.DEPOSIT`).

**M2. 유동성 우선** — AoM 낮음(버퍼 얇음) · 또는 `predictable = false` · 또는 `large_expense_cycle`이 짧음 → **파킹통장 그룹 상단**.

**M3. 수익률 우선** — AoM 높음(버퍼 두꺼움) 그리고 큰 지출 예측 가능 → **자유적립식 그룹 상단**.

**M4. 정액적립식** — 항상 노출한다. 표시는 `매달 고정 금액 납입 필요`까지만.
금지 — `MOA 흐름과 맞지 않음` · `부적합` · `추천하지 않음` 같은 판단 표현. **적합 여부는 사용자가 정한다.**

**M5. 가입 금액** — 2026-08-11 전면 개정.

상품이 받아 주는 금액과 `kept_mean`(월 확정 지킨 돈 평균)을 견준다. **둘을 다르게 다룬다**(사용자 결정 2026-08-11).

```text
하한 미달   "월 1만원 이상"을 못 채운다   → 가입 자체가 안 된다   → 목록에서 뺀다
상한 초과   "월 50만원까지"를 넘는다      → 가입은 된다           → 남기고 사실만 적는다
```

상한 초과를 빼지 않는 것은 거울 원칙이다. 지킨 돈이 월 80만인 사람에게 월 50만 상한 상품은
**금리가 제일 높아도 내 돈의 3/8이 안 들어가는 상품**이라 그 사실은 알려야 하지만, 담을지 말지는
사용자가 정한다. 화면에는 `월 50만원까지 담을 수 있어요`까지만 쓰고 `부족`·`맞지 않음` 같은 판단어는 안 쓴다.

**재료는 두 칸에 나뉘어 있고, 지금은 둘 다 안 읽고 있다.**

| 출처 | 수집률(적금) | 모양 |
|---|---:|---|
| `max_limit` | 43/58 (74%) | 정수. 적금은 **월** 납입 상한 (`500000` = 월 50만) |
| `etc_note` | 29/58 (50%) | 자연어. `가입한도: 월 1만원 이상 50만원 이하` — **하한은 여기에만 있다** |

**하한을 아예 못 구하는 상품이 절반이다.** 그 상품은 하한 조건 미수집(`null`)이라 M5가 통과시킨다 —
없는 값으로 상품을 지우지 않는다.

`max_limit`을 1순위로 읽고 없으면 `etc_note`를 파싱한다. 둘 다 있으면 대조해 **어긋나면 둘 다 버린다**
(`null` = 미수집 = 통과). 틀린 금액으로 상품을 지우느니 안 거르는 편이 낫다.

**규모 필터는 적립식(적금)에만 건다.** 정기예금의 가입금액은 `최소 100만원 이상`처럼 **목돈** 기준이라
월 단위인 `kept_mean`과 비교 대상이 아니다. 예금의 재원은 월 저축액이 아니라 이미 모인 목돈인데 우리는
그중 얼마를 묶을지 모른다 — AoM의 평균잔고를 대신 쓰면 생활비까지 묶는 셈이 된다.
**예금·파킹은 금액 조건을 표시만 한다.**

※ 규모는 **필터 기준일 뿐** 추천 방향을 정하지 않는다.

**M6. 실수령 금리 계산 — 3분기.** 2026-08-11 전면 개정.

옛 규칙은 이분(전부 충족=최고 / 미충족=기본)이었는데, **모든 상품이 카드 실적·급여이체를 요구한다는
가정** 위에 서 있었다. 실측상 그 가정은 83%에서 틀린다. 그래서 **상품마다 요구 조건을 읽고**, 읽어도
판정할 수 없으면 **판정할 수 없다고 말한다**(사용자 결정 2026-08-11).

**먼저 조건 종류를 뽑는다 — 가산폭은 뽑지 않는다.** `spcl_cnd` 자연어에서 **종류만** 구조화한다.

**이미 있는 틀에 얹는다.** 가입 자격(`join_member`)을 구조화하는 `EligibilityLabelService`가 같은 문제를
이미 풀어 놨다 — **LLM이 공시 문구를 구조로 옮기기만 하고 판정은 순수 함수가 하며, 키가 없거나 호출이
실패하면 규칙 파서로 떨어진다.** 원칙 1과 충돌하지 않는 이유도 그대로다: 밖으로 나가는 것은 **금감원이
공개한 상품 공시 문구뿐**이고 사용자 소비·식별 정보는 나가지 않으며, `충족했나`라는 판정은 AI가 하지
않는다. 상품별 라벨은 문구 해시로 캐시해 같은 공시를 두 번 묻지 않는다(`ProductEligibility`와 같은 방식).

`없음`·`해당없음`·`-`은 **요구 조건이 빈 집합**이라는 뜻이고(실측: 한국스탠다드차타드 `퍼스트가계적금`),
파싱 실패와 **다르게** 다룬다 — 빈 집합이면 채울 조건이 없으니 곧바로 최고금리다. 지금 규칙은 이 상품에
`미충족: 카드 실적, 급여이체`라고 **없는 조건을 지어내 말한다.**

> **자격 라벨러와 실패 방향이 반대다.** 자격은 못 읽으면 **제외**한다(가입 못 할 상품을 권하느니 덜 보여준다).
> 우대조건은 못 읽어도 **제외하지 않고 기본금리로 내린다** — 조건을 모른다고 해서 그 상품에 가입할 수 없는
> 것은 아니기 때문이다. 둘을 같은 규칙으로 묶으면 83%가 목록에서 사라진다.

**조건 하나를 판정하는 규칙.**

| # | 상황 | 판정 |
|---|---|---|
| 1 | 사전에 없는 종류 | **판정 불가** |
| 2 | 종류는 알지만 우리 축이 아님 (자동이체·첫거래·마케팅 동의…) | **판정 불가** |
| 3 | 우리 축인데 **당행 한정**이 붙음 — 그 금융사와 거래가 **없음** | **미충족 (확정)** |
| 4 | 우리 축인데 당행 한정 — 그 금융사와 거래가 **있음** | **그 금융사로 좁혀서** 충족 / 미충족 |
| 5 | 우리 축이고 금융사 한정 없음 | **충족 / 미충족 (확정)** |
| 6 | 종류가 `주거래`·`예적금 보유`처럼 정의가 상품마다 다름 | **판정 불가** |

③·④가 **당행 축**이다. 실측상 28%(16/58)가 `당행`·`주거래`·`입출식 계좌`를 걸고, 12%는 조건문에 자기 은행
이름을 그대로 박는다(`우리은행 입출식 계좌에서 각 항목별 실적 월 수가 계약기간의 1/2 이상인 경우`).

**좁혀서 판정할 수 있다는 근거는 §0.2에 있다** — ①이 `UserPayment.cardCode → UserCard.companyName`으로
**카드사별 실적 분리가 가능하다**고 확인해 줬고, 급여가 어느 은행 계좌로 들어오는지는 계좌의 `bank`가 준다.
그러니 당행 한정을 만나면 후보를 통째로 포기할 게 아니라 **그 금융사 것만 보면 된다.**

지금 L5는 카드 실적을 **보유 카드 중 최대 전월실적**으로, 급여이체를 **계좌에 급여가 잡히는지**로 보며
**어느 금융사인지 안 본다**(`AccountFundFlowSource.preferential`). 당행 한정 상품에 이 판정을 그대로 쓰면
과대 표시가 된다 — ③·④가 그 자리를 메운다. **L5 재료를 금융사별로 쪼개는 것이 M6 개정의 선행 작업이다.**

> **유지 요건은 원래 확정할 수 없다.** 대부분의 우대조건은 `계약기간의 1/2 이상`처럼 **가입 이후 지켜야 하는
> 것**이라, 엄밀히는 지금 시점에 충족·미충족이 정해지지 않는다. 우리가 하는 판정은 **"지금 그 습관이 있으니
> 이어 가면 채울 수 있다"는 근사**다. 이 근사는 M6 개정 전에도 이미 쓰고 있었고 그대로 둔다 — 다만 화면
> 문구는 `충족했어요`가 아니라 **`카드 실적 조건이 있어요`** 쪽 사실형이어야 한다(R9 · §8.1).

**상품 하나의 실수령 금리.**

```text
요구 조건이 빈 집합                     → effective = max_rate    (채울 게 없다)
전부 확정 판정 & 전부 충족               → effective = max_rate
확정 미충족이 하나라도 있음               → effective = base_rate   + 미충족 목록 (M8)
확정 미충족은 없고 판정 불가만 있음        → effective = base_rate   + `확인 못한 조건 N개`
```

마지막 줄이 새로 생긴 상태다. **`미충족 없음`으로 읽으면 안 된다** — 코드에는 이미 `conditionsKnown`
플래그가 있고(`SavingsMatch`), 화면은 그 사실을 그대로 말한다. 판정 불가일 때 기본금리로 내리는 쪽을
택한 것은 **덜 준다고 말하는 방향**이라 사용자가 받을 금리를 부풀리지 않기 때문이다.

**조건별 부분 가산은 하지 않는다**(§8.1 D2 유지). 다만 **검산식을 게이트로 둔다** — 어떤 상품의 `%p` 합이
`(최고 − 기본)`과 맞으면 그 상품은 파싱이 신뢰되는 것이고, 안 맞으면 종류만 쓰고 숫자는 버린다. 실측
일치율이 4/25(16%)라 지금은 거의 전부 후자다. **일치율이 올라가면 그때 부분 가산을 다시 본다.**

**M7. 그룹 내 정렬** — 각 그룹 **내부에서만** `effective_rate` 내림차순. **그룹 간 우열은 매기지 않는다.**

**M8. 우대조건 표시** — 실수령 금리(`effective_rate`) · 최대 금리(`max_rate`) · 현재 미충족 우대조건을 함께 노출한다.

```text
실수령 금리 3.2%
(조건 충족 시 최대 4.0%)
현재 미충족
- 카드 실적
```

사실 정보만 준다. 가입 유도·행동 유도 표현은 쓰지 않는다 (R9).

**세 번째 화면 상태가 생겼다**(M6 3분기, 2026-08-11). 판정 불가 상품은 미충족 목록 자리에 **못 읽었다는
사실**을 쓴다. 실측상 이쪽이 다수(83%)라, 화면 설계에서 예외가 아니라 **기본 상태**로 다뤄야 한다.

```text
실수령 금리 3.2%
(조건 충족 시 최대 4.0%)
우대조건 2개는 확인하지 못했어요
- 자동이체 · 마케팅 동의
```

`미충족`이라고 쓰지 않는다 — 모르는 것과 안 되는 것은 다르다. 반대로 우대조건이 아예 없는 상품
(`퍼스트가계적금`)은 **이 영역을 통째로 비운다.** 없는 조건을 `미충족`으로 적으면 거짓말이 된다.

**M9. 동점 처리** — 같은 그룹에서 `effective_rate`가 같으면 ① 미충족 우대조건 수가 적은 것 → ② 만기가 짧은 것 → ③ `base_rate`가 높은 것 → ④ 금융사명 가나다순.

**판정 불가 상품은 ①에서 맨 뒤다** — 미충족이 0건이어서가 아니라 셀 수 없는 것이라, 0으로 세면 확인된
완전충족 상품과 같은 자리에 놓인다.

> **M2(유동성 우선)일 때만** ①과 ② 사이에 **중도해지이율이 높은 것**을 끼운다(M10). 돈이 묶이면 안 되는
> 사람에게는 "깼을 때 얼마 남나"가 만기 길이보다 실질적이다. 유동성이 급하지 않은 사용자에게까지 이 축을
> 쓰면 만기까지 갈 사람에게 무의미한 순서 변동을 만든다.

**M10. 중도해지이율** — 2026-08-11 신설.

**금감원에는 이 칸이 없다.** `mtrt_int`는 이름이 비슷하지만 *만기 후* 이자율이고
(`만기 후 1개월 이내: 만기시점약정이율 × 50%`), 중도해지와 무관하다. 그런데 M2가 파킹통장을 위로 올리는
근거가 바로 "적금은 중도에 깨면 손해"라서, **손해의 크기를 모른 채 규칙만 서 있는 상태**였다.

**각 은행 상품공시에서 수집한다**(사용자 결정 2026-08-11). 카드(§4.4)와 같은 방식이고 같은 선을 지킨다 —
1차 원천(각 사 자사 공시)만 쓰고, 운영자가 명시적으로 막아 둔 곳은 우회하지 않으며, **수집 기준일을 화면에
병기**한다. 대상은 금감원 응답에 나오는 은행권 상품(적금 58 · 예금 38)이다.

**못 구한 상품은 `null`로 두고 화면에서 그 자리를 비운다** — 카드에서와 같이 모르는 값을 0이나 평균으로
메우지 않는다.

쓰임은 둘이다. **표시**(`지금 깨면 연 0.9%예요`)와 **M9 동점 처리**(유동성 우선일 때만). 정렬의 1순위인
`effective_rate`는 건드리지 않는다 — 중도해지는 만기까지 가는 사용자에게는 일어나지 않는 일이라, 모든
사용자의 순위를 이 값으로 흔들면 안 된다.

> 🔁 **개정 (2026-08-12) — 표기 구조가 설계 때 적어 둔 것과 달랐다.** 예전 문장은 *"대개
> `예치기간 구간 → 약정이율 × N%` 표라 카드 혜택보다 구조가 단순하다. `(구간, 배수 또는 고정이율)`
> 배열로 담는다"* 였다. **실제 공시를 열어 보니 셋이 더 있었다**(케이뱅크 `코드K 자유적금`).
>
> ```text
> 1개월(30일) 미만    연 0.10 %
> 1개월(30일) 이상    연 0.30 %
> 6개월(180일) 이상   기본금리 × 70% × 경과일수/계약일수  (최저 연 0.50 %)
> ```
>
> ① 구간이 `미만`이 아니라 **`이상`(하한)** 으로 끊긴다 ② 배수 구간에 **경과일수 비례**가 붙어 절반
> 시점에 절반만 받는다 ③ 그 아래로 안 내려가는 **최저이율**이 따로 있다. 비례를 빼먹으면 12개월 상품을
> 6개월에 깼을 때 `3.7×0.7=2.59%`로 **실제(1.295%)의 두 배**를 말하게 된다. 그래서 칸을
> `(하한, 고정이율 | 배수, 비례여부, 최저이율)`로 고쳤다 — 카드 스키마를 BC 3장에서 역으로 뽑은 것과
> 같은 순서다. **지어낸 구조로 그릇을 먼저 만들면 실제 표기와 어긋난다.**

**표기가 다섯 가지다** — 은행 사이는 물론 **한 은행 안에서도** 갈린다. 파서를 한쪽에만 맞추면 나머지가
조용히 빠진다.

| | 예 | 어디서 |
|---|---|---|
| 개월(일) 병기 | `1개월(30일) 미만 연 0.10 %` | 케이뱅크 코드K 자유적금 |
| 일 단위만 | `30일 미만 연 0.10 %` | 케이뱅크 마이키즈 적금 |
| 구간표 없이 한 줄 | `중도해지금리 적용금리 : 연 0.10 %` | 케이뱅크 데굴데굴 농장 |
| 개월만 | `6개월 미만 연 1.8%` | 토스뱅크 굴비 적금 |
| **구간 · 하한 미포함** | `1개월 초과 3개월 이하 연 0.30%` | 토스뱅크 정기예금 |

**마지막 것이 값을 바꾼다.** `3개월 초과 6개월 이하`를 `6개월 이상`으로 읽으면 12개월 상품을 6개월에
깼을 때 다음 구간(70%)을 집어 **실제(50%)보다 많이 준다고 말하게 된다.** 그래서 구간에 `하한 미포함`
표시를 따로 둔다.

`중도해지금리`라는 낱말은 본문에도 나오므로(부분인출 설명) **표 머리말(`보유기간`·`가입기간`·`예치기간`)이
붙은 자리**를 골라 잘라야 하고, 바로 뒤의 **만기 후 금리 표와 섞이지 않게** 끊어야 한다 — 값의 모양이
`기본금리 × 50%`로 비슷해서 섞여도 눈에 안 띈다.

> **조용한 누락이 실제로 났다.** 토스뱅크 자유 적금은 `기본 금리X50%`처럼 **`기본`과 `금리`를 띄어 써서**
> 구간 여섯 중 넷이 빠졌는데, **남은 둘로도 그럴듯해 보여 안 걸렸다.** 그래서 수집기가 이제
> **표의 기간 표현 수와 읽어낸 구간 수를 대조해** 모자라면 경고를 남긴다. 시험도 구간 수로 못을 박았다.

### 4.6 목표 추천 (FP-04) — 2026-08-04 신설

③의 세 번째 추천이다. 저축·카드와 달리 **두 축을 함께 쓴다.**

| | FP-01 저축 | FP-03 카드 | **FP-04 목표** |
|---|---|---|---|
| 매칭 근거 | 자금 흐름 축 | 취향 축 | **취향 축 = 무엇을 · 자금 흐름 축 = 얼마나** |
| 주는 것 | 실수령 금리 | 예상 절약액 | **도달 시점과 대상** |
| 선행 조건 | 없음 | 없음 | **②의 확정 지킨 돈 > 0** |

#### 되살린 근거

`03_솔루션/01_핵심설계결정` 5차 검토가 여행·물건 목표를 제거했다. 그러나 `_history/0730_멘토링회의록` Ⅱ.3에 기록된 실제 기각 사유는 **이중 목표 구조**였지 기능 자체가 아니었다.

```text
이가원        "목표가 두 개가 되어버린 게 문제였다 (지킬 돈 10만 원 + 맥북)"
박은종 디렉터  "10만 원을 지키면 맥북은 자연히 지켜진다. 두 개를 동시에 쫓는 구조가 아니다"
```

같은 회의의 결정사항은 **영구 배제가 아니라 `나중에 선택지로 제공`** 이었다. 이 절이 그 유보를 해제한다.

#### 코어 루프 — 목표는 다음 챌린지의 동기가 된다

```text
① 챌린지 수행 → ②가 지킨 돈 확정
② ③이 환산해 노출          "126만이면 이런 것들"
③ 사용자가 목표 선택         (선택 사항. 안 골라도 서비스는 그대로 돈다)
④ 다음 챌린지의 동기 ────┐
                          │
   └──────────────────────┘
```

**첫 챌린지는 목표 없이 돈다.** 확정 지킨 돈이 없으면 ②가 뜨지 않으므로, 멘토가 지시한 배치(`온보딩 앞이 아니라 성과가 났을 때 뒤에`)가 규칙이 아니라 **구조로** 지켜진다. 콜드스타트도 같은 이유로 발생하지 않는다.

#### 이중 목표를 레이어로 푼다

| 레이어 | 있는 것 | 판정 관여 |
|---|---|---|
| **판정** | 지킬 돈 · 한도 · 차감 · 확정 금액 | ✅ 전부 |
| **동기** | 마이룸 · 칭호 · **목표** | ❌ **없음** |

**목표는 마이룸과 같은 층이다.** 마이룸이 `지킨 돈 → 소품`으로 환산하듯 목표는 `지킨 돈 → 실물`로 환산한다. 목표 금액은 ②의 판정에도, FP-01 상품 매칭에도 들어가지 않는다.

> 목표가 2개인 것이 아니라 **목표 1개(지킬 돈) + 동기 2개(마이룸·목표)** 다.

#### 계산 방향 — 기간을 먼저 고정한다

```text
X  목표를 고른다 → 몇 개월 걸리나 계산      ← 그랜저를 넣으면 40년이 나온다
O  기간을 고정한다(3·6개월) → 그 예산에 맞는 대상을 찾는다
```

```text
3개월 예산 = kept_mean × 3
6개월 예산 = kept_mean × 6
```

기간이 상수이므로 **동기가 소멸하는 장기 목표가 구조적으로 생기지 않는다.** 멘토 답변(`절약 가능한 금액에 맞춰 3개월·6개월 단위로 시스템이 제안`)을 그대로 옮긴 것이다.

#### 표현 규칙

마이룸(`03_여정과_성장` §4.2)과 주간 리포트(§3.1)의 규칙을 재사용한다. 새로 만들지 않는다.

| 규칙 | 출처 |
|---|---|
| **목표는 실패하지 않는다. 늦어질 뿐이다** | 마이룸 `감소·리셋 없음` |
| **진척은 사실로만. 페이스 평가·독촉 금지** | §3.1 `금액과 평가의 경계` |
| **언제든 바꾸거나 지울 수 있다** | 페르소나 — `또 하나의 숙제가 되는 것`에 대한 두려움 |

```text
O  "지금 42만 원 · 목표까지 84만 원"
O  "이 속도면 3개월 뒤 126만 원이 모여요"

X  "목표의 33% 달성"              ← 도착률 (R9)
X  "이 페이스면 5개월 걸려요"      ← 페이스 평가 (R9)
X  "맥북 사려면 3개월 더 아껴보세요" ← 행동 유도 (R9)
```

`126만 원 중 42만 원`은 되고 `33%`는 안 된다. 주간 리포트에서 이미 긋고 있는 선과 같다.

#### 이커머스 연결

목표 대상은 실제 구매처로 연결한다. **금소법은 적용되지 않는다** — 맥북·여행상품은 금융상품이 아니다. 적용되는 것은 전자상거래법·표시광고 계열이고, 핵심 의무는 `대가를 받으면 광고임을 표시`뿐이다.

| 안전핀 | 없으면 |
|---|---|
| **지킨 돈 범위 안에서만 노출** — 예산 초과 상품은 보여주지 않는다 | 절약 앱이 아니라 쇼핑 앱이 된다 |
| **성과 난 뒤에만** — 온보딩·홈 상단 금지 | 목표가 2개가 된다 |
| **제휴를 맺지 않는다** — 수수료 0 | 수수료를 받는 순간 `덜 쓰게`와 `더 사게`가 충돌한다 |

세 번째가 핵심이다. **수수료를 받으면 서비스의 인센티브가 사용자와 반대 방향이 된다.** 받지 않으면 링크는 편의 기능일 뿐이다.

| | 물건 | 여행 |
|---|---|---|
| 소스 | 상품 검색 API (상품명·가격·링크) | 공개 API 사실상 없음 |
| 판단 | 🟢 **먼저 한다** | 🟡 **후순위** — 가격 비교가 성립하지 않는다 |

#### 화면 형태

```text
┌ 이번 챌린지 42만 원 지켰어요              ← 선행 조건
│
├ 이 속도면  3개월 뒤 126만 · 6개월 뒤 252만

└ 126만 원이면                              ← 예산 안에서만
  · 다이슨 에어랩   42만   [보러가기]
  · 아이패드 에어   89만   [보러가기]
```

모든 문장이 과거·현재형이고 명령형이 없다. **목표를 정해주는 것이 아니라 이미 지킨 돈이 얼마짜리인지 번역한다.**

### 4.7 지킨 돈 굴리기 — 2026-08-12 신설

**예적금이 비교만 하기로 되면서 생긴 빈자리를 메운다**(§4.5 개정). 비교 화면을 따로 두면 사용자가
`얼마 넣을 건데?`를 직접 입력해야 하는데, **결산 시점에는 그 금액이 이미 정해져 있다** — 지킨 돈이다.

#### 왜 이 자리인가

챌린지를 끝내면 지킨 돈이 생기는데 **그 돈을 어디 둘지는 아무도 안 알려 준다.** 결산 화면은 금액이
확정되는 유일한 순간이고, 사용자가 성과를 막 확인한 자리다.

#### 무엇을 보여주나

```text
지킨 돈, 그냥 두실 건가요?
파킹통장은 언제든 넣고 뺄 수 있어요.

  이 페이스로 1년이면        1,044,000원 + 이자 10,120원 → 1,054,120원
  지금까지 모은 522,000원을 1년 두면   522,000원 + 이자 11,040원 → 533,040원

  매일이자Wa파킹통장  광주은행   연 2.50%
  JB MY금고          전북은행   연 2.00%
  기분통장           케이뱅크   연 1.70%
```

**원금을 같이 보여주는 것이 핵심이다**(사용자 결정 2026-08-12). 이자만 떼어 놓으면 `2,215원`이라
초라한데, 원금이 붙으면 규모가 보인다. 사용자가 알고 싶은 것은 *금리 몇 %*가 아니라 **얼마가 되나**다.

#### 개인화가 아니다

| | 개인화였던 것 | 지금 |
|---|---|---|
| 답 | 사람마다 다름 (`당신은 조건을 채웠으니 3.2%`) | **같은 금액이면 누구나 같음** |
| 쓰는 것 | 마이데이터로 우대조건 충족 판정 | **금액 하나** — ②가 확정한 지킨 돈 |

금액 칸이 자동으로 채워질 뿐이라 §4.5의 `비교만 한다`와 어긋나지 않는다.
**금액은 ②가 계산한 것을 합산만 한다**(R10) — 거래를 다시 훑으면 결산 화면과 다른 숫자를 말하게 된다.

#### 파킹통장만 쓴다

지킨 돈은 **매달 금액이 다르고 결산마다 덩어리로** 들어온다.

| | 맞나 |
|---|---|
| 파킹통장 | ✅ 아무 때나 넣고 뺀다. 다음 달 지킨 돈도 그냥 더한다 |
| 자유적금 | 🟡 매달 다른 금액은 되지만 만기까지 묶인다 |
| 정기예금 | ❌ 목돈 한 번에 · 만기까지 묶임 — 다음 달 지킨 돈을 못 얹는다 |
| 정액적금 | ❌ 매달 **같은 금액**을 요구한다 |

옛 설계가 `중심축은 파킹통장 ↔ 자유적립식`이라 했던 이유가 이것이고, **개인화를 걷어내도 이 사실은
그대로 성립한다.** 파킹은 금감원에 없어 별도 출처에서 온다(`ParkingAccountSource` — 비공식 API를 알고 쓴다).

**기본금리순으로 세운다.** 최고금리는 예치금 구간·첫거래 같은 조건이 붙는다 — 실측에 광주은행이
기본 2.50%인데 최고 5.10%로 **두 배가 넘는** 상품이 있다. 그 값으로 줄을 세우면 조건을 못 채운 사람에게
못 받을 금리를 앞세우게 된다.

#### 이자 계산에서 틀리기 쉬운 자리

**매달 넣는 돈은 전액이 1년 내내 있는 게 아니다.** 마지막 달에 넣은 돈은 이자가 거의 안 붙는다.

```text
X  1,044,000 × 2.5%                    = 26,100원   ← 2.2배 부풀려진다
O  87,000 × 2.5%/12 × (12×11/2 = 66)   = 11,962원   → 세후 10,120원
```

결산이 월말에 나오므로 **월말 입금**을 가정한다. 세후는 **일반과세 15.4%** 기준이며, 비과세종합저축·
세금우대는 **쓰지 않는다** — 사람마다 자격이 달라 개인화가 되고, 우리는 그 자격을 모른다.
파킹통장은 이자 지급 주기가 상품마다 달라(매일·매월) **단리로** 센다 — 복리로 계산하면 부풀려진다.

#### 표현의 선

§4.4 카드 추천과 같은 자리다. `이 페이스로 1년이면`은 **가정**이므로 화면이 그 사실을 밝힌다.

```text
O  "이 페이스로 1년이면 1,054,120원"          ← 산수 + 가정 명시
X  "1년 목표 100만원까지 얼마 안 남았어요"      ← 없던 목표를 만든다 (R9)
X  "조금만 더 하면 200만원도 가능해요"          ← 페이스 압박 (R9)
X  "지금 가입하세요"                          ← 가입 편의 (마스터 원칙 5)
```

**지킨 돈이 0이면 이 블록은 안 뜬다**(서버가 204). 없는 성과를 축하하지 않는다(거울 원칙).
파킹 조회가 막혀도 마찬가지다 — 0원짜리 블록을 그리느니 자리를 비운다.

## 5. 취향 서술의 단계적 확장

취향은 한 번에 열지 않는다. **사실 → 패턴 → 취향** 순으로 넓힌다.

| 단계 | 서술 | 상태 |
|---|---|---|
| 사실 | "올해 영화 관련 소비가 32회 있었어요." | **MVP — 현재 여기까지** |
| 패턴 | "영화를 꾸준히 즐기는 편이네요." | 향후 |
| 취향 | "영화가 삶의 중요한 취미인 것 같아요." | 최종 |

MVP에서는 **취향 단정을 금지한다.** §3.3의 `올해의 영화 러버`는 집계 사실에 붙는 라벨이지 성향 단정이 아니다 — 32회라는 숫자가 함께 보이는 형태로만 쓴다.

## 6. 보류 — 은퇴(Retire)

초기 아이디어는 이랬다.

```text
"택시는 줄이기 어려운 필수 소비 같아요."  → 절약 후보에서 제외
```

**MVP에서 보류한다.** 시스템 판단이 들어가고, 잘못 분류될 위험이 있으며, 사용자가 평가받는 느낌을 받는다.

현재 허용 수위는 여기까지다.

```text
O  "택시는 최근 3개월 동안 큰 변화가 없었어요."
X  "택시는 줄이기 어려운 필수 소비예요."
```

그 이상의 의미 부여는 하지 않는다.

### 8.1 확신이 낮은 지점

매칭(§4.5)을 지으면서 확신이 낮다고 적어 둔 것들이다. 구현 전에 한 번씩 다시 봐야 한다.

## 10. 어떤 순서로 만드나

각 단계에 **수용기준**(무엇이 되면 끝인가)을 붙인다. 앞 단계가 뒤 단계의 입력이다.

> ⛔ **2~3.6단계는 2026-08-12로 무효다** — 예적금이 개인화 대신 비교만 하기로 정해지면서(§4.5 개정)
> 매칭 경로가 코드에서 떼어졌다. 아래 ✅ 표시는 **그때 실제로 완료됐던 기록**이고 지금 살아 있는 경로가
> 아니다. 되살릴지는 §12가 정본이다. **1단계(①에 (B) 재료 요청)도 함께 값이 얇아졌다** — L1~L5를 쓰던
> 유일한 자리가 FP-01이었고, 지금 남은 소비처는 FP-04(§4.6)의 예산 산정뿐이다.

**0단계 ✅ (B) 소스 방식 결정 — 완료.** ①의 (B)가 아직 없어, 잔액을 마이데이터 계좌에서 직접 읽는 **B안**으로 풀기로 했다. 소비는 계속 카드로만 세므로 이중 계산이 없다(R7). `AccountFundFlowSource`가 L1·L3를 켰다.

**1단계 — ①에 나머지 재료 (B) 요청 → L2·L4·L5 켜기.** `fixed_expense_summary`·`recurring_payments`·`preferential_material`이 오면 같은 seam에 꽂는다. 판정 기계는 안 바꾸고 소스만 교체.
> *수용기준:* (B) 재료가 오면 L2·L4·L5도 UNKNOWN을 벗어난다.

**2단계 ✅ 매칭 M1~M9 (저축 추천의 두뇌) — 완료.** FundFlowProfile을 입력으로, AoM·L4로 파킹↔자유를 가르고 우대조건 충족으로 실수령 금리를 매긴 뒤 적립방식 그룹핑·그룹 내 금리순. (규칙은 §4.5, 판정은 코드·문장만 AI.)
> *수용기준:* 프로필이 다르면 추천 상품군이 갈린다. 규칙 단위 테스트 통과. → `SavingsMatchService` + 테스트 28개.

**3단계 ✅ 저축 비교 교체·확장 — 완료.** 옛 `SavingsCompareService`를 2단계 매칭에 연결하고 **예금(`depositProductsSearch`)을 조회에 추가**한다. 추천 대상 = 적금·예금·파킹 전부.
> *수용기준:* `GET /api/savings/compare`가 매칭 근거를 반영해 내려온다. 예금 포함. → 파킹은 별도 출처(`ParkingAccountSource`)로 채웠다.

**3.5단계 ✅ 상품 쪽 재료 채우기 — 완료 (2026-08-12).** 규칙은 다 섰는데 **입력이 비어서 헛돌던 세 자리**를 메웠다. 앞 단계와 달리 규칙 작업이 아니라 **데이터 작업**이었다.

| | 하는 일 | 수용기준 | 결과 |
|---|---|---|---|
| a | `min/max_amount` — `max_limit` 읽고 `etc_note` 파싱 (M5) | 지킨 돈이 하한에 못 미치는 상품이 목록에서 빠지고, 상한 초과 상품은 **남되 금액 문구가 붙는다** | ✅ 예금은 목돈 기준이라 **금액으로 거르지 않는다**(표시만) — 월 단위 `kept_mean`과 비교 대상이 아니다 |

**4단계 — 리포트 3층.** 옛 월간 리포트를 걷어내고 §3의 주간=관찰/월간=회고/연간=정체성으로 다시 짓는다. 소비 흐름은 ③ 직접 집계(R10), 금액은 ②의 (C) 값 그대로(R10).
> *수용기준:* 세 리포트가 각자의 주기·화법으로. 취향은 월간=집계 사실, 정체성 서술은 연간만(§3·§5).

**5단계 — 카드 추천 (FP-03).** 카드 공시 수집이 끝나면 취향 축으로 혜택 카드를 매칭한다(§4.4).
> *수용기준:* 소비처 상위와 혜택 카테고리가 맞는 카드가 상단에. *(선행: 카드 데이터 수집 완료 — 후순위)*

**6단계 — 목표 추천 (FP-04).** 두 축을 합쳐 `3·6개월 예산 → 취향 카테고리 → 상품`을 낸다(§4.6). **선행이 다르므로 둘로 쪼갠다 — 6a는 지금 착수 가능하고, 6b만 외부 데이터를 기다린다.**

**6a. 예산·취향까지 (선행 없음).** `budgets`(예산) + `taste_categories`(취향 축) + `selected_goal`(저장·표시). 취향 축은 이미 구현돼 있고(`TasteAnalysisService`), 예산은 `kept_mean`이 없으면 **(C)의 `securedSaving` 직전 1건으로 대체**한다 — 이력이 쌓이면 평균으로 승격.
> *수용기준:* 확정 지킨 돈이 0이면 `goal_suggestions`가 `null`이고, 0보다 크면 3·6개월 예산과 취향 카테고리가 나온다. 사용자가 목표를 직접 적어 저장·수정·삭제할 수 있다. 진척 표현에 `%`·페이스 문구가 없다.

**6b. 상품 목록 (선행: 상품 검색 API).** `items`를 예산 이하 가격으로만 채운다. API 선정 전에는 **수기 목록·mock으로 화면을 세워두고** 소스만 교체한다.
> *수용기준:* 예산을 넘는 상품이 응답에 포함되지 않는다. `affiliate: false`가 화면에 표시된다.

> **착수 시점을 고정하지 않는다.** 회의록 Ⅱ.4는 `중간발표 이후 개인화 집중`이라 했으나, 6a는 선행이 없어 **다른 단계와 병행 가능**하다. 가능한 범위부터 진행하고 6b만 데이터가 열리는 순서를 따른다.

| **②의 이력** | `GET /api/guardian/challenges/history`(`securedSaving`·`endDate`) | L3 규모용 `kept_mean`·월간 회고 | 🔴 ②에 조회 신설 요청 (§0.2·§8) |
| **외부 (D)** | 금감원 상품(금리·`spclCnd` 자연어)·카드 공시 | 저축·카드 추천 후보 | 🟡 적금·예금·파킹 조회 중. **`spclCnd`·`etc_note`는 안 읽고 있다**(M5·M6가 굶는다) · 중도해지이율·카드 공시는 수집 대기 |
| **③이 내는 것** | `FundFlowProfile`(L1~L5) → 매칭 입력 · 리포트 산출물 (E) | 저축/카드 추천·리포트 | 🟢 프로필까지 · 매칭 이후 미구현 |

## 13. 프론트 (frontend)

**`frontend` 하나로 관리한다** (2026-08-18 결정). 앞서 이 절은 *"frontend-moa가 우리 기본 앱이고
③ 화면은 거기 처음부터 짓는다(그린필드)"* 라고 적고 있었는데, **그 방향은 폐기됐다.**

`frontend-moa` 는 2026-07-27 이후 손대지 않았고(30일간 커밋 2건 · 화면 10개), CI·compose·배포
스크립트 어디에도 걸려 있지 않았다. 반면 `frontend` 는 같은 기간 커밋 107건 · 화면 43개이고
**③ 화면 넷이 실제로 여기서 돈다** — 카드 추천(`Compare`) · 예적금 비교(`ReportSavings`) ·
지킨 돈 굴리기(`Settle`) · 리포트(`ReportSpending`).

옛 문장대로 하면 **이미 도는 화면을 버리고 다시 짓게 된다.** 그래서 `frontend-moa` 는 저장소에서
지웠다(되살릴 일이 있으면 `git show <2026-07-27 커밋>:frontend-moa/…`).

> **옛 `frontend` 를 "①개발자의 테스트베드일 뿐"이라 적었던 것도 함께 무효다.** 그 판단 위에
> 그린필드 결정이 서 있었는데, 지금은 그 앱이 제품이다.

| 신설 화면 | 대응(IA) | 비고 |
|---|---|---|
| 저축 추천 | FP-01/02 | 파킹↔자유 분기·실수령 금리 |
| 리포트 주간/월간/연간 | RP-01/02 + 연간 RP-07 | 3층 각각 |
| 취향(리포트 내) | §3.2/§3.3 | 월간=집계·연간=정체성 |
| 카드 추천 | FP-03 | 후순위(데이터 대기) |
| 목표 추천 | **FP-04 (IA 신설 필요)** | 확정 지킨 돈 > 0일 때만 진입. 리포트 월간 하단 또는 홈 성과 영역 |

> **방식**: 실연동 전에는 mock으로 화면 뼈대 먼저 → 해당 단계 백엔드 준비되면 실데이터로 교체.

## 14. 구현 예외 / 엣지

§8(미정)이 "무엇을 아직 못 정했나"라면, 여기는 "지금 코드가 어떻게 처리하나"다.

| 상황 | 처리 |
|---|---|
| **소비 이중 계산** | 소비는 카드 승인내역만 센다. 계좌에선 잔액·급여만 읽고 출금 거래를 소비로 세지 않는다(R7) → 겹세기 원천 차단. |
| **콜드스타트** | AoM은 마이데이터로 가입 첫날부터 계산돼 안정성 콜드스타트는 완화(§4.1). 재료 없는 축은 `UNKNOWN`으로 두고 숨기지 않는다. |
| **우대조건 정밀 가산 불가 (D2)** | 금감원 API가 우대조건을 자연어 `spclCnd`로만 줌 → "전부 충족=최고금리 / 미충족=기본금리" 이분만 확정 사용. 부분 가산은 파싱 신뢰도 확보 후(§8). |
| **미분류(category2 없음)** | 취미·매칭에서 조용히 제외. 없는 신호를 지어내지 않는다(거울 원칙). |
