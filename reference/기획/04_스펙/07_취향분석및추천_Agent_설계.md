## 1. 제품 철학

가계부 앱은 보통 사용자를 교정하려고 한다. 우리는 교정하지 않는다.

**서비스의 역할은 판단자가 아니라 거울이다.** 사용자가 데이터를 보고 스스로 의미를 발견하도록 설계한다.

---

## 2. 핵심 원칙

> **AI는 소비를 설명하고, 소비의 의미는 사용자가 결정한다.**

```text
O  "이번 달 택시비 8만 원 중 5만 원이 평일 오전에 발생했어요."
O  "올해 가장 많이 택시를 탄 시간대는 오전 8~9시였어요."

X  "출근 때문에 택시를 많이 타시네요."
X  "지각 방지 택시가 반복되고 있어요."
X  "이 소비는 필수 소비예요."
```

### 2.1 왜 해석하지 않는가

AI의 정확도 문제가 아니다. **사용자가 "평가받고 있다"고 느낄 위험** 때문이다.

같은 데이터가 전혀 다른 사정을 담는다.

```text
데이터    오전 8~9시 택시 12회
해석 시도  "지각 방지 택시가 반복되고 있습니다"
실제 이유  출근 · 등원 · 병원 · 미팅 · 그날만의 사정 …
```

하나를 골라 말하는 순간 나머지 사정을 가진 사용자는 오해받는다. 그래서 **현 단계에서는 의미를 단정하지 않고 사실만 전달한다.**

## 3. 리포트 3종

### 3.1 주간 = 관찰

**이번 주 어떤 소비가 있었는지.**

| | |
|---|---|
| 포함 | 카테고리별 소비 · 시간대 패턴 · 요일 패턴 · 소비 흐름 |
| 포함 | **지키는 금액 — 사실로서만** |
| 금지 | 목표 달성 여부 · 잘했다/못했다 · 페이스 평가 · 행동 교정 |

```text
O  "배달 3건이 화·목·금 밤에 있었어요."
O  "이번 주 카페에서 4번, 21,000원 썼어요. 지금 100,000원 지키는 중이에요."

X  "이번 주 목표의 80%를 달성했어요."
X  "이 페이스면 이번 챌린지는 어려워요."
X  "주말엔 배달을 줄여보세요."
```

> **금액과 평가의 경계.** `100,000원 지키는 중`은 **상태 사실**이라 넣는다. `달성률 80%`·`이 페이스면`은 **평가**라 뺀다. 금액을 숨기면 사용자가 홈에서 본 숫자와 리포트가 어긋나 오히려 혼란스럽다.
> ②의 `achievementRate`·`paceRatio`는 주간 리포트에 쓰지 않는다.

### 3.2 월간 = 회고

**이번 챌린지에 어떤 흐름이 있었는지.** 주기는 달력 월이 아니라 **챌린지 종료일**이다(`06_지킴이_Agent_설계.md` §0.2).

| | |
|---|---|
| 포함 | 지킨 금액 · 소비 카테고리 비중 · 직전 챌린지 대비 변화 · 반복적으로 나타난 패턴 |
| 포함 | **취향 축의 집계 사실** — `이번 챌린지 카페 12번 · 영화 2편` |
| 금지 | 실패 · 합격/불합격 · 절약을 못했다는 평가 |
| 금지 | **취향 해석** — `당신은 미술 애호가` 같은 정체성 서술은 연간에서만 |

```text
O  "이번 챌린지 택시비의 62%가 평일 오전에 발생했어요."
O  "지난 챌린지보다 카페 소비가 3건 줄었어요."

X  "목표 달성에 실패했어요."
X  "절약이 부족했어요."
```

②의 `state`가 `SHORTFALL`·`FAILED`여도 그 이름을 노출하지 않는다. 사실(지킨 금액·흐름)만 말한다.

### 3.3 연간 = 정체성

**올해 나는 어떤 사람이었는지.** Spotify Wrapped와 유사한 경험.

| | |
|---|---|
| 포함 | 연간 소비 사실의 집계 — 횟수·장소 수·시간대 |
| 포함 | **제한적 취향 서술 (§5)** — 세 리포트 중 여기서만 허용 |
| 주기 | **달력 연도.** 챌린지 경계와 맞추지 않는다 |

```text
영화 32편 관람 · 전시 9회 방문 · 새로운 식당 47곳 방문
→ "올해의 영화 러버"
→ "새로운 경험을 즐긴 한 해"
```

연간은 챌린지 실적이 아니라 **소비 사실**을 재료로 하므로 챌린지 주기에 맞출 이유가 없다. 챌린지를 하지 않은 기간의 소비도 포함한다.

### 3.4 주기 정리

| 리포트 | 주기 | 성격 | ②의 금액 |
|---|---|---|---|
| 주간 | 챌린지 시작일 기준 7일 (§8 미정) | 관찰 | `securedSaving`만 |
| 월간 | 챌린지 종료일 (30일) | 회고 | 확정 지킨 돈 |
| 연간 | 달력 연도 | 정체성 | 쓰지 않음 |

## 4. 라이프스타일 분석 — 한 이름, 두 축

③의 분석 축은 **라이프스타일 분석** 하나다. 그 안에 성격이 다른 두 축을 둔다.

```text
마이데이터 · ①의 (B)
  ├─ 금액 · 시점 · 규칙성   →  자금 흐름 축 (L1~L5)  →  저축 상품 매칭 (FP-01)
  └─ 카테고리 · 가맹점 빈도  →  취향 축  ┬──────────▶  월간 리포트 (집계 사실)
                                        ├──────────▶  연간 리포트 (정체성)
                                        └──────────▶  카드 추천 (FP-03)

                              취향 축 ──✕──▶ 저축 상품 매칭
```

### 4.1 자금 흐름 축 (L1~L5)

| 축 | 계산값 | 출처 |
|---|---|---|
| L1 소득 | `salary_regular` · `salary_day` | (B) `income_profile` ← ① |
| L2 고정비 | `fixed_total` · 인출일 분포 | (B) `fixed_expense_summary` ← ① |
| L3 안정성 | `aom`(Age of Money = 자금 버퍼) · 규모는 `kept_mean` | (B) `cash_buffer` ← ① · kept_mean은 (C) ← ② |
| L4 유동성 | `large_expense_cycle` · `predictable` | (B) `recurring_payments` + 큰 1회성 지출 ← ① |
| L5 우대조건 | **카드 실적 · 급여이체** 충족 여부 | (B) `preferential_material` × (D) ← ①·외부 |

**대부분 ①에게서 온다.** ③이 직접 계산하지 않고 (B)로 받는 이유는 R7이다 — 급여·고정비·잔고는 계좌를 봐야 알 수 있는데 ③은 계좌 원본을 만질 수 없다. L3(AoM)도 ①이 (B) `cash_buffer`로 넘긴다. 규모용 `kept_mean`만 ②의 확정 이력에서 온다.

매칭 규칙 M1~M9는 §4.5가 정본이다. 규칙 엔진이 판정·정렬을 하고 LLM은 문장만 만든다(R2).

**L5는 카드 실적·급여이체 둘만 본다.** 자동이체는 더미에 해당 거래가 없어 제외했다(R7). 실제 적금 우대조건에서 가장 흔하고 가산폭도 큰 두 가지가 남았으므로 D2는 그대로 성립한다.

> ### ✅ L3 재정의 — kept 변동성 → AoM(Age of Money) (2026-07-28 해결)
>
> 옛 L3(`kept_cv` 지킨 돈 변동성)는 저축 여력이 아니라 **사용자의 목표 변경 빈도**를 재는 결함이 있었다 — 지킬 돈은 매 챌린지마다 사용자가 카테고리·강도를 새로 골라 달라지므로, 소비 습관이 그대로여도 `kept_cv`가 크게 나온다. 결과적으로 M2(정액 적금)가 죽은 규칙이 되던 문제.
>
> **해결**: 안정성은 목표 선택과 무관한 **AoM(자금 버퍼)** 으로 잰다 — 간이식 `평균잔고 ÷ 월평균지출`. 실제 입출금 현금흐름으로 계산돼 챌린지 선택에 오염되지 않고, 마이데이터로 **가입 첫날부터** 계산되어 콜드스타트도 완화된다. `kept_mean`은 *납입 규모* 산정에만 쓴다.
>
> 더불어 MOA의 지킨 돈은 매달 금액이 다르고 덩어리로 들어와 **정액적금과 구조적으로 안 맞으므로**(고정 납입 강제 = R9 페이스 유도 위험), 중심축을 "정액 vs 자유"가 아니라 **파킹통장 ↔ 자유적립식**으로 바꾼다(AoM·L4 주도). 상세 규칙은 §4.5(M1~M9).
>
> **남은 미정**: θ_buffer(버퍼 구간)·간이 vs 정통 AoM·카드-현금 시점 차이 보정 → §8.

### 4.2 취향 축

카테고리·가맹점 빈도에서 나오는 것.

```text
영화관 결제 32회 · 전시 9회 · 처음 가본 식당 47곳
```

**재료와 해석을 나눈다.** 같은 축이지만 어디까지 말하느냐가 다르다.

| 쓰이는 곳 | 어디까지 |
|---|---|
| 월간 리포트 | **집계 사실까지** — `이번 챌린지 카페 12번` |
| 연간 리포트 | **정체성 서술까지** — `당신은 미술 애호가` (§5) |
| **카드 추천 (§4.4)** | 소비처별 혜택 매칭의 입력 |
| ~~저축 상품 매칭~~ | **금지** (§4.3) |

### 4.3 왜 경로를 나누는가

취향이 **저축** 상품 매칭 입력으로 들어가는 순간 이런 문장이 만들어진다.

```text
X  "영화를 좋아하시니, 영화값 모으는 적금 어떠세요?"
```

**소비 목표를 만들어 유도**하는 것이라 R9 위반이다. 규칙으로 "쓰지 말자"고 막는 대신 **입력에서 빼서 구조적으로 불가능하게** 만든다. 규칙은 잊히지만 없는 데이터는 쓸 수 없다.

두 축은 포함 관계가 아니라 **직교**다. 취향이 같아도 자금 흐름이 다르면 추천이 갈린다.

```text
둘 다 영화 32편을 본 사람 —
  A  급여 25일 규칙적(L1) · 큰 지출 없음(L4)   → 만기 긴 상품도 가능
  B  수입 불규칙(L1) · 분기마다 큰 지출(L4)    → 만기 짧은 상품·파킹통장
```

### 4.4 카드 추천 (FP-03)

취향 축이 상품 매칭에 쓰이는 **유일한 자리**다. 저축(FP-01)과 근거가 반대다.

| | FP-01 저축 | FP-03 카드 |
|---|---|---|
| 매칭 근거 | 자금 흐름 축 + 우대조건 | **취향 축 — 소비처별 혜택** |
| 상품 정보 | 금감원 오픈API (실데이터) | 카드사 자사 공시 수집 |
| 사용자에게 주는 것 | 실수령 예상 금리 | **예상 절약액** |

#### 왜 카드는 취향을 써도 되는가

저축에 취향을 쓰면 **없던 소비 목표를 만든다.** 카드는 반대로 **이미 하는 소비를 덜 나가게** 한다.

```text
X  "영화 좋아하시니 영화 적금 어떠세요?"        ← 목표를 새로 만든다 (R9 위반)
O  "이미 배달에 월 25만 쓰시는데, 이 카드면 연 9.6만 덜 나가요"
```

절약 서비스와 방향이 같다. 다만 선이 미묘해서 **표현을 강제한다.**

- 반드시 **사용자의 실제 소비 상위 카테고리**를 근거로 말한다(`회원님 지출 상위 2개 카테고리에 겹쳐요`).
- `이 카드로 배달 더 시키면 이득` 류의 **소비 증가를 전제한 문장은 금지**한다.
- 절약액은 **현재 소비를 그대로 유지했을 때**의 값이다. 늘렸을 때를 가정하지 않는다.

#### 절약액 계산

```text
예상 절약액 = Σ min(카테고리 월소비 × 할인율, 월 한도)      [전월실적 충족 시]
```

`카테고리 월소비`는 ③이 마이데이터에서 집계한 값(R10), 나머지는 카드 카탈로그 값이다.
전월실적을 못 채우면 혜택이 0이므로 **실적 충족 가능성도 함께 판정**한다.

#### 규제 — 저축보다 더 조심해야 한다

> 2021년 금융위·금감원은 플랫폼의 금융상품 비교·추천을 단순 광고가 아닌 **중개 행위**로 판단했고,
> **신용카드 추천도** `잠재고객 발굴·가입 유도 과정`으로 보아 문제 삼았다.

저축은 정보성 비교 예외(금융위·금감원 유권해석 2022.6.15)를 근거로 실 금리를 쓴다. **카드는 그 예외를 검증받은 적이 없으므로 더 보수적으로 간다.**

- 앱 안에서 발급·신청을 하지 않는다. `가입은 각 사로`.
- 제휴 링크·신청 폼·발급 편의 필드를 두지 않는다.
- 정렬은 **매칭 점수 순**이다. 광고비·제휴 순이 아니며, 화면에 그렇게 밝힌다.

#### 카탈로그 규모로 경쟁하지 않는다

카드 비교 서비스(예: 카드고릴라)는 카드사와 제휴해 1,500여 종을 유지한다. 수집으로는 그 규모를 따라갈 수 없고, 따라갈 이유도 없다.

```text
그들   1층(공시) + 2층(카드 혜택)          → "이 카드는 카페 5%"
우리   2층 + 3층(마이데이터 소비 흐름)     → "당신은 카페에 월 8만 → 연 4.8만"
```

**3층이 있어야 나오는 문장이 우리 자리다.** 카탈로그가 20~30장이어도 성립한다.

#### 데이터 출처

`scripts/collect-cards/` 참조. 요지만 적으면 —

- 여신금융협회 **카드다모아는 데이터 API가 403**이라 쓰지 않는다.
- **카드사 자사 공시** 중 `robots.txt`가 명시 허용한 곳만 수집한다(신한·KB·우리). **삼성은 `Disallow: /`라 제외**한다.
- 카드 부가서비스는 **3년 이상 유지 의무**가 있고 변경 시 **6개월 전 고지** 의무가 있다(신용카드 표준약관). 그래서 카탈로그가 빨리 낡지 않고, **재수집은 월 1회로 충분**하다.
- 혜택 문구를 우리 카테고리로 나누는 일은 자동화하지 않는다(§4.2 — 판단이 필요하다).

### 4.5 저축 상품 매칭 (FP-01) — M1~M9

자금 흐름 축(§4.1)을 실제 상품 추천으로 바꾸는 규칙이다. **판정·정렬은 규칙 엔진이 하고 LLM은 문장만 만든다**(R2).

> **2026-07-28 개정.** 기존 `kept_cv`(지킨 돈 변동성) 기반의 "정액 vs 자유" 분기는 폐기했다 — `kept_cv`는 실제 저축 여력이 아니라 **사용자의 챌린지 목표 변경 빈도**를 반영하는 경향이 있었다. 재정 안정성은 **AoM(Age of Money)** 으로 판단한다.
> 또 MOA의 지킨 돈은 매달 금액이 달라지고 덩어리로 들어와 정액적립식과 구조적으로 맞지 않으므로, 추천의 중심축은 **정액적립식 ↔ 자유적립식**이 아니라 **파킹통장 ↔ 자유적립식**이다.

#### AoM(Age of Money)

사용자의 자금 버퍼가 얼마나 두꺼운지를 재는 지표다. "지금 소득이 끊겨도 며칠 버티나"에 해당한다.

```text
AoM = 평균잔고 ÷ 월평균지출
```

| AoM | 의미 |
|---|---|
| 0.5 | 약 2주치 생활비 보유 |
| 1.0 | 약 1개월치 생활비 보유 |
| 3.0 | 약 3개월치 생활비 보유 |

AoM이 높을수록 당장 쓸 일이 없는 여유 자금이 많고, 낮을수록 유동성 확보가 급하다.

```text
AoM < θ_buffer   → 버퍼 얇음
AoM ≥ θ_buffer   → 버퍼 두꺼움
```

※ `θ_buffer`는 실데이터 검증 후 확정 — §8 미정.

#### 입력값

| 항목 | 변수 | 의미 | 출처 |
|---|---|---|---|
| 납입 규모 | `kept_mean` | 월 확정 지킨 돈 평균 | `finalized_kept_amount` 이력 |
| 안정성(버퍼) | `aom` | AoM(Age of Money) | `cash_buffer` |
| 유동성 필요도 | `large_expense_cycle` · `predictable` | 큰 지출 주기와 예측 가능 여부 | `recurring_payments` + 대규모 지출 |
| 우대조건 | `met` | 카드 실적·급여이체 충족 여부 | `preferential_material` × 사용자 데이터 |

#### 판단 로직

**M1. 상품 그룹 분류** — 적립 방식별로 분리해 제시한다: 파킹통장 · 자유적립식 · 정액적립식.
전체 상품을 하나의 순위표로 합치지 않는다. **그룹 순서 자체가 추천 결과가 되므로** 적립 방식을 먼저 가른다 (거울 원칙 — §1·§2).

**M2. 유동성 우선** — AoM 낮음(버퍼 얇음) · 또는 `predictable = false` · 또는 `large_expense_cycle`이 짧음 → **파킹통장 그룹 상단**.

**M3. 수익률 우선** — AoM 높음(버퍼 두꺼움) 그리고 큰 지출 예측 가능 → **자유적립식 그룹 상단**.

**M4. 정액적립식** — 항상 노출한다. 표시는 `매달 고정 금액 납입 필요`까지만.
금지 — `MOA 흐름과 맞지 않음` · `부적합` · `추천하지 않음` 같은 판단 표현. **적합 여부는 사용자가 정한다.**

**M5. 납입 규모 필터** — `kept_mean`으로 최소 가입금액·권장 납입금액 조건에 맞는 상품만 남긴다.
※ 규모는 **필터 기준일 뿐** 추천 방향을 정하지 않는다.

**M6. 실수령 금리 계산**

- 우대조건 모두 충족 → `effective_rate = max_rate`
- 하나라도 미충족 → `effective_rate = base_rate`

반영하는 우대조건은 **카드 실적 · 급여이체**. 자동이체는 더미에 해당 거래가 없어 제외한다. 조건별 부분 가산은 상품 데이터 파싱 신뢰가 확보된 뒤에만 적용한다.

**M7. 그룹 내 정렬** — 각 그룹 **내부에서만** `effective_rate` 내림차순. **그룹 간 우열은 매기지 않는다.**

**M8. 우대조건 표시** — 실수령 금리(`effective_rate`) · 최대 금리(`max_rate`) · 현재 미충족 우대조건을 함께 노출한다.

```text
실수령 금리 3.2%
(조건 충족 시 최대 4.0%)
현재 미충족
- 카드 실적
```

사실 정보만 준다. 가입 유도·행동 유도 표현은 쓰지 않는다 (R9).

**M9. 동점 처리** — 같은 그룹에서 `effective_rate`가 같으면 ① 미충족 우대조건 수가 적은 것 → ② 만기가 짧은 것 → ③ `base_rate`가 높은 것 → ④ 금융사명 가나다순.

#### LLM 역할 범위

LLM은 **상품 판정 · 그룹 분류 · 금리 계산 · 정렬 순서에 관여하지 않는다.** 생성하는 것은 `reason`과 `lifestyle_profile.narrative` 두 가지, 곧 설명 문장뿐이다.

#### 요약

AoM으로 자금 버퍼를 본다. 버퍼가 얇거나 큰 지출 변동성이 크면 → **파킹통장 우선**. 버퍼가 두껍고 지출이 예측 가능하면 → **자유적립식 우선**. 상품은 적립 방식별로 묶고, 묶음 안에서만 실수령 금리로 정렬한다. 정액적립식은 판단 없이 사실만 제공한다.

## 5. 취향 서술의 단계적 확장

취향은 한 번에 열지 않는다. **사실 → 패턴 → 취향** 순으로 넓힌다.

| 단계 | 서술 | 상태 |
|---|---|---|
| 사실 | "올해 영화 관련 소비가 32회 있었어요." | **MVP — 현재 여기까지** |
| 패턴 | "영화를 꾸준히 즐기는 편이네요." | 향후 |
| 취향 | "영화가 삶의 중요한 취미인 것 같아요." | 최종 |

MVP에서는 **취향 단정을 금지한다.** §3.3의 `올해의 영화 러버`는 집계 사실에 붙는 라벨이지 성향 단정이 아니다 — 32회라는 숫자가 함께 보이는 형태로만 쓴다.

## 6. 보류 — 은퇴(Retire)

초기 아이디어는 이랬다.

```text
"택시는 줄이기 어려운 필수 소비 같아요."  → 절약 후보에서 제외
```

**MVP에서 보류한다.** 시스템 판단이 들어가고, 잘못 분류될 위험이 있으며, 사용자가 평가받는 느낌을 받는다.

현재 허용 수위는 여기까지다.

```text
O  "택시는 최근 3개월 동안 큰 변화가 없었어요."
X  "택시는 줄이기 어려운 필수 소비예요."
```

그 이상의 의미 부여는 하지 않는다.

### 8.1 확신이 낮은 지점

매칭(§4.5)을 지으면서 확신이 낮다고 적어 둔 것들이다. 구현 전에 한 번씩 다시 봐야 한다.

| 지점 | 왜 불안한가 | 지금의 방어 |
|---|---|---|
| **실수령 금리 표현의 자문·중개 경계** | "실제로 받으실 수 있어요"가 자문·추천으로 읽힐 여지. 사실 서술로 한정하면 방어 가능하다고 보나 법무 확인 전까진 확신 낮음 | 사용자 **마이데이터 사실의 서술**까지만. "이 조건을 채우면 +0.x% 더 받아요"는 **행동 유도**라 R9 경계에 닿는다 → `○○ 조건은 아직 충족되지 않았어요` 같은 사실형까지, 명령형·페이스 금지. **법무 확인 대상**(③·법무) |
| **취소·환불이 `kept_mean`을 흔든다** | `kept_cv`는 폐기했지만 규모 지표 `kept_mean`은 여전히 취소·환불에 흔들린다 — 실데이터에서 환불 1건으로 월 총액이 음수가 됐다 | 규모 필터(M5)가 튈 수 있다. **취소 정규화 규칙 필요** |
| **L4의 1회성 지출 누락** | 고유 가맹점 284곳 중 75%가 1회성이고 금액의 44%를 차지한다. 반복 결제만으로 유동성(L4)을 잡으면 소비 절반이 빠진다 | "큰 1회성 지출" 포착 방식이 관건 — 반복성 기준만으론 부족 |
| **정액적립식 무판정 노출의 부작용** | M4가 판정을 안 붙이므로, 최고금리 상품이 정액이면 사용자가 구조 부적합을 모르고 고를 수 있다 | `매달 고정 금액 납입 필요` 사실 표시만으로 충분한지 **UX 검증 필요** (거울 원칙 vs 실질 도움의 긴장) |
| **(D) 조건별 가산금리의 실현성** | 출처가 우대조건을 자연어 `spclCnd`로만 준다. 조건별 `rate_bonus`는 파싱 산물이라 정확도 보장 불가 | 확정 사용은 **전부 충족=최고 / 미충족=기본** 이분까지(M6). 부분 실수령 금리는 파싱 신뢰 확보 전까지 보류 |

**구현계획 (§9~§15).** 위 §0~§8은 ③의 **설계**다. 아래는 그 설계를 **실제로 어떤 순서로 짓는지** — 현황·빌드순서·계약접점·레거시·프론트다. (옛 `14_취향 분석 및 추천` 구현계획을 여기로 합쳤다. ②는 거래 반응형이지만 ③은 *분석 → 산출물* 구조라 흐름을 그렇게 그린다.)

## 10. 어떤 순서로 만드나

각 단계에 **수용기준**(무엇이 되면 끝인가)을 붙인다. 앞 단계가 뒤 단계의 입력이다.

**0단계 ✅ (B) 소스 방식 결정 — 완료.** ①의 (B)가 아직 없어, 잔액을 마이데이터 계좌에서 직접 읽는 **B안**으로 풀기로 했다. 소비는 계속 카드로만 세므로 이중 계산이 없다(R7). `AccountFundFlowSource`가 L1·L3를 켰다.

**1단계 — ①에 나머지 재료 (B) 요청 → L2·L4·L5 켜기.** `fixed_expense_summary`·`recurring_payments`·`preferential_material`이 오면 같은 seam에 꽂는다. 판정 기계는 안 바꾸고 소스만 교체.
> *수용기준:* (B) 재료가 오면 L2·L4·L5도 UNKNOWN을 벗어난다.

**2단계 — 매칭 M1~M9 (저축 추천의 두뇌).** FundFlowProfile을 입력으로, AoM·L4로 파킹↔자유를 가르고 우대조건 충족으로 실수령 금리를 매긴 뒤 적립방식 그룹핑·그룹 내 금리순. (규칙은 §4.5, 판정은 코드·문장만 AI.)
> *수용기준:* 프로필이 다르면 추천 상품군이 갈린다. 규칙 단위 테스트 통과.

**3단계 — 저축 비교 교체·확장.** 옛 `SavingsCompareService`를 2단계 매칭에 연결하고 **예금(`depositProductsSearch`)을 조회에 추가**한다. 추천 대상 = 적금·예금·파킹 전부.
> *수용기준:* `GET /api/savings/compare`가 매칭 근거를 반영해 내려온다. 예금 포함.

**4단계 — 리포트 3층.** 옛 월간 리포트를 걷어내고 §3의 주간=관찰/월간=회고/연간=정체성으로 다시 짓는다. 소비 흐름은 ③ 직접 집계(R10), 금액은 ②의 (C) 값 그대로(R10).
> *수용기준:* 세 리포트가 각자의 주기·화법으로. 취향은 월간=집계 사실, 정체성 서술은 연간만(§3·§5).

**5단계 — 카드 추천 (FP-03).** 카드 공시 수집이 끝나면 취향 축으로 혜택 카드를 매칭한다(§4.4).
> *수용기준:* 소비처 상위와 혜택 카테고리가 맞는 카드가 상단에. *(선행: 카드 데이터 수집 완료 — 후순위)*

## 11. 계약 접점 — 누구에게 무엇을 받나

③은 혼자 다 계산하지 않고 다음을 **받아서** 쓴다.

| 출처 | 받는 것 | 쓰는 곳 | 상태 |
|---|---|---|---|
| **①의 (B)** | `income_profile`(L1)·`fixed_expense_summary`(L2)·`cash_buffer`(L3)·`recurring_payments`(L4)·`preferential_material`(L5) | 자금흐름 5축 | 🔴 미구현 → **L1·L3만 B안(계좌 직접)으로 임시 충당**, 나머지 대기 |
| **②의 (C)** | `securedSaving`·`achievementRate`·`daysLeft`·`state` | 리포트 금액·상태 (재계산 금지, R10) | 🟡 필드는 있으나 ③ 리포트 미연동 |
| **②의 이력** | `GET /api/guardian/challenges/history`(`securedSaving`·`endDate`) | L3 규모용 `kept_mean`·월간 회고 | 🔴 ②에 조회 신설 요청 (§0.2·§8) |
| **외부 (D)** | 금감원 상품(금리·`spclCnd` 자연어)·카드 공시 | 저축·카드 추천 후보 | 🟡 적금만 조회 중, 예금·카드 추가 예정 |
| **③이 내는 것** | `FundFlowProfile`(L1~L5) → 매칭 입력 · 리포트 산출물 (E) | 저축/카드 추천·리포트 | 🟢 프로필까지 · 매칭 이후 미구현 |

> **최대 블로커**: ①의 (B). 지금은 B안으로 L1·L3만 켰고, 나머지 축과 정공법 전환은 ①이 (B)를 채워야 완성된다.

## 13. 프론트 (frontend-moa)

**frontend-moa가 우리 기본 앱**이다. 옛 `frontend`의 `Report*`·`My*`(25개)는 ①개발자의 데이터 가시화 테스트베드일 뿐 ③ 타깃도 재사용 대상도 아니다. ③ 화면은 **frontend-moa에 처음부터** 짓는다(지금 0개, 그린필드).

| 신설 화면 | 대응(IA) | 비고 |
|---|---|---|
| 저축 추천 | FP-01/02 | 파킹↔자유 분기·실수령 금리 |
| 리포트 주간/월간/연간 | RP-01/02 + 연간 RP-07 | 3층 각각 |
| 취향(리포트 내) | §3.2/§3.3 | 월간=집계·연간=정체성 |

> **방식**: 실연동 전에는 mock으로 화면 뼈대 먼저 → 해당 단계 백엔드 준비되면 실데이터로 교체.

## 14. 구현 예외 / 엣지

§8(미정)이 "무엇을 아직 못 정했나"라면, 여기는 "지금 코드가 어떻게 처리하나"다.

| 상황 | 처리 |
|---|---|
| **소비 이중 계산** | 소비는 카드 승인내역만 센다. 계좌에선 잔액·급여만 읽고 출금 거래를 소비로 세지 않는다(R7) → 겹세기 원천 차단. |
| **콜드스타트** | AoM은 마이데이터로 가입 첫날부터 계산돼 안정성 콜드스타트는 완화(§4.1). 재료 없는 축은 `UNKNOWN`으로 두고 숨기지 않는다. |
| **우대조건 정밀 가산 불가 (D2)** | 금감원 API가 우대조건을 자연어 `spclCnd`로만 줌 → "전부 충족=최고금리 / 미충족=기본금리" 이분만 확정 사용. 부분 가산은 파싱 신뢰도 확보 후(§8). |
| **미분류(category2 없음)** | 취미·매칭에서 조용히 제외. 없는 신호를 지어내지 않는다(거울 원칙). |

## 15. 우리가 내린 결정 요약 (구현)

| 결정 | 내용 | 근거 |
|---|---|---|
| (B) 재료 조달 | **B안 — 잔액을 계좌에서 직접**(L1·L3), 나머지는 ①(B) 대기 | ①의 (B) 미구현. 소비는 카드로만 세므로 잔액 읽기는 이중 계산과 무관 |
| 추천 중심축 | "정액 vs 자유"가 아니라 **파킹통장 ↔ 자유적립식** | 지킨 돈이 매달 달라 정액적금과 구조적으로 안 맞음(§4.1) |
| 실수령 금리 | 우대조건 **전부 충족=최고 / 미충족=기본** 이분 | `spclCnd` 자연어라 조건별 정밀 가산 불가(D2) |
| 추천 대상 | 적금·예금·파킹(저축) + 카드 — 카드만이 아님 | 저축=자금흐름축, 카드=취향축(§4.4) |
| 옛 `RecommendService` | **폐기** | 취향으로 저축을 매칭하는 R9 위반 경로 |

> **아이디어**: N3(결제 전 카드 실적·한도 판단)는 L5(우대조건)와 **같은 재료**(카드사별 월 실적)를 쓴다 → 저축 우대 판정과 카드 실적 안내를 한 재료로 낼 수 있다.
