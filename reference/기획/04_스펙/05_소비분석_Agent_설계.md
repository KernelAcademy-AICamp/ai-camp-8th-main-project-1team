## 1. 이 Agent가 하는 일

거래 원자료를 **소비의 구조**로 바꾼다. 취향은 보지 않는다(③ 담당).

```text
마이데이터 카드 승인내역 (UserPayment)
        │
        ├─ Consumption(MYDATA)으로 투영 ──▶ A-1 공유 분석 엔진 ──┬─▶ A-6 단기 이상소비(FDS)
        │                                     (AnalysisResult)   ├─▶ ② 기준 지출·평균 결제액
        │                                                        └─▶ 리포트·소비건전성지수
        │
        └─ 원본 그대로 ──▶ A-2 반복 결제  ─┐
                          A-3 소비 패턴   ├─▶ A-4 소비 프로필(이상소비지수)
                          A-5 절약 후보   ─┘
                          A-7 낭비/필수 ML ──▶ 리포트·챌린지 후보

계좌 (잔액·급여만) ──▶ (B) 자금 흐름 재료 ──▶ ③   ※ 현재 ③이 직접 읽는다(§7.2)
```

| ID | 모듈 | 구현 | 단위 | 창 |
|---|---|---|---|---|
| A-1 | 카테고리 집계·과소비·장기 변동성 | `AnalysisEngine` | 대분류 | 전 기간 |
| A-1b | **기준 지출·평균 결제액** | `GuardianService.baselineFor` | **중분류**(변경 예정) | **최근 3개월**(변경 예정) |
| A-2 | 반복 결제 탐지 (고정형·루틴형) | `RecurringPaymentDetector` | 중분류 | 고정형 전 기간 · 루틴형 28일 |
| A-3 | 요일×시간대 패턴 | `PatternAnalyzer` | — | 90일(기본) |
| A-4 | 소비 프로필·이상소비지수 | `ProfileBuilder` | 대·중분류 | 90일(기본) |
| A-5 | 절약 후보·예상 절약액 | `CutCandidateSelector` | 중분류 | 90일(기본) |
| A-6 | 단기 이상소비 탐지(FDS) | `AnalysisEngine` + `AlertService` | 대분류 | 최근 1개월 vs 직전 3개월 |
| A-7 | 낭비/필수 판정 | `WasteScoringService` + `SpendingClassifier` | 중분류 | 전 기간 |

> 코드 주석의 `②③④⑤` 번호는 **Agent 번호가 아니라 분석 모듈 번호**다(마스터 문서 §5 계열). 이 문서에서는 Agent 번호와 충돌하지 않도록 `A-n`으로 부른다.

**하지 않는 것**: 카테고리 확정·절약 강도 확정·소비 목표 추천·취향 분석·금액 판정(② 소관).

## 2. 기준 지출 — ②가 쓰는 유일한 숫자

> **확정 (2026-07-29): 창은 최근 3개월, 단위는 중분류.** 정본(`avg_3m`)이 맞고 구현이 전 기간·대분류를 쓰고 있었다. 구현을 정본에 맞춘다.

```text
창             = referenceTime 기준 최근 3개월
카테고리 월평균 = 그 중분류의 창 내 합계 ÷ 3
기준 지출      = Σ(선택 중분류 월평균)
평균 결제액    = Σ(선택 중분류 합계) ÷ Σ(선택 중분류 건수)
```

②는 이 두 값으로 한도와 버퍼를 만든다(`11` §1·§1.1). **②는 다시 계산하지 않는다.**

```text
챌린지 한도 = 기준 지출 − 지킬 돈          (②)
버퍼        = min(0.20, 평균 결제액 / 한도) (②, 평균 결제액은 ①의 산출물)
```

### 2.1 무엇을 고쳐야 하나

현재 구현은 `Consumption`(대분류로 투영된 사본)을 **전 기간** 읽는다. 두 가지를 함께 바꾼다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 데이터 소스 | `Consumption`(대분류) | **`UserPayment.category2`(중분류)** |
| 창 | 보유 전 기간 | **최근 3개월** |
| 나누는 수 | 지출이 있던 달의 수 | **3 고정** |

> **소스를 `UserPayment`로 옮기는 이유.** `Consumption`은 대분류로만 투영돼 있어 중분류를 꺼낼 수 없다. 투영 자체를 중분류로 바꾸면 **같은 사본을 쓰는 과소비(비중 30%)와 이상소비 탐지가 함께 흔들린다** — 중분류는 훨씬 잘게 쪼개져 있어 어느 하나도 30%를 넘지 못하고, 그러면 과소비 판정이 사실상 죽는다. 기준 지출만 절약 후보와 **같은 소스·같은 층위**(`UserPayment`의 중분류)를 보게 하는 것이 안전하다. 후보와 기준이 같은 눈금을 쓰게 되는 부수 효과도 있다.

> **콜드스타트는 백로그다 (2026-07-29 결정).** 관측 3개월 미만인 신규 사용자는 3으로 나누면 기준 지출이 실제보다 낮게 잡힌다. MVP는 3개월 이상 이력이 있는 더미로 시연하므로 드러나지 않으며, **MVP 개발 이후 과제**로 뺀다.

> **함정 — 이상치를 제거하지 않는다.** 단순 산술평균이라 한 건의 고액 결제가 기준 지출을 그대로 끌어올린다. 창이 3개월로 짧아지면 **한 건의 영향이 오히려 커진다.** 중앙값·절사평균 비교는 `07` §8 미정 항목으로 남아 있다.

## 3. 카테고리 — 층위와 분류의 현실

### 3.1 우리는 카테고리를 분류하지 않는다

PRD §10.2는 `1차 키워드 사전 → 2차 ML 텍스트 분류 → 3차 LLM`의 3단 구조를 규정했다. **구현되지 않았고, 지금 구조에서는 필요하지도 않다.**

마이데이터 제공자(`backend-mydata`)가 결제마다 `category1`(대분류)·`category2`(중분류)를 **이미 붙여서 준다.** 백엔드는 그 값을 그대로 적재한다(`MyDataLinkService`). 실제 카드사 마이데이터도 가맹점 업종을 함께 내려주므로 이 구조 자체는 비현실적이지 않다.

분류가 실제로 필요한 자리는 **하나뿐**이다.

```text
PG 결제   가맹점명 = "토스페이먼츠" · category1 = "온라인" · category2 = "미분류"
          → 무엇을 샀는지 알 수 없다 (UnknownPgPaymentRunner, 사용자별 1~8주 간격 주입)
```

현재 처리는 **판정에서 제외**다.

| 모듈 | 미분류 처리 |
|---|---|
| A-5 절약 후보 | 3등급 어디에도 없으므로 후보에서 뺀다(보수적) |
| A-7 낭비/필수 ML | 판정하지 않고 집계에서도 뺀다 |
| A-1 기준 지출 | `category1 = 온라인`으로 **집계에는 들어간다** |

> **미분류를 낭비로도 필수로도 찍지 않는 이유**는 정확도가 아니라 태도다. 무엇을 샀는지 모르는 결제에 성격을 붙이면 사용자는 근거 없이 평가받는다. `12` §2.1과 같은 원칙이다.

### 3.2 ②의 C7이 발화하지 않는다 — 확인 필요

`11` §3의 **C7(분류 신뢰도 0.70 미만 → 되묻기)** 은 미분류 결제를 사용자에게 물어보는 자리인데, 현재 발화하지 않는다.

```text
GuardianService.syncFromMyData
  → ingest(..., categoryConfidence = 1.0, ...)   ← 항상 1.0으로 고정
```

카테고리가 제공자에게서 확정돼 오므로 신뢰도라는 개념이 없어서 1.0을 넣은 것인데, 결과적으로 `미분류` 결제도 신뢰도 1.0으로 집계된다. 되묻기가 필요한 유일한 케이스가 되묻기를 통과해 버린다.

**제안**: `category2 == "미분류"`일 때 `categoryConfidence`를 `null` 또는 임계 미만으로 넣는다. ①이 한 줄, ②는 손대지 않아도 된다. **②(윤정) 합의 필요.**

### 3.3 챌린지는 중분류로 간다 (2026-07-29 확정)

| | 대분류 `category1` | 중분류 `category2` |
|---|---|---|
| 예 | 식비 · 교통 · 온라인 | 카페 · 배달 · 택시 · 스트리밍 |
| 쓰는 곳 | 과소비 · 이상소비 탐지(A-6) | **기준 지출 · ②의 선택 카테고리** · 반복 결제(A-2) · 절약 후보(A-5) · 낭비 ML(A-7) |

**"식비를 줄이자"는 행동으로 옮길 수 없고 "배달을 줄이자"는 옮길 수 있다.** 챌린지가 행동 교정을 목표로 하는 이상 대상은 중분류여야 한다.

#### 문서는 원래 맞았고 구현만 어긋나 있었다

`11` §5.1과 `07` (C)의 예시는 처음부터 `배달`·`카페` — **중분류**였다. 어긋난 것은 구현 한 곳이다.

```text
CutCandidateSelector   UserPayment.category2  →  카페 · 배달        (중분류) ✅
GuardianService        Consumption.category   →  식비 · 교통        (대분류) ❌
                       .baselineFor(categories)
```

그래서 AN-01이 보여준 `배달`을 그대로 챌린지에 넣으면 기준 지출 조회가 **빈손으로 돌아온다.** 지금 터지지 않은 이유는 MOA 온보딩이 아직 챌린지 생성 API를 부르지 않고 로컬 상태만 세팅하기 때문이다. 붙이는 순간 `이 카테고리의 소비 이력이 없어 기준 지출을 잡을 수 없어요`(400)가 난다.

#### 고칠 곳은 ① 한 군데다

②의 스키마·화면·산수는 그대로 둔다. `baselineFor`가 보는 소스를 `Consumption`(대분류)에서 `UserPayment.category2`로 옮기면 된다 — §2.1.

과소비(비중 30%)와 이상소비 탐지는 **대분류로 남긴다.** 중분류로 내리면 어느 항목도 전체의 30%를 넘지 못해 판정이 죽는다.

## 4. 모듈별 판정 규칙

임계치는 **전부** `application.yml`(`finntech.analysis.*`)에 있다. 아래 값은 현재 설정값이다.

### 4.1 A-1 공유 분석 엔진

하나의 `AnalysisResult`를 세 갈래가 재사용한다(마스터 §4 원칙 2). 소비자는 임계치를 다시 계산하지 않는다.

| 산출 | 규칙 |
|---|---|
| 카테고리별 합계·비중·건수 | 대분류 단위 |
| 표본 충분 여부 | 건수 ≥ `10` |
| 과소비 카테고리 | 지출 비중 > `0.30` |
| 지출 비중 내림차순 | 동률은 코드 오름차순으로 깨 **순서를 결정적으로** 만든다 |
| 장기 변동성 | 월별 총지출의 변동계수(CV) · 관측 월수 ≥ `3` |
| 월별 총지출 | `yyyy-MM` → 금액 |

> **`cv-cap`을 0.6에서 1.5로 완화한 이력.** 재생성 데이터는 시작월이 부분월이라 CV가 과대계상돼(≈0.59) 안정성이 0으로 뭉개졌고, 소비건전성지수가 전원 C·D로 몰렸다. 값 하나로 끝내려고 임계치를 설정값으로 분리해 둔 것이다.

### 4.2 A-2 반복 결제 탐지

두 종류를 나눈다. **성격이 다르면 다르게 잡아야 한다** — 통신비와 아침 커피는 같은 규칙으로 안 걸린다.

| | 고정형 FIXED | 루틴형 ROUTINE |
|---|---|---|
| 뜻 | 같은 가맹점에서 같은 금액·같은 주기 | 같은 중분류·같은 시간대에 반복 |
| 그룹키 | (중분류, 가맹점) | (중분류, 시간대) |
| 가맹점 식별 | **사업자번호 우선**, 없으면 표시명 | 무관 |
| 최소 발생 | 서로 다른 날 `3`회 | 창 내 `3`일 |
| 금액 조건 | 금액 CV < `0.05` | MAD ÷ 중앙값 ≤ `0.35` |
| 주기 조건 | 평균 간격이 `6~8`일(주간) 또는 `27~33`일(월간) | — |
| 규칙성 조건 | 간격 표준편차 ÷ 평균 ≤ `0.30` | 등장 비율 ≥ `0.25` (28일 창) |
| 산출 | 대표금액(중앙값)·주기·**다음 예상일** | 대표금액·주당 빈도 |

**사업자번호를 먼저 쓰는 이유**는 표기 노이즈 때문이다. `스타벅스 강남2호점`과 `스타벅스강남2`는 다른 문자열이지만 같은 가맹점이고, 표시명으로 묶으면 3회를 못 채워 고정형이 통째로 사라진다.

**고정형은 절약 후보에서 빠진다**(보호 카테고리와 별개로, 조정 불가능한 지출이라 후보로 제시하면 무의미하다). AN-01은 이를 `못 줄여요` 칩으로 분리해 보여준다.

### 4.3 A-3 소비 패턴

요일 × 시간대 히트맵과 최대 지출 칸(peak).

```text
심야  hour ≥ 23 또는 hour ≤ 4
아침  (4, 11)
점심  [11, 17)
저녁  [17, 23)
```

이 정의는 **A-2 루틴형과 A-3이 공유하는 단일 출처**다(`AnalysisProperties.Daypart`). 두 곳에 따로 두면 "저녁에 반복되는 소비"와 "저녁 지출 비중"이 서로 다른 시간을 가리키게 된다.

> **심야 정의가 두 개다.** A-6 FDS의 심야는 `[0, 6)`이고 여기와 ML 피처는 `[23, 4]`다. FDS는 "새벽 고액 결제"라는 다른 현상을 잡으므로 의도된 분리이지만, 사용자에게 두 정의가 동시에 보이면 설명이 어긋난다. 화면 문구에 심야를 노출할 때는 어느 정의인지 확인할 것.

### 4.4 A-4 소비 프로필 — 이상소비지수

**충동 구매 지수의 실제 구현체**다. (B)의 `impulse_index`가 이 값이다.

```text
이상소비지수 = 100 × Σ(가중치 × 성분)      성분은 각각 [0,1]
```

| 성분 | 정의 | 가중치 |
|---|---|---:|
| 낭비비율 | 제거가능 중분류 지출 ÷ 총지출 | 0.40 |
| 과소비집중 | 최대 대분류 지출 비율 | 0.25 |
| 지출변동성 | 월지출 CV ÷ `cv-cap` (clamp) | 0.15 |
| 심야충동 | (심야 지출 + 루틴형 낭비지출) ÷ 총지출 (clamp) | 0.20 |

**성분별 기여 점수를 함께 낸다**(합 = 지수). 블랙박스 점수를 주지 않는 것이 마스터 §4 원칙 1의 요구다 — "판단은 설명가능한 모델이".

> 심야 지출과 루틴형 낭비지출은 **겹칠 수 있다**(심야에 반복되는 배달). 분모가 총지출이라 합이 1을 넘을 수 있어 clamp한다. 겹침을 빼지 않는 것은 "심야이면서 습관"인 소비를 더 무겁게 보겠다는 선택이다.

### 4.5 A-5 절약 후보

중분류를 3등급으로 나눈다. **등급은 설정값**이고 코드에 카테고리 이름이 없다(마스터 §4 원칙 4).

| 등급 | 목록 | 절감액 |
|---|---|---|
| 제거가능 REMOVABLE | 카페 · 배달 · 스트리밍 · 백화점 · 면세점 · 간편결제 | **전액** |
| 최적화가능 OPTIMIZABLE | 한식 · 중식 · 일식 · 양식 · 분식 · 대중교통 · 택시 | **중앙값 초과분의 합** |
| 보호 PROTECTED | 공과금 · 통신비 · 약국 · 보험 | 후보에서 원천 제외 |
| (미등재) | 그 외 전부 | 후보 아님(보수적) |

```text
최적화가능 절감액 = Σ max(0, 결제액 − 그 카테고리 중앙값)
```

**중앙값 초과분만 잡는 이유**는 식비·교통을 0으로 만들 수 없기 때문이다. "평소만큼 쓰되 유난히 비쌌던 몫만" 줄이자는 제안이 된다.

정렬은 절감액 내림차순, 동점은 이름 사전순(결정론).

> **함정 4 — `monthlySpend`는 월 지출이 아니다.** 필드 이름과 달리 **창(기본 90일) 전체 합계**다. AN-01이 이 값을 `월 {금액}`으로 표시하고 있어 화면에 **약 3배로 나온다**. 필드명을 `windowSpend`로 고치거나 프론트가 `÷ (days/30)`을 하거나 둘 중 하나가 필요하다 — §10.

> **보호 목록은 ML의 `ESSENTIAL` 집합과 독립이다.** 값이 겹칠 수 있지만 한쪽을 고쳐도 다른 쪽은 안 바뀐다. ML 쪽은 학습 시점 정의라 함부로 못 바꾸고, 이쪽은 운영 중 조정 대상이라 분리했다.

#### 등급을 데이터로 정한다 (2026-07-29 결정 · 미구현)

지금의 3등급은 **사람이 yml에 적어둔 고정 목록**이다. 데이터를 보지 않으므로 두 가지 문제가 있다.

```text
목록에 없는 중분류  → 조용히 후보에서 빠진다 (그 사용자가 실제로 많이 쓰는 곳이어도)
목록에 있는 중분류  → 그 사용자에게 낭비가 아니어도 후보로 올라온다
```

**재료는 이미 있다.** 낭비 ML이 거래마다 낭비 여부를 판정하고 그 결과에 중분류가 붙어 있다(§5). 지금은 그 결과를 **대분류로만 합산**해 리포트에 쓰고, 절약 후보는 ML을 전혀 보지 않는다. 합산 바구니를 중분류로 하나 더 만들면 이어진다.

```text
현재   거래별 낭비 판정 ──▶ 대분류 합산 ──▶ 1차 앱 리포트
                        └─✕ 절약 후보 (고정 목록만 본다)

이후   거래별 낭비 판정 ──┬─▶ 대분류 합산 ──▶ 리포트
                        └─▶ 중분류 합산 ──▶ 절약 후보 게이트
```

`finntech.analysis.cut-candidate.waste-ratio-threshold`가 **바로 이 게이트용으로 예약된 값**이다(주석: `후속 EBM 낭비확률 게이트로 예약`). 지금 호출자가 없다.

세 등급의 역할은 바꾸지 않는다 — **어느 중분류가 어느 등급인지를 목록이 아니라 낭비 비율로 정하는 것**이다. 보호 등급만은 목록으로 남긴다. 공과금·통신비를 데이터로 판단하게 두면 "이 사람은 통신비 비중이 높으니 줄이자"가 나올 수 있고, 그건 조정 불가능한 지출이다.

> **임계는 다시 잡아야 한다.** 대분류용 `0.35`를 중분류에 그대로 쓰면 안 된다. 중분류는 잘게 쪼개져 있어 낭비 비율이 0 또는 1에 몰린다(`배달`은 거의 전부 낭비, `약국`은 거의 전부 필수). 분포를 보고 역산한다 — §6.2와 같은 방식.

### 4.6 A-6 단기 이상소비 탐지 (FDS)

```text
Modified Z = 0.6745 × (log(금액) − 중앙값) / MAD        임계 3.5
최종 경고  = Z 플래그 AND 룰 1개 이상 일치
```

| 구간 | 정의 |
|---|---|
| 평가 구간 | 최근 `1`개월 |
| 기준 분포 | 그 직전 `3`개월 — **평가 구간과 겹치지 않는다** |

**겹치면 이상치가 자기 기준을 끌어올려 탐지가 무뎌진다.**

| 룰 | 조건 |
|---|---|
| 심야 고액 | 시각 ∈ `[0,6)` **且** 금액 ≥ 기준 중앙값 × `2.0` |
| 신규 카테고리 급증 | 기준 구간 건수 ≤ `2` |
| 빈도 이탈 | 최근 건수 > 기준 월평균 건수 × `2.0` |

**단일 조건으로 판정하지 않는 이유**: 금감원 공개 시나리오가 조건을 AND로 묶는 구조이고, 단일 조건이면 오탐이 도배된다.

세 가지 방어 장치가 더 있다.

- **로그를 취한다.** 금액은 로그정규에 가까워 원값에 z를 걸면 고액이 전부 이상치가 된다.
- **평균·표준편차가 아니라 중앙값·MAD를 쓴다.** 이상치 자체가 통계량을 오염시키지 않게 한다.
- **표본이 부족한 카테고리는 전체 분포로 대체한다(GLOBAL).** 그냥 건너뛰면 신규 카테고리는 z를 못 내고, 그러면 `신규 카테고리 급증` 룰이 **영원히 발화하지 못한다.** 경고 문구에 어느 분포로 쟀는지(`같은 카테고리의 평소 지출` / `회원님 전체 평소 지출`) 밝힌다.
- **MAD가 0이면** 평균절대편차로 대체하고, 그것도 0이면 0을 반환한다. 이 처리를 빼면 균일한 카테고리에서 `Infinity`가 나와 전건이 경고로 뜬다.

## 5. 낭비/필수 판정 — 규칙에서 해석가능 ML로

### 5.1 왜 바꿨나

정본의 낭비 판정은 `지출 비중 30% 쏠림`이라는 규칙이었다. 카테고리 단위라 **같은 카테고리 안의 차이를 못 본다** — 점심 8,000원과 새벽 배달 42,000원이 같은 판정을 받는다.

교체 대상은 **모델의 종류가 아니라 판정의 단위**다. 그래서 블랙박스가 아닌 **EBM(Explainable Boosting Machine)** 을 쓴다. 순수 가법 모델이라 특징별 기여를 그대로 꺼낼 수 있다.

```text
낭비 로그오즈 = 절편 + Σ(특징별 구간 기여값)     →  시그모이드  →  낭비 확률
```

마스터 §4 원칙 1의 개정 방향(`판단은 설명가능한 모델(규칙 또는 해석가능 ML)이`)과 같은 자리다. LLM은 여전히 판정하지 않는다.

### 5.2 특징 11개

```text
cat2 · log_amount · hour_sin · hour_cos · night · dow_sin · dow_cos ·
weekend · amt_vs_typical · user_mean_log_amount · user_disc_ratio
```

- 시각·요일은 **sin/cos 쌍**으로 넣는다. 23시와 0시가 24만큼 떨어진 값이 되지 않게 하려는 것이다(원형 변수).
- `amt_vs_typical` = 결제액 ÷ 그 사용자의 그 카테고리 중앙값 (상한 20). **같은 금액도 사람마다 다르게 읽힌다.**
- 사용자 단위 집계(`user_*`)는 라벨을 쓰지 않으므로 누수가 아니다.

Python 학습 결과를 **형상함수 테이블(JSON)** 로 내보내 Java가 읽는다. 재현 오차 ~1e-16을 테스트로 고정했다(`ModelParityTest`). 정적 아티팩트라 추론이 결정론이다.

### 5.3 개인화 override

사용자가 중분류를 "나에겐 필수/낭비"로 지정하면 **그 사용자에 한해 모델 판정을 덮어쓴다.**

```text
통념상 낭비여도 본인 취미·필수면 보호한다.
```

override는 개인정보 파기 흐름에 포함된다(`PrivacyService`).

### 5.4 다운스트림 요약 — 판정과 합산은 층위가 다르다

**판정은 거래 한 건 단위**다. 그 결과를 어느 바구니에 담아 합산하느냐가 그다음 문제이고, 지금은 바구니가 대분류 하나뿐이다.

```text
1단계 판정   거래마다 낭비 확률 → 임계 넘으면 낭비    (결과에 중분류가 붙어 있다)
2단계 합산   결과를 대분류로 묶는다                   ← 여기서 중분류가 버려진다
3단계 사용   낭비 비율 ≥ 0.35인 대분류를 고른다        (1차 앱 절약 리포트만 쓴다)
```

```text
배달 32,000  낭비 ○  ┐
배달 28,000  낭비 ○  ├─▶ 대분류 "식비" 낭비비율 41% → 줄이면 좋은 소비
한식  9,000  낭비 ✕  │
분식  6,500  낭비 ✕  ┘

※ "배달은 100% 낭비, 한식·분식은 0%"라는 사실이 합산에서 사라진다
```

| 산출 | 정의 |
|---|---|
| `essentialRatio` | 필수 판정 금액 ÷ 총금액 → 소비건전성지수의 `계획소비비율` 항을 대체 |
| `wasteCategories` | **대분류** 지출 중 낭비 비율 ≥ `0.35`인 집합 → 리포트의 `줄이면 좋은 소비` |
| `wasteRatioByCategory1` | 대분류별 낭비 비율 |
| 🆕 **중분류별 낭비 비율** | **미구현.** 절약 후보 등급 판정에 쓴다 — §4.5 |

> **임계 0.35의 근거.** 처음에는 `0.5`(과반)가 코드에 박혀 있었는데, 실측하니 절약형 사용자는 최대 카테고리도 35~41%에 그쳐 **후보가 0개**가 됐다(10명 중 3명). 절약 리포트가 "줄일 게 없다"고 말하고 챌린지 추천도 비었다. 판정 단위를 카테고리에서 거래로 옮기며 기준이 훨씬 엄해진 것이 원인이라, 규칙 시절 강도(전체 대비 30% 쏠림)와 비슷하게 맞췄다.

**모델이 없으면 조용히 규칙으로 떨어진다.** `SpendingClassifier.isReady() == false`면 요약이 비고, 상위는 규칙 baseline(`overspending`·`planned`)을 쓴다. 규칙 FDS(A-6)는 폐기되지 않고 병존한다.

## 6. 신뢰도와 데이터 부족

### 6.1 모르는 것을 모른다고 말한다

| 표시 | 조건 |
|---|---|
| `CONFIRMED` | 직접 입력 `30`건 이상 **且** 최초 입력으로부터 `14`일 이상 |
| `ESTIMATED` | 그 외 — 부족한 건수·일수를 문구로 함께 낸다 |

건수만 보면 하루 몰아쓰기로 통과하므로 **건수 AND 기간**이다.

`volatilityMeasured`는 이와 별개의 플래그다. 관측 월수가 `3` 미만이면 변동성을 **재지 않았다**고 표시한다.

> 이 플래그가 없으면 "변동성 0(완벽히 안정적)"과 "변동성을 잴 수 없음"을 구분하지 못한다. 그러면 데이터가 적은 사용자가 안정성 만점을 받아 **기록을 적게 할수록 점수가 높아진다.**

> **마이데이터 연동 사용자는 즉시 CONFIRMED다.** 판정이 `USER_INPUT` 건수만 보므로, `MYDATA` 소스만 있는 계정은 "더미만 있는 계정"과 같은 분기로 들어간다. 마이데이터가 주 입력이 된 지금은 이 조건을 다시 볼 필요가 있다 — §10.

### 6.2 임계치는 최적화가 아니라 제약 충족으로 정한다

FDS 임계치는 `CalibrationService.sweep`으로 역산한다.

```text
목표: 더미 100건 중 경고 3~5건
방법: 임계치를 스윕하며 경고율을 재고, 목표 구간에 드는 첫 값을 고른다
```

**데모에서 경고가 도배되면** *"이거 그냥 다 잡는 거 아니냐"* 는 질문을 받고 발표 주인공 기능이 그 자리에서 무너진다. 현재 3.5는 잠정값이며, 페르소나가 확정되면 그 분포로 다시 돌려 `finntech.analysis.fds.modified-z-threshold` 한 줄만 바꾼다.

> 스윕은 전역 설정값을 잠시 바꾸므로 동시 요청과 경쟁한다. 개발·관리자 경로에서만 부른다.

## 7. 연결부의 실제 구현 상태

### 7.1 (A) ① → ② — 스키마가 아니라 함수다

문서상 (A)는 배치·이벤트로 발행되는 JSON이지만, 실제로는 ②가 `AnalysisEngine.analyze()`를 **직접 호출해** 기준선을 파생한다.

```text
GuardianService.baselineFor(userId, categories, now)
  → analysisEngine.analyze(userId, now)
  → 선택 카테고리의 월평균 합 + 평균 결제액
```

같은 프로세스라 스키마 직렬화가 불필요했고, 원칙 2(하나의 결과를 재사용)에도 부합한다. 다만 **(A)의 다른 필드는 아무도 만들지 않는다.**

| (A) 필드 | 상태 |
|---|---|
| `categories[].baseline` | ✅ `baselineFor`가 파생 |
| `baseline_method` | ⚠️ 실제는 `avg_all` (정본 `avg_3m` 개정 대상) |
| `recommended_to_cut` · `recommended_intensity` | ❌ 미산출. §7.3 참조 |
| `reason` | △ A-5의 `reason`이 대응하나 중분류 단위 |
| `confidence` | ❌ 미산출 |
| `fixed_expenses[]` | △ A-2 고정형이 대응. `day_of_month` 대신 `주기(일)`·`다음 예상일` |
| (없음) `평균 결제액` | ⚠️ ②가 쓰는데 스키마에 없다 |

### 7.2 (B) ① → ③ — 미발행, ③이 우회 중

(B)는 발행되지 않는다. ③의 `FundFlowService`는 계약(`FundFlowInputs`)만 잡아두고, 구현(`AccountFundFlowSource`)이 마이데이터 계좌를 **직접** 읽는다.

| 축 | 현재 |
|---|---|
| L1 소득 | ✅ 계좌의 급여·급여일 |
| L3 안정성 | ✅ 현재 잔액 ÷ 카드 월평균지출 (평균잔고의 간이 대용) |
| L2 고정비 · L4 큰지출 · L5 우대조건 | ❌ `UNKNOWN` — ①의 (B) 대기 |

**R7은 지켜진다.** 계좌에서 읽는 것은 잔액(스냅샷)과 급여뿐이고 지출은 카드로만 센다. 다만 `12` §4.1의 서술(`③은 계좌 원본을 만질 수 없다`)과 코드가 어긋나므로 문구 정합이 필요하다.

**①이 채워야 할 것**: `fixed_expense_summary`(A-2 고정형 합계로 산출 가능) · `recurring_payments`(A-2 그대로) · `preferential_material`(카드사별 실적 — `UserPayment.cardCode` → `UserCard.companyName`) · `cash_buffer`의 평균잔고(기간 평균 산출 방법 미정).

### 7.3 권장 강도는 ①이 내지 않는다

정본은 ①이 `recommended_intensity`를 제안한다고 적었지만, 실제 기본값은 ②에 있다.

```text
targetSaving == null  →  기준 지출 ÷ 3   (≈ 33%)
```

**①이 강도를 제안하려면 근거가 있어야 한다.** 자연스러운 근거는 절약 후보의 `예상 절감액 ÷ 기준 지출`이다. 층위를 중분류로 통일하기로 했으므로(§3.3) 이 나눗셈이 **같은 눈금 위에서 성립한다** — 두 값이 같은 중분류의 같은 3개월 창을 보게 되기 때문이다. 층위·창 정정이 끝나면 붙일 수 있다.

### 7.4 (F) 재분류 · (G) 종료 실적 — 둘 다 미구현

| 연결 | 상태 |
|---|---|
| (F) ①→② 재분류 | ❌ 카테고리 재분류 경로 자체가 없다. `UserSpendingOverride`는 **낭비/필수** 재지정이지 카테고리 변경이 아니다 |
| (G) ②→① 종료 실적 | ❌ ②가 챌린지를 정산하지만 ①에 넘기지 않는다. 정본 (G)도 옛 금액 모델 그대로 미개정 |

R6(다음 챌린지 분석은 종료 마감을 기다린다)은 **현재 강제되지 않는다.** ①의 분석은 항상 최신 데이터로 재계산되므로 게이팅이 없어도 값이 틀리지는 않지만, 맥락 태그·오분류율을 다음 제안에 반영하는 경로는 없다.

## 8. 화법 — 판단은 코드가, 표현은 AI가

### 8.1 순서

```text
규칙 엔진이 숫자와 판정을 전부 끝낸다
  → 코드가 폴백 문장(reason)을 먼저 완성한다
    → 그 문장을 LLM이 다듬는다
```

LLM은 **계산도 판정도 추정도 하지 않는다.** ②(`11` §7)와 같은 구조다.

### 8.2 외부 AI에는 집계 수치만

개인 소비 기록 원문을 보내지 않는다. 실제로 전송되는 것은 카테고리명·집계 금액·비율·지수뿐이다. 개인정보 처리방침 5번의 요구이자, 원칙 1을 지키면 자연히 충족된다.

### 8.3 폴백은 조용히

API 키가 없거나 호출이 실패하면 템플릿으로 떨어진다. 응답에 `source`를 실어 **무엇이 생성했는지 밝힌다**.

```text
AI                LLM이 생성
TEMPLATE          키 없음 — 처음부터 템플릿
TEMPLATE_FALLBACK 호출 실패 — 템플릿으로 회수
```

### 8.4 금지 표현

`07` §6과 `12` §7을 그대로 따른다. ① 고유의 금지 두 가지를 더한다.

| 금지 | 이유 |
|---|---|
| `줄이면 좋은 소비 중 1등`을 `전체에서 가장 큰 비중`으로 말하기 | 실제로 쇼핑 0.4% 하나만 후보인 사용자에게 `쇼핑이 전체의 0.4%로 가장 큰 비중`이라는 문장이 나갔다. **무엇들 중의 1등인지 밝힌다** |
| 미분류(PG) 결제에 성격 붙이기 | 무엇을 샀는지 모르는 결제를 평가하지 않는다 (§3.1) |

카테고리 이름의 받침 유무로 조사가 흔들리지 않게, 템플릿은 `{카테고리} 지출이`처럼 **받침 있는 명사로 받아** 조사를 고정한다.

## 9. 재현성

- 엔진은 **어디서도 현재 시각을 직접 읽지 않는다.** `Clock` 주입 + `referenceTime` 파라미터.
- 모든 조회는 정렬이 고정돼 있다(`order by occurredAt, id` · `paymentDate desc`).
- 모든 그룹핑은 `TreeMap` — 키 순회 순서가 결정적이다. 동점은 사전순으로 깬다.
- ML 추론은 정적 테이블 기반이라 결정론이다.
- 순수 함수 코어(`selectFrom` · `analyzeFrom` · `detectFrom` · `buildFrom`)를 저장소 없이 단위 테스트한다.
- 임계치는 전부 `application.yml`. **카테고리 이름은 코드에 등장하지 않는다** — 페르소나가 바뀌어도 엔진을 다시 만들지 않기 위해서다.
