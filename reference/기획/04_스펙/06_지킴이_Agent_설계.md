## 1. 핵심 산수

```text
챌린지 한도 = 기준 지출 − 지킬 돈
남은 한도   = 한도 − 집계 지출
확보 절약액 = min(지킬 돈, max(0, 기준 지출 − 집계 지출))
방어율      = 확보 절약액 / 지킬 돈
```

기준 지출은 ① 분석이 낸 카테고리 월평균의 합이다. ②가 다시 계산하지 않는다.

> **카테고리는 중분류다 (2026-07-29 확정).** `카페`·`배달`이지 `식비`가 아니다 — **"식비를 줄이자"는 행동으로 옮길 수 없고 "배달을 줄이자"는 옮길 수 있다.** §5.1과 `02_에이전트_연결부.md` (C)의 예시가 처음부터 중분류였으므로 **이 문서와 ②의 스키마는 바뀌지 않는다.** 다만 구현의 `baselineFor`가 대분류로 조회하고 있어 ①이 소스를 옮긴다 — `05_소비분석_Agent_설계.md` §2.1·§3.3.
>
> 창도 **최근 3개월**로 확정했다(정본대로). 관측 3개월 미만인 신규 사용자 처리는 MVP 이후 백로그다.
>
> **아직 터지지 않은 이유**는 MOA 온보딩이 챌린지 생성 API를 아직 부르지 않기 때문이다. 붙이는 순간 `이 카테고리의 소비 이력이 없어 기준 지출을 잡을 수 없어요`(400)가 난다.

### 1.1 페이스와 버퍼

```text
페이스 비율 = 판정 대상 일차 / 총 일수
허용 비율   = 페이스 비율 + 버퍼
버퍼        = min(0.20, 평균 결제액 / 한도)   (데이터 없으면 0.15)
```

버퍼가 있는 이유는 **결제 한 건이 곧바로 페이스를 깨면 안 되기** 때문이다. 그 사용자의 평소 한 건 크기만큼을 여유로 준다. 배달(단가 큼)은 버퍼가 넓고 카페(단가 작음)는 좁아진다.

> **함정**: `판정 대상 일차`는 오늘이 아니라 **판정하는 날짜** 기준이다. 새벽 배치에서 전날을 판정할 때 오늘 기준으로 계산하면 허용 비율이 하루치(1/총일수)만큼 커져 판정이 뒤집힌다. 같은 60,000원 지출이 7일차 기준으로는 페이스 초과, 8일차 기준으로는 페이스 이내가 된다.

## 2. 일 판정

하루를 세 갈래로 나눈다.

| 그날 집계 결제 | 지출 비율 | 판정 | 사물 |
|---|---|---|---|
| 0건 | — | `NO_SPEND_DAY` | 지급 + 희귀 확률 보너스 |
| 1건 이상 | ≤ 허용 비율 | `ON_PACE_DAY` | 지급 |
| 1건 이상 | > 허용 비율 | `OFF_PACE_DAY` | 미지급 |

**미지급은 지출한 날에만 생긴다.** 참는 날은 언제나 보상받으며, 한도를 초과한 사용자도 무지출 날이면 계속 받는다 — 사물은 벌이 아니다.

정산 중(`SETTLING`)이거나 아직 시작 전(`SETUP`)이면 판정하지 않는다.

### 2.1 등급 확률

| 상황 | COMMON | RARE | EPIC |
|---|---:|---:|---:|
| 페이스 이내 | 0.85 | 0.14 | 0.01 |
| 무지출 1~2일 | 0.70 | 0.25 | 0.05 |
| 무지출 3~6일 | 0.60 | 0.32 | 0.08 |
| 무지출 7일 이상 | 0.50 | 0.38 | 0.12 |

지킴이가 **가중치를 정하고**, 추첨 실행은 보상 계층이 한다. 추첨은 (챌린지, 판정일, 리롤 횟수)에서 유도한 시드를 쓰는 **결정론**이다 — 같은 날을 다시 판정하면 같은 사물이 나온다.

## 4. 거래 판정과 되돌리기

### 4.0 판정 종류 `kind` — 5종 (v1.5 신설)

**이 하나가 뒤의 모든 판정을 좌우한다.** v1.2는 "챌린지 카테고리인가"만 봤고, 그래서 통신비·구독 같은 고정지출이 예산에서 깎였다 — 사용자가 손쓸 수 없는 돈으로 한도를 넘기는 셈이다.

| kind | 예산 차감 | 개입 | 일 판정 | 3칩 |
|---|:---:|---|:---:|---|
| `target` 줄이기로 한 카테고리 | ○ | C1 C2 C3 C8 | ○ | 필수 |
| `normal` 관리 밖 일반 지출 | ✕ | C4 침묵 | ✕ | 표시만 |
| `sanct` 성역(의료·경조사) | ✕ | 영구 침묵 | ✕ | 표시만 |
| `fixed` 고정지출(통신·구독·통근) | ✕ | ✕ | ✕ | 고정지출 칩 |
| `unknown` 분류 실패·저신뢰 | 보류 | C7 질문 | 보류 | 필수, 2P |

```text
resolveKind(tx, ch):
    분류 없음 또는 신뢰도 < 0.70  → unknown
    성역 카테고리                 → sanct    ← 고정지출보다 먼저
    고정지출 표시                 → fixed
    챌린지 카테고리               → target
    그 외                         → normal
```

**성역을 고정지출보다 먼저 본다.** 챌린지 도중 성역을 추가하면 챌린지 카테고리와 겹칠 수 있는데, 그때 성역이 이겨야 "여기엔 참견하지 않겠다"는 약속이 지켜진다.

**`kind`와 3칩은 다른 축이다.** `kind`는 시스템이 정하는 판정 대상 여부이고, 3칩(`PLANNED`·`REDUCING`)은 사용자가 남기는 소비 맥락이다. **라벨을 붙여도 차감은 그대로다** — 유리한 칩을 고를 유인이 없어야 데이터가 정직해진다. 세 번째 칩 '불가피한'은 미결(D29)이라 아직 내보내지 않는다.

### 4.1 낙관적 판정

거래가 들어오면 **즉시 집계하고 24시간 되돌리기를 준다.** "확인받고 차감"은 사용자가 매번 확인 버튼을 눌러야 해서 알림 피로가 커진다.

```text
환불              → 원 거래를 찾아 예산 복원, 조용히 (C12)
unknown           → 집계하지 않고 되묻기만 (C7) — 분류 전에는 판정할 수 없다
sanct·fixed·normal → 원장에 남기되 집계 제외, 침묵 (C4)
target            → COUNTED, 유예 24시간, 예산 차감
```

### 4.2 되돌리기 두 가지

| 버튼 | 사유 | 소모 |
|---|---|---|
| `챌린지랑 상관없어요` | NOT_MINE | 없음 |
| `면제권 쓸게요` | EXEMPTION | 면제권 1장 |

`이 소비 아니었어요`는 사용자가 지킴이를 반박하는 프레임이라 쓰지 않는다. 되돌리기는 **알림을 만들지 않는다** — 자기가 한 행동을 통보받게 하지 않는다.

서포트의 '패스(쿠폰)'와 마이룸의 '불가피 태그'는 면제권 하나로 통합했다. 같은 일을 하는 장치가 둘이면 어느 쪽을 쓸지 고민하게 된다.

### 4.3 초과 확정은 배치가 한다

거래 순간에 `EXCEEDED`로 넘기면, 24시간 안에 되돌렸을 때 이미 초과 알림이 나간 뒤가 된다. 상태 전이는 유예가 만료된 뒤 새벽 배치가 확정한다.

## 5. 상태

```text
SETUP → ACTIVE ⇄ AT_RISK → EXCEEDED
                    ↓
                 SETTLING → SUCCESS | PARTIAL | SHORTFALL | FAILED
                                          ↓
                            REWARD_PENDING | RESTART_OFFER → CLOSED
```

| 전이 | 조건 |
|---|---|
| → AT_RISK | 지출 비율 ≥ 0.80 |
| → EXCEEDED | 지출 비율 > 1.0 **且** 되돌리기 유예 만료 |
| → SUCCESS | 방어율 ≥ 1.0 |
| → PARTIAL | 방어율 ≥ 0.70 |
| → SHORTFALL | 방어율 > 0 |
| → FAILED | 방어율 = 0 |

부분 달성 하한 0.70은 **5주차 인터뷰로 검증할 가정값**이다.

### 5.1 (C) ② → ③ 개정 필드

```json
{
  "challengeId": 1, "state": "AT_RISK",
  "baselineAmount": 250000, "targetSaving": 100000, "challengeCap": 150000,
  "spentAmount": 122000, "remainingCap": 28000, "spentRatio": 0.8133,
  "securedSaving": 100000, "achievementRate": 1.0,
  "daysTotal": 30, "daysElapsed": 21, "daysLeft": 9,
  "noSpendStreak": 4, "grassStreak": 4
}
```

`baselineAmount`·`challengeCap`·`spentRatio`·`paceRatio`는 **사용자 표시 계약에 포함하지 않는다**(정본 (C)의 `spend_limit` 비노출 원칙 유지). ③은 `securedSaving`·`achievementRate`·`daysLeft`로 서술한다.

## 6. 포인트

| 사유 | 포인트 | 판정 시점 | 상한 |
|---|---:|---|---|
| 주간 미션 | **총 30P를 진행 중 미션이 나눠 가짐** | 일요일 배치 | 안 |
| 위기 방어(AT_RISK로 한 주 버팀) | 20 | 일요일 배치 | 안 |
| 3칩 라벨링 | 건당 2 (주 최대 50) | 즉시 | 안 |
| 챌린지 완주 | 100 | 종료일 배치 | **밖** |
| 중복 사물 전환 | 일반 5 · 희귀 15 · 에픽 30 | 즉시 | **밖** |

주간 상한 **100P** = 미션 30 + 위기 방어 20 + 라벨링 50(25건).

```text
missionShare(개수) = ⌊30 / clamp(개수, 1, 3)⌋      # 1개 30 · 2개 15 · 3개 10
```

**미션당 정액이 아니라 총액을 나눈다(v1.5).** 미션마다 30P를 주면 "두 개 하면 두 배"가 되어 수집형 플레이로 변질된다. 화면에도 미션별 포인트를 붙이지 않고 "이번 주 미션 보상 15P / 30P" 게이지 하나를 둔다.

**완주와 중복 전환은 상한 밖이다.** 완주는 장기 보상이고, 중복 전환이 상한에 걸려 0이 되면 "또 같은 게 나왔다"가 아무 보상도 없는 일이 되어 뽑기 자체가 벌처럼 읽힌다.

**출석·로그인 보상은 없다.** 포인트는 절약 행동의 증명이어야 한다.

상점: 사물 30P · 가구 150P · 벽/바닥 400P. **현금 결제 경로는 두지 않는다.**

### 6.1 주간 미션 유형

| 유형 | 판정 | 비고 |
|---|---|---|
| `MAX_COUNT` | 주간 해당 카테고리 집계 건수 ≤ 임계 | v1.5 |
| `AVOID_SLOT` | 지정 요일·시간대에 결제 0건 | v1.5 — **요일·시간은 반드시 KST** |
| `NO_SPEND_STREAK_MIN` | 무지출 최고 연속 ≥ 임계 | 기존 유지 |
| `LABELING_COUNT_MIN` | 라벨링 건수 ≥ 임계 | 기존 유지 |

`AVOID_SLOT`을 UTC로 재면 금요일 밤 22시 주문이 토요일로 넘어가 미션이 통과해 버린다.

부분 성공을 인정한다 — 2개 중 1개만 달성하면 그 몫(15P)을 받는다.

## 7. 화법

### TENTATIVE — 되돌릴 수 있는 결제

일어난 일은 '결제 사실'까지만, 결과 숫자는 조건부로.

```text
O  "배달 32,000원 결제가 들어왔어요. 챌린지에 넣으면 한도는 118,000원 남아요."
X  "배달에 32,000원 썼어요. 118,000원 남았어요."
```

금지: 썼어요 / 남았어요 / 넘었어요 / 소진됐어요 같은 완료 단정형.

### DEFINITIVE — 이미 확정된 사실

조건부로 쓰지 않는다. 금지: ~인 것 같아요 / ~할 수도 있어요 / 아마 / ~로 보여요.

### 고정구 — 반복 금지에서 빼는 표현

```text
"결제가 들어왔어요" · "챌린지에 넣으면" · "이 결제까지 넣으면"
"들어온 결제가" · "챌린지랑 상관없어요" · "알려줘서 고마워요"
```

매 알림에서 써야 하는 표현이라 반복 감지 대상에서 빼야 한다. 이걸 빼먹으면 며칠 뒤 지킴이가 단정형으로 되돌아가고, 원인 추적이 어렵다.

### 판단은 규칙이, 표현은 AI가

규칙 엔진이 "보낼지 말지"와 "무슨 숫자를"까지 다 정한 뒤에야 LLM이 불린다. LLM은 계산도 판단도 추정도 하지 않는다. **폴백 문구를 먼저 완성하고 LLM은 맨 마지막에 얹는다** — 새벽 배치는 전 사용자 분량이 한꺼번에 생성돼 호출이 몰리므로 폴백이 특히 중요하다. 폴백 사용률 목표는 5% 이하다.

> **문구 원문 유실**: 설계서 v1.2 원본의 한글이 전달 과정에서 인코딩이 깨져(UTF-8 3바이트 중 0x80~0x9F 구간 유실) 복원할 수 없었다. 현재 구현의 문구는 위 화법 규칙에 맞춰 새로 쓴 것이며 `GuardianCopy.java` 한 곳에 모여 있다. 원문이 확보되면 그 파일의 문자열만 갈아끼우면 된다.

## 8. 재현성

- 지킴이 코드는 어디서도 현재 시각을 직접 읽지 않는다. **사용자별 가상 시계**를 거친다.
- 한 달 챌린지를 발표 5분 안에 시연하려면 시간을 앞으로 밀 수 있어야 한다. 나중에 고치려면 전부 뒤져야 한다.
- 사물 추첨은 결정론이다.
- 모든 조회는 정렬이 고정돼 있다.
- 임계치는 전부 `application.yml`(`finntech.guardian.*`)에 있다. 케이스의 **구조**(우선순위·톤·쿨다운)는 값이 아니라 로직이라 코드에 남는다.

## 9. 미정

### 9.1 규칙은 있으나 호출부가 없는 것 (v1.5)

판정 함수와 테스트는 있는데 재료를 넘겨줄 곳이 아직 없다. **재료가 붙으면 바로 켜진다.**

| 항목 | 상태 | 필요한 것 |
|---|---|---|
| C9 위험 시간대 넛지 | `shouldNudgeAhead()` 구현·검증 완료 | ① 분석의 `time_patterns`(요일·시간대·4주 빈도) 전달 |
| `AVOID_SLOT` 미션 | `countInSlot()` + 엔티티 필드 완료 | 보상 계층의 미션 생성 규칙 |
| 3칩 라벨링 | `applyChip()` + 라벨링 포인트 완료 | 칩을 붙이는 API·화면 |
| 중복 사물 전환 | `duplicateAmount()` 완료 | 추첨이 중복을 만났을 때의 분기 |
| `oneline` 홈 한마디 | `resolveOneline()` 우선순위 완료 | 폴백 문구 44자 표 + LLM 출력 계약에 필드 추가 |
| 다중 챌린지 합산 | `combineDailyVerdicts()` 완료 | 현재 사용자당 챌린지 1개라 합산이 항등. 카테고리별 한도를 별도 챌린지로 쪼갤 때 그대로 맞는 답을 낸다 |

### 9.2 아직 정해지지 않은 것

| 항목 | 비고 |
|---|---|
| D29 — 3칩의 '불가피한' | 면제권 쓰기로 대체할지. 상시 무료 되돌리기와 뽑기 면제권이 모순이다 |
| 챌린지 정산 → 캐릭터 성장 원장 연결 | 정본 `03_여정과_성장.md` §4의 누적 성장과 잇는 부분 |

| 사용자 지정 챌린지 기간 | 현재 30일 고정. 기간이 바뀌면 기준 지출 환산 로직이 필요 |
