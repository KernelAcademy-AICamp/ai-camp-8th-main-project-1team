## 0. 이 문서를 쓰는 이유

멘토링 B의 핵심 조언은 기록 방식에 관한 것이었다.

> 가설이 부정적인 결과로 나오더라도 실패로 치부하지 말고, 가설 설정 · 검증 과정 · 데이터 도출을 통해 왜 그런 결과가 나왔는지 스토리를 구성하면 포트폴리오상 큰 자산이 된다.

이 문장의 실무적 함의는 하나다. **검증 결과가 나온 뒤에 기록을 시작하면 늦다.**

"이런 가설이 있었다"는 사후 서술은 누구나 쓸 수 있고, 그래서 아무 증거력이 없다. 결과를 모르는 시점에 살리는 신호와 죽이는 신호를 미리 적어둔 기록만이 "우리는 결과에 맞춰 이야기를 만들지 않았다"를 증명한다.

**따라서 이 문서는 결과가 나오기 전인 지금 채운다.**

## 1. 기록 템플릿

```markdown
### H-XX. [가설 이름]

| 항목 | 내용 |
|---|---|
| 상태 | 검증 대기 / 검증 중 / 확인됨 / 기각됨 / 보류 |
| 등재일 | YYYY-MM-DD |
| 소유자 | |

**목표**
이 가설이 참일 때 무엇이 좋아지는가. 어떤 문제(P#)를 푸는가.

**가설문**
[조건]하면 [사용자]는 [행동/인지 변화]할 것이다.

**살리는 신호**
이 결과가 나오면 가설이 지지된 것으로 본다. (사전에 정의)

**죽이는 신호**
이 결과가 나오면 가설을 기각한다. (사전에 정의 — 이게 없으면 검증이 아니다)

**검증 방법**
누구에게, 무엇을, 어떻게 측정하는가.

**필요한 데이터 설계**
검증하려면 지금 무엇을 로깅/설계해두어야 하는가.

**결과** (검증 후 기입)

**액션** (검증 후 기입)
- 확인됨 → 무엇을 확대하는가
- 기각됨 → 무엇을 제거/대체하는가
```

**작성 원칙**

- 죽이는 신호를 못 쓰겠으면 그건 가설이 아니라 신념이다. 검증 목록에서 뺀다
- 살리는 신호는 결과를 보기 **전에** 확정한다. 사후 수정 시 수정 이력을 남긴다
- 검증 방법의 한계(표본 수·합성 데이터·자기보고 편향)를 함께 적는다. 한계를 적는 것이 신뢰도를 높인다

## 2. 검증 방법의 공통 한계 (먼저 명시)

| 한계 | 내용 | 대응 |
|---|---|---|
| 표본 수 | 사용자 테스트 N=8~12 수준. 정량 유의성 확보 불가 | 정량은 **방향 신호**로만 사용. 결론은 정성 근거로 서술 |

| 더미 데이터 | 실제 마이데이터가 아님 | `README` 규제 경계 원칙대로 "더미 파이프라인으로 검증"으로만 표현 |

**목표**

**가설문**

**죽이는 신호**
- 개념 이해도 60% 미만
- "결국 쓰지 말라는 소리 아니냐"는 반응이 절반 이상

**검증 방법**
사용자 테스트 시 온보딩 완료 직후 "지금 화면이 무슨 뜻인지 설명해 주세요" (설명 없이). A/B 대조군으로 같은 금액을 '이번 달 지출 한도'로 제시한 화면을 함께 보여주고 부담 점수를 비교한다.

**필요한 데이터 설계**
온보딩 완료 시점 스크린샷 + 발화 녹취. 별도 로깅 불필요.

### H-04. 마이룸 리텐션 — 게임화

| 항목 | 내용 |
|---|---|
| 상태 | 검증 대기 · **구현 완료 (7/30, 프론트 반영)** |
| 등재일 | 2026-07-30 (멘토링 B) |
| 소유자 | 지윤정 |

**목표**
게임화는 **리텐션 확보를 위해 도입한 기능이다.** 절약 금액이라는 숫자 피드백만으로는 재방문 동기가 약할 것이라는 우려에 대한 대응이며, [0722_멘토링회의록](0722_멘토링회의록.md) §2에서 **게임을 목적이 아닌 수단으로 쓰기로 한 결정**의 연장선이다. 조기 검증을 위해 최소 버전으로 구현했다.

**가설문**
절약 달성에 대해 비화폐성 보상(오브젝트·도감)을 지급하면, 숫자 피드백만 있을 때보다 사용자는 앱을 더 자주 열고 싶어 한다.

**살리는 신호**
- "내일 아침에 뭐 들어왔나 보고 싶다" 계열 발화 다수
- 마이룸 유무 화면 비교 시 마이룸 있는 쪽 재방문 의향이 높음
- 오브젝트 획득 순간 긍정 정서 반응 관찰

**죽이는 신호**
- "금융 앱에서 이런 걸 왜" 계열 반응이 절반 이상
- 마이룸 진입 후 체류 5초 미만
- 서비스 신뢰도가 오히려 하락 — 금융 앱에 게임 요소를 얹었을 때의 신뢰 희석 우려가 현실화

**검증 방법**
프로토타입 태스크 + 사후 인터뷰 + 선호 비교. **실제 리텐션은 측정 불가** — 의향과 관찰로 대체하며 이 한계를 결과에 명기.

**필요한 데이터 설계**
- 마이룸 탭 진입률 · 체류 시간
- 오브젝트 획득 화면에서의 반응 녹취
- 사후: "이 기능이 없으면 앱을 덜 열게 될까요?"

**결과** — 미기입

**액션 (사전 작성)**

> 멘토 B: "실패해도 그것을 어떻게 스토리로 구성하느냐가 자산" ([0730_멘토링회의록](0730_멘토링회의록.md) Ⅰ-4)

멘토가 정리한 두 가설 위에서 판단한다 ([0730_멘토링회의록](0730_멘토링회의록.md) Ⅰ-4).

- **① 유저는 실제 아끼는 금액(숫자)에 반응한다**
- **② 그럼에도 재미 요소가 있을 때 리텐션이 올라간다**

마이룸은 **②를 푸는 여러 방식 중 하나**이지 ② 자체가 아니다.

- **확인됨** → 마이룸 유지. 도감·마일스톤 확장
- **기각됨** → 마이룸을 제거하지 않고 **비노출 처리**. 발표 서사: "리텐션을 위해 게임화를 도입했고, 가설 ②를 검증하려 최소 버전을 구현했다. 결과는 부정이었고, 이는 **가설 ①(숫자 피드백만으로 충분하다)을 사후 지지**한다"
- **부분 확인** → 오브젝트 수집은 유지, 포인트 샵은 제거

멘토는 **실제 서비스에서는 운영 리소스 때문에 잘 돌아가기 어렵다고 보면서도, MVP 단계에서는 해볼 만하다**고 평가했다 ([0730_멘토링회의록](0730_멘토링회의록.md) Ⅰ-4). 즉 **기각되어도 "왜 뺐는지"의 근거가 이미 확보돼 있다.** 어느 쪽으로 나와도 서사가 성립한다.

> 과다 판정 발견·보정은 이 가설의 "죽이는 신호"(정밀도 60% 미만)에 해당하는 상황을 **검증 전에 자체적으로 잡아낸 것**이다. 재학습 전후 판정 금액 비교 수치를 확보해 결과란에 기록한다.
>
> **단, 위 세 건은 모두 L1(후보 선정) 층위다.** 이 가설의 본체인 L2(건별 편차 감지)는 아직 확인되지 않았다.

**목표**
멘토링 A가 "서비스의 핵심 경쟁력"으로 지목한 지점. P1을 건별 단위로 해결.

**가설문**
사용자 **개인의 평소 소비 대비** 편차로 판정하면, 카테고리 일반 기준으로 판정할 때보다 사용자가 "맞다"고 인정하는 비율이 높다.

> 판정 방법·기준값은 개발 영역이다 ([0730_기획변경사항](0730_기획변경사항.md) D장). 이 가설은 **개인 기준 판정이 일반 기준보다 나은가**만 검증한다.

**살리는 신호**
- 알림에 대해 사용자가 "맞다"고 인정하는 비율이 높음
- "이건 괜찮아" 예외 처리 빈도가 낮음
- "어떻게 알았지" 계열 반응

**죽이는 신호**
- 알림 상당수를 사용자가 부정
- 예외 처리가 잦아 잔소리로 인지됨
- 알림을 끄는 사용자 발생

> 구체적 목표 수치는 상현님과 함께 정한다. 기획이 먼저 숫자를 박지 않는다.

**검증 방법**
1. 더미 데이터에 정답 라벨을 심은 케이스로 오프라인 평가 (상현님 주도)
2. 사용자 테스트에서 실제 알림에 대한 "맞다/아니다" 응답 수집

**필요한 데이터 설계** — 개발에 요청할 것

- **판정 근거 기록**: 어떤 결제를 왜 그렇게 판정했는지, 판정 시점의 기준값을 함께 남기기
- 알림별 사용자 응답 (맞다 / 괜찮아)
- 예외 처리 및 자동 제외 이력

> **왜 필요한가**: 판정 근거가 남지 않으면 사용자 테스트 결과를 해석할 수 없고, 발표에서 "왜 이 알림이 갔느냐"는 질문에 답할 수 없다. **기준을 정해달라는 게 아니라, 나중에 설명할 수 있게 해달라는 요청이다.**

**결과** — 미기입

### H-06. 성역 지정과 통제감

| 항목 | 내용 |
|---|---|
| 상태 | 검증 대기 |
| 등재일 | 2026-07-30 (멘토링 A) |
| 소유자 | 지윤정 |

**목표**
P8(절약 조언이 잔소리로 느껴짐) 해결. 두 멘토가 공통으로 강조한 예외 처리의 효과 검증.

**가설문**
사용자가 절대 포기하지 않을 카테고리를 직접 성역으로 지정하게 하면, 나머지 소비에 대한 절약 제안을 통제·잔소리로 인지하는 정도가 낮아진다.

**살리는 신호**
- 성역 지정 단계를 거친 뒤 절약 제안 수용률이 상승
- "내가 정하는 거니까 괜찮다" 계열 발화

**죽이는 신호**
- 성역을 과도하게 지정해 절약 후보가 거의 남지 않음 (= 기능 무력화)
- 성역 지정 자체를 귀찮아하며 건너뜀

**검증 방법**
온보딩 태스크 관찰 + 성역 지정 개수 분포 확인.

**필요한 데이터 설계**
성역 지정 카테고리 수 · 지정 후 남은 절약 후보 금액.

**진행 기록 (2026-07-30)**
- 가맹점 단위 예외 학습 구조 구현 (제외 → 기준 강화 → 반복 시 판정 제외 → 설정에서 취소)
- 명시적 "성역 지정"과 행동 기반 자동 학습이 **두 경로로 공존**하게 됨
- → 이 가설의 검증 질문이 하나 늘었다: **사용자가 명시적으로 지정하는 것과 시스템이 행동에서 학습하는 것 중 어느 쪽이 통제감을 더 주는가.** 전자는 주체감이, 후자는 편의성이 강하다

**결과** — 미기입
**액션** — 미기입
