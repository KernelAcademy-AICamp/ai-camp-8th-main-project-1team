# Ⅰ. 오전 — 이주형(YAW) 멘토 (11:00 · 58분)

> 문서상 호칭: **멘토링 B · 멘토 2**

## 1. 가입 플로우 — 동의가 개인정보 입력보다 앞에 와야 한다

현재 프로토타입은 `이름 → 전화번호·주민번호 입력 → 통신사 인증 → 동의` 순서다.

- **개인정보 동의는 정보를 받기 전에 있어야 한다.** 입력받는 것이 전부 개인정보이므로 인증 전에 동의가 선행돼야 한다
- 들어오자마자 이름을 요구하니 어색하다 → 앞에 **스플래시 + `가입하기`/`로그인하기`** 단계가 있으면 자연스럽게 납득된다
- 순서 자체(동의 → 정보 입력 / 정보 입력 → 동의)는 무관하다. 인증 후 API로 쏘는 것이므로 문제없다
- 동의 화면에 **전체 선택**을 넣는다

**금융정보 동의를 두 번 받는 게 맞는가** (지윤정 질문)

- 필요한 것은 **①고지 ②동의** 두 가지뿐이다. 보여주고 받고를 반복할지, 한 번에 묶을지는 **UI 설계 나름**이지 규정 문제가 아니다

## 2. 예외 케이스 질문의 노출량

프로토타입은 반복 KTX 결제를 잡아 "통근인가요, 여행인가요"를 되묻는다. 멘토는 AI가 이 판별까지 한다는 점을 확인하고 긍정 평가했다.

- 팀 우려(지윤정): 예외 케이스가 늘면 **"설문조사 취조당하는 느낌"** 이 된다
- 멘토: **결제 상위 3~5개 정도만 노출**한다. 나름의 확률을 갖고 **"이건 아닐 확률이 높다"는 높은 기준의 건만** 물어보는 로직을 넣으면 된다. 나머지는 그냥 보여주고 사용자가 빼면 된다
- 사용자 상황은 바뀐다 — 이전엔 통근이던 KTX가 나중엔 여행이 될 수 있다 → **마이페이지에서 재설정 가능**해야 한다. 그게 마이페이지가 필요한 이유다

## 3. 카테고리 분류 — 현업에도 정답이 없다

- 배달과 외식을 한 카테고리로 묶는 게 맞는가, 카페·간식을 분리할 것인가에 대한 팀 고민 공유
- 멘토: **현업에도 답이 없다.** 데이터를 보면서 계속 수정·재분류할 수밖에 없다 (번개장터 경험 — 신규 제품이 나올 때마다 어느 카테고리에 넣을지, 한쪽이 넓어지면 다시 쪼갤지 반복)
- 실제 운영이라면 **페르소나를 정하고 그에 맞춰** 데이터를 보며 바꿔 나간다
- 세분화가 곧 정답은 아니다 — **너무 쪼개면 건당 금액이 작아져 오히려 애매해진다**
- 결론: 지금 확정할 문제가 아니고, **그런 성질의 문제라는 것만 알고 있으면 된다**

## 4. 마이룸(게이미피케이션) — "그것도 하나의 가설이다"

- 멘토의 사전 평가: **실제 서비스에서 이런 기능이 잘 돌아가기는 어렵다**고 본다. 카드사도 비슷한 걸 많이 하지만 본인은 잘 안 하게 되더라. 실 운영 시 리소스가 크게 든다
- 다만 **MVP 단계에서는 운영비용이 당장 들지 않으므로 해볼 만하다**
- 게이미피케이션을 제안했을 때 이 정도 규모를 생각한 건 아니었지만, 방향 자체는 괜찮다
- 팀 제약(지윤정): 확률형 아이템·리롤은 **금융 서비스라 법적 제약**에 걸린다는 안내를 받아, 재미를 어디까지 줄지 결정에 시간이 필요하다

**핵심 조언 — 부정적 결과를 어떻게 다룰 것인가** (지윤정 질문: 검증에서 부정적으로 나오면 포트폴리오·면접에서 어떻게 설명하나)

- 현재 가설은 두 개다
  - ① 유저는 **실제 아끼는 금액(숫자)** 에 반응한다
  - ② 그럼에도 **재미 요소가 있을 때** 서비스에 더 관심을 갖고 리텐션이 올라간다
- 마이룸은 ②를 푸는 **여러 방식 중 하나**일 뿐이다
- **"이런 가설을 세웠고 → 이렇게 검증했고 → 결과가 이랬다"** 로 스토리가 만들어진다. 모든 가설이 성공할 수는 없다
- 중요한 것은 결과가 아니라 **성공/실패의 근거를 어떻게 도출했는가, 그 도출을 위해 데이터를 어떻게 설계했는가**다
- 부정적으로 나와도 출시해도 된다. 단 **무엇을 근거로 넣고 무엇을 근거로 뺄지**가 있어야 한다

## 6. 질문 ② — 더미 마이데이터를 얼마나 현실적으로 만들 것인가

현재 구성: 계좌 = 급여 입금·잔액 / 소비 = **카드 사용내역만**. 전자금융업권 미포함.

**카테고리 판정 방식** (이상현 설명)

```
마이데이터 수신: CI · 결제시각 · 사업자등록번호 · 금액
    ↓
사업자등록번호 → 국세청 업종분류코드(6자리)
    ↓
업종분류코드 ↔ 내부 카테고리 1:1 매칭
```

- 멘토: **업종코드 + 가맹점명을 함께 매칭하면 더 정확해진다.** 업종코드만으로는 볼링장이 술집으로 나올지 체육시설로 나올지 알 수 없다
- **상세 물품을 알 수 없는 것은 현실적 한계다.** 카드사는 카테고리 로직을 내부에 갖고 있지만 **마이데이터 규격으로는 내보내지 않는다**(넣을 필요도, 넣을 수도 없다). 우리가 받을 수 있는 건 **제공 규격 안의 정보뿐**
- 사례: 토스에서 이디야 4,500원은 보이지만 무엇을 마셨는지는 안 나온다. **토스플레이스(오프라인 결제기기)가 하려는 것이 그 상세 수집**이다

**중복 계상 문제 — 스코프 밖으로 결정**

- 팀 질문: 체크카드는 카드내역과 계좌출금이 동시에 잡히고, 카카오페이도 계좌·카드 양쪽에 찍힌다. 중복 제거 로직이 필요한가
- 멘토: **토스도 아직 해결하지 못한 문제다** (신용카드 대금 이체 50만 원과 카드 승인액이 둘 다 지출로 잡힘)
- **계좌이체는 일반적으로 지출로 보지 않는다.** 우리가 다룰 것은 **카드사 승인 내역 + 간편결제사 결제 내역** 두 가지면 충분하다
- → **계좌이체 중복 제거는 지금 우리 스코프가 아니다**

**업종코드의 한계** (이상현 질문)

- 같은 올리브영이라도 점주가 국세청에 **편의점 / 슈퍼마켓 / 화장품일반판매업** 중 무엇으로 등록했는지에 따라 카테고리가 갈린다. 실데이터라면 전부 다른 카테고리가 된다
- 멘토: **현업에서는 수기로 보정한다.** 가맹점명과 업종코드를 함께 보고, 올리브영의 80%가 화장품판매점으로 나온다면 나머지를 그쪽으로 맞춘다
- 해외 카드 결제도 현지 매입사에 따라 제각각이라 같은 작업을 계속한다. **요즘은 이 보정을 AI로도 한다**

```
목표 → 가설 → 어떻게 검증했는가 → 검증 결과 → 어떻게 반영했는가(액션 아이템)
```

- 개인이 각자 업데이트한 것을 모아 **스프린트 문서**로, 다시 **정책서**로 관리할 수 있다
- 만드는 데 여유가 있다면 **이쪽에 리소스를 더 쓰는 편이 낫다.** AI에게 양식 초안을 만들게 해도 된다

- 홈 = 지킬 돈 · 카테고리별 잔여 · 최근 소비. 불가피했던 소비는 사후 되돌리기
- 리텐션 장치로 **마이룸**(방 꾸미기·포인트 굿즈·스트릭·캘린더)
  - 이가원: 심리학의 **'동기 치환'** — 돈을 지키는 게 아니라 **방을 꾸미려고** 돈을 지키게 된다
- 리포트 탭·마이 탭 구성은 아직 고민 중

## 3. 보상 체계를 뺀 것에 대하여

- 원래 있던 보상(일본 여행·에어팟 등)을 폐기한 이유: **보상이 또 다른 소비를 부른다.** 아낀 돈으로 다시 쓰면 절약이 아니다
- 멘토: 원래 의도는 "쓸데없는 소비를 줄이고 **의미 있는 소비**를 하자", 즉 **소비의 질을 바꾸는 것**이었다
- 이가원: 목표가 두 개가 되어버린 게 문제였다 (지킬 돈 10만 원 + 맥북)
- 멘토: **10만 원을 지키면 맥북은 자연히 지켜진다.** 두 개를 동시에 쫓는 구조가 아니다
- 목표가 너무 크면(자동차·집) 여정이 길어진다는 우려에 대해
  - 멘토: **그렇게 안 되도록 설계하면 된다.** 6천만 원 그랜저를 설정하게 두지 말고, 이 사람이 절약 가능한 금액에 맞춰 **3개월·6개월 단위로 시스템이 제안**하면 된다. 시스템적으로 핸들링 가능한 문제이니 **이것 때문에 미션을 포기할 필요는 없다**
- **결론**: 지금 단계는 보상을 빼고 가는 게 맞다. 보상·저축 전환은 **나중에 옵션**으로 둔다 — 지킨 돈으로 또 소비할지, 통장에 넣을지는 **사람마다 다르므로 우리가 정할 필요 없이 선택지로 주면 된다**
- 지킨 돈은 저금통 형태의 가상 통장으로 들어간다 (마이데이터 서버가 분리돼 있어 통장 생성 가능)

## 4. 중간발표 범위 — 멘토가 정리한 코어 루프

```
데이터 생성 → 분석·리포트 제공 → 고객이 인사이트 획득
   → 리포트 기반 설정으로 소비 절약 유도 → "네가 이렇게 잘하고 있다" 선순환
   → 계속 아끼게 만든다
```

- **여기까지가 중간발표 범위.** 마이룸을 디테일하게 꾸미기보다 **리포트에 무엇이 나오는지**를 보여주는 게 우선
- 리포트 + 마이(설정)까지 나오면 충분하다
- 중간발표 이후에는 **개인화에 집중**

## 5. 지킴·차감 인식과 알림

- '참았음' 입력은 없다. 마이데이터가 자동 수신하므로 **온보딩 이후 유저가 할 일이 없다**
- 이미 나간 소비 중 불가피했던 건은 사후에 유저가 입력해 **튜닝**
- 멘토: **알림을 써야 한다.** "다른 앱도 보내는데 우리도 보낸다. 안 볼 사람은 어차피 끈다" → **무엇을 알림으로 보낼지**를 고민할 것
- 마이룸은 LLM이 들어가는 영역이 아니라 크게 상관없다 (유저가 앱 안에서 액션하게 만드는 장치로 이해)
- 배치 제안: 절약 현황 옆에 **"이렇게 아끼면 3개월 뒤 이걸 살 수 있어요"** 를 붙이되, **온보딩 앞이 아니라 성과가 났을 때 뒤에** 배치한다

## 6. 낭비 판정 로직 — 가장 집요하게 파고든 부분

**현재 판정 방식** (이상현 설명)

```
6개월 소비내역 → 사용 패턴의 규칙성 도출
    ↓ 규칙에서 벗어나면 충동성 지수 부여
    ↓ 평소 결제하지 않는 시간대 → 가중치 상향
    ↓ 심야(23시~) 결제 → 심야 가중치 추가
    ↓ EBM 머신러닝 1차 판정
    ↓ 가중치 × 요소별 수치 → 최종 확률
    ↓ 건별 라벨 부착 → 카테고리별 재정렬(낭비 판정액 높은 순)
```

- 일상적·규칙적 금액은 이미 빠져 있다. 식비 300만 원 중 180만 원이 레귤러면 **120만 원만 낭비 후보**로 본다
- 화면 상위에 뜨는 것은 전부 낭비 판정 건이며, **차이는 확률의 크기**다
- 낭비 라벨이 붙으면 지킨 돈에서 차감되고, 아니면 차감되지 않는다
- 정합도는 **75~80%** — 라벨링된 데이터로 지도학습 후, 미분류 소비를 넣었을 때 기존 라벨과 일치하는 비율

**멘토의 핵심 지적 — 리포트가 아니라 '그 순간'에 잡히는가**

- 리포트를 뽑을 때 사치인지 아닌지가 구별되는 것과, **카드를 긁는 순간 건별로 판별되는 것**은 다르다. 후자가 되는지를 반복해서 물었다
- 구체적 사례: **평소 점심 12,000원 → 오늘 16,000원.** 사실 안 먹어도 되는 돈인데 **이건 못 잡을 것 같다**
  - 이상현도 **"안 잡힐 것 같다"** 고 확인 (카테고리 가중치 0.2 + 0.27 수준으로는 임계에 못 미침)
- 멘토: 이 앱이 해야 하는 것은 **'센서'의 기능**이다. "어제는 안 잡더니 오늘은 잡네" 하는 감각이 와야 한다
- **예민하게 잡는 쪽이 맞다.** 유저가 번거로우면 **딤드 옵션**(이 건에 대해서는 더 이상 알리지 마)을 주면 된다
- **이게 잘 나와야 리포트도 잘 나온다. 전부 연결돼 있어서 집요하게 묻는 것**이다

> ※ 이 지점이 [0730_기획변경사항](0730_기획변경사항.md) A장(R-1)과 [0730_가설검증로그](0730_가설검증로그.md) H-05의 출발점이다.

## 7. 개인화 — 어디까지 할 수 있는가

- 이가원 문제 제기: 월 100만 원 버는 사람이 반려동물에 30만 원 쓰면 과할 수 있는데, 이를 알려줘야 하지 않나
- 멘토: 그건 **평균치를 보여주는 방식**으로 푼다. "당신 나이·수입대라면 이 항목엔 이 정도를 씁니다" — 같은 평수 아파트 전기세 비교처럼. 개인화라기보다 **에버리지 제시**다
- 이가원 조사 공유: 요즘 핀테크는 마이데이터로 패턴만 찾는 게 아니라 **사용자 프로필을 만들고** 그 위에서 추론한다
- 멘토: **그쪽을 생각해보라.** 나이·직업·소득에 따라 같은 골프도 달라진다
  - 20대의 골프 = 과소비 / 골프 선수 = 정상 / 50대 = 운동
  - **같은 골프장 결제라도 어떤 사람에게는 알림이 울려야 한다** — 그게 개인화다
  - 논문을 쓸 때도 이런 걸 쓴다: 일반적인 방식 → 여기에 플러스 알파 → 이만큼 좋아졌다
- 지윤정: 20대가 골프 선수일 수도 있다 → 멘토: **직업을 업데이트하면 된다.** "이 건은 더 이상 올리지 마"를 체크할 수 있어야 한다
- 이가원 조사 — **지역 클러스터링**
  - 반복 등장하는 가맹점 지점명으로 **일터·생활권 추정**
  - 택시 차량번호로 지역 추정 (경기 번호판은 경기 면허에서만 발급)
  - 교통 결제 구간으로 **출퇴근 소요시간 추정**
- 멘토: 그런 것이 데이터 사이언스다. 데이터 마이닝·통계까지 가면 할 게 많지만, **우리 영역에서 할 수 있는 정도의 개인화는 해볼 만하다.** 지금 하라는 게 아니라 생각해볼 만하다는 것. 보험사가 이런 걸 많이 한다
- **"그런 예민함이 필요한 앱이다"**

## 10. 실데이터 투입 논의

- 멘토 제안: **내 작년 신용카드 데이터를 다 주면 리포트가 나오는가** → 아직 넣어본 적 없음
- 전제 조건: **사업자등록번호가 있어야 한다** → 연말정산 자료에 사업자번호가 포함돼 있음 (이가원이 전달한 버전에도 있음)
- 멘토 조언
  - **주로 쓰는 카드 하나만** 넣어도 패턴은 거의 나온다
  - LLM이 잘하려면 **전처리가 잘 돼 있어야 한다.** 전부 다 던지지 말고, 분석하지 않을 항목(교통비 등)은 **미리 빼고** 넣어라. 소비 금액을 빼는 게 아니라 **분석 대상 항목**을 거르는 것
- 해외 결제는 **사업자번호가 없다**(트래블월렛 등) — 별도 처리 필요

# ✅ 결정사항 (양 세션 종합)

- **챌린지 기간 = 달력 월 고정 + 기사용액 차감.** 가입일 기준 30일·일할 계산·다음 달 합산(40일)은 기각. 월 목표에서 가입 이전 실사용액을 빼고 "남은 기간 동안 남은 금액"으로 제시
- **더미 마이데이터는 현재 범위(카드 사용내역 + 계좌 급여·잔액)로 충분.** 전자금융업권 확장, 체크카드·간편결제 **중복 계상 제거는 이번 스코프에서 제외**
- **리포트 대원칙 = 지출 통제 현황 최상단 노출**, 나머지는 우선순위 하향. 1뎁스 요약 + 클릭 시 상세로 유연하게 설계
- **가입 플로우 개편** — 스플래시 → 가입하기/로그인 → 개인정보 동의(전체 선택) → 정보 입력 → 인증
- **온보딩 확인 질문은 상위 3~5건으로 제한**하고, 확률이 높은 건만 되묻는다
- **보상 체계는 빼고 간다.** 지킨 돈의 사용처(재소비 vs 저축)는 확정하지 않고 나중에 **선택지**로 제공
- **중간발표 범위 = 리포트에 무엇이 나오는지까지.** 마이룸 디테일은 후순위. 발표 이후 개인화 집중
- **마이룸은 가설로 취급한다.** 부정 결과가 나와도 무엇을 근거로 넣고 뺄지를 남기면 자산이 된다
- **기록 체계 = 목표 → 가설 → 검증 방법 → 결과 → 액션 아이템** 형식으로 항목화

# ⚠️ 미해결 — 팀이 답을 내야 하는 것

- **건별 편차 탐지(12,000원 → 16,000원)가 현재 로직으로는 잡히지 않는다.** 양측이 확인했고 대안은 나오지 않았다. 멘토는 "예민하게 잡고 딤드 옵션을 주라"는 방향만 제시
- 카테고리 분류 기준(배달/외식, 카페/간식) — 현업에도 정답이 없으며 데이터를 보며 조정할 사안
- 업종코드 오등록(올리브영 사례) 보정 — 현업은 가맹점명 병행 매칭 + 수기 보정. 우리 방식 미정
- 실시간 알림의 내용과 하루 상한
