## 이 문서의 경계

**담는 것 — 기획이 정하는 것**

- 사용자에게 무엇이 보여야 하는가
- 사용자가 무엇을 할 수 있어야 하는가
- 어떤 상태를 성공으로 볼 것인가

**담지 않는 것 — 개발이 정하는 것**

- 낭비·과소비 판정 알고리즘과 임계값
- 모델 구조와 재학습 기준
- 업종코드 매핑 로직
- 데이터 파이프라인 구현 방식

**왜 나누는가**

낭비 판정 기준은 상현님이 현재 계속 조정·재학습하고 있는 영역이다. 기획 문서가 특정 계산식이나 임계값을 확정하면, 진행 중인 개선과 충돌하거나 이미 지난 기준이 문서에 박제된다.

기획은 **"무엇이 달성되어야 하는가"** 까지만 쓰고, **"어떻게 계산할 것인가"** 는 개발에 맡긴다. 이 문서의 요구사항이 충족되는지 여부만 함께 확인한다.

> rev.1에서 편차 점수 계산식·임계값·관측 구간을 제안했으나 **전부 삭제했다.** 기획이 정할 영역이 아니다.

# A. 과소비 탐지 — 기획 요구사항

## A-1. 멘토 피드백에서 나온 요구사항

### R-1. 건별 편차를 알려줘야 한다

> **멘토 1**: "평소 점심 12,000원인데 오늘 16,000원. AI가 감지하는가? 알림을 주는가? 이 부분이 서비스 핵심 가치."

| 항목 | 내용 |
|---|---|
| 요구사항 | 사용자 **개인의 평소 소비 대비** 과한 결제를 **건 단위**로 알려준다 |
| 왜 필요한가 | 현재 온보딩 분석은 "어떤 카테고리를 줄일까"(월 단위)에 답한다. "오늘 이 결제가 과했는가"(건 단위)는 별개 문제이며, 멘토가 핵심 가치로 지목한 쪽은 후자다 |
| 기획이 정하는 것 | 알림이 필요하다는 것 · 알림에 담길 정보 · 노출 위치 |
| **개발이 정하는 것** | **무엇을 '평소'로 볼 것인가, 얼마나 벗어나야 알릴 것인가** |

**알림에 담길 정보 (기획)**

- 이번 결제 금액
- 평소와 비교한 표현 — "평소보다 얼마 더" (기준값 자체를 숫자로 노출할지는 별도 논의)
- 바로 예외 처리할 수 있는 버튼

**표현 원칙**: 지적이 아니라 정보 전달의 어조. [03_솔루션/02_솔루션컨셉](../03_솔루션/02_솔루션컨셉.md) §반드시 지킬 제품 원칙 · [01_고객/03_타깃고객](../01_고객/03_타깃고객.md) §이 사람이 거부하는 것(지적·잔소리·감시) 준수.

### R-2. 사용자가 판정을 되돌릴 수 있어야 한다

> **멘토 1**: 사용자가 "이건 괜찮아", "앞으로 알림 보내지 마"를 설정할 수 있어야 한다
> **멘토 2**: 마이페이지에서 특정 소비를 관리 대상에서 제외하거나 재설정할 수 있어야 한다

**이미 구현됨 (7/30).** → A-3

### R-3. 절대 포기할 수 없는 카테고리는 제외한다

> **멘토 1**: 건강·반려동물·취미 등은 추천 제외 기능 필요

프로토타입 '성역' 기능으로 구현됨.

**기획이 정할 것**: 성역으로 지정한 카테고리를 **건별 알림 대상에서도 제외할 것인가**, 아니면 알림만 끄고 리포트에는 표시할 것인가.

## A-2. 개인화 변수 — 기획 원칙

> **멘토 1**: 나이·직업·소득·소비 성향·생활권·출퇴근 패턴·지역 클러스터링을 반영. 예시로 "20대 골프 → 과소비 / 골프선수 → 정상 소비 / 50대 → 정상 소비"

**변수를 쓸지 말지, 어떻게 쓸지는 개발 영역이다. 다만 기획이 지켜야 할 선이 하나 있다.**

### 지켜야 할 선 — 속성으로 낭비를 판정하지 않는다

"20대에게 골프는 과소비"는 나이·직업으로 소비의 정상 여부를 판정하는 구조다. 우리가 세 문서에서 반복 확정한 원칙과 충돌한다.

- [03_솔루션/02_솔루션컨셉](../03_솔루션/02_솔루션컨셉.md) §반드시 지킬 제품 원칙 — "후보와 근거만 제안한다. AI는 낭비를 확정하지 않는다"
- [03_솔루션/02_솔루션컨셉](../03_솔루션/02_솔루션컨셉.md) §반드시 지킬 제품 원칙 — "가치 소비의 기준은 사용자에게 있다"
- [01_고객/03_타깃고객](../01_고객/03_타깃고객.md) §이 사람이 거부하는 것 — 잔소리 · 통제 · 감시

"20대인 당신에게 골프는 과소비입니다"는 정확히 이 거부 지점을 밟는다.

### 대안 — 판정이 아니라 제안에 쓴다

| 용도 | 판단 |
|---|---|
| 사용자에게 **낭비라고 말하는 근거** | 쓰지 않는다 |
| 온보딩에서 **성역 후보를 추천**하는 근거 | 쓴다 — "골프를 성역으로 두시겠어요?" |
| 결제 이력이 부족한 초기 사용자의 **판정 보조** | 쓴다 (방식은 개발 영역) |

같은 변수를 써도, 결론을 **사용자가 내리게 하면** 원칙에 걸리지 않는다.

### 수집 방식 — 온보딩 문항을 늘리지 않는다

| 변수 | 방법 |
|---|---|
| 나이 | 본인 인증 데이터에서 자동 취득 — 질문 없음 |
| 직업 | 온보딩 1문항, 건너뛰기 가능 |
| 소득 | 질문하지 않음 — 마이데이터 급여성 입금으로 대체 |
| 생활권 · 출퇴근 | 질문하지 않음 — 이미 재생성 데이터에 이동 동선이 반영되어 있음 |

온보딩 문항 추가는 이탈 요인이다. 마이데이터로 알 수 있는 것은 묻지 않는다.

## A-3. 예외 처리 UX

### 구현 완료 (7/30) — 설계보다 앞서 있음

```
사용자가 낭비 판정을 제외
    ↓
제외된 가맹점의 사업자등록번호 저장
    ↓
해당 가맹점을 더 깐깐한 기준으로 판정 (덜 낭비라고 봄)
    ↓
그럼에도 반복 제외될 경우
    ↓
낭비 판정 대상에서 가맹점 제외
    ↓
사용자는 설정에서 취소 가능
```

**기획 관점의 평가**: 사용자가 "항상 빼주세요"를 명시적으로 선택하지 않아도 행동에서 학습한다. 멘토 2가 우려한 "설문조사 취조당하는 느낌"을 줄이는 방향이다.

명시적 선택지가 없는 만큼 **설정에서 무엇이 제외됐는지 확인·해제할 수 있는 경로가 필수**이며, 이는 구현되어 있다.

### 노출량 — 멘토 2가 준 기준

> **멘토 2**: 결제 상위 3~5개 정도만 노출. 나름의 확률을 가지고 "이건 아닐 확률이 높다"는 것만 물어보는 로직

| 시점 | 노출량 | 출처 |
|---|---|---|
| 온보딩 확인 질문 | **최대 5건** | 멘토 2 |
| 실시간 알림 | 하루 몇 건까지 허용할지 **팀 결정 필요** | — |
| 사후 수정 | 무제한 | — |

> 실시간 알림 상한은 기획이 정해야 한다. 알림 피로는 UX 문제이지 알고리즘 문제가 아니기 때문이다. **다만 몇 건이 적정한지는 데이터가 없으므로, 우선 낮게 두고 사용자 테스트에서 조정한다.**

### 기획이 정할 남은 항목

- 자동 제외가 일어났을 때 사용자에게 알릴 것인가
  - 알리지 않으면 → "왜 이건 안 잡히지" 혼란
  - 알리면 → 알림이 늘어남
- 성역 카테고리의 소비를 리포트에는 표시할 것인가

## A-4. 무엇을 성공으로 볼 것인가

**정확도 목표치는 개발이 판단할 영역이지만, 어느 방향을 우선할지는 제품 결정이다.**

### 제품 원칙 — 놓치는 것보다 틀리게 지적하는 것이 나쁘다

우리 타깃은 잔소리·감시를 명시적으로 거부하는 프로필이다 ([01_고객/03_타깃고객](../01_고객/03_타깃고객.md)). 놓친 과소비 1건보다 **잘못된 지적 1건의 비용이 훨씬 크다.** 오탐 한 번이 앱 삭제로 이어진다.

따라서 판정 기준을 조정할 때는 **덜 잡는 쪽이 기본값**이다.

> **이미 실행된 사례 (7/30)**: 초기 모델이 낭비 수치를 실제보다 2배 이상 과다 판정하는 것을 확인하고 보완 재학습. 이 원칙과 일치하는 조정이다.

### 사용자 테스트에서 확인할 것

| 확인 항목 | 왜 보는가 |
|---|---|
| 알림 중 사용자가 "맞다"고 인정한 비율 | 잘못된 지적의 빈도 |
| 알림 대비 "이건 괜찮아" 응답 비율 | 높으면 판정이 과하다는 신호 |
| 알림을 부담스러워하는지 | 잔소리로 인지되는지 |
| 사용자가 "이건 알려줬어야 하는데" 하는 건 | 놓친 것의 빈도 |

> 목표 수치는 상현님과 함께 정한다. 기획이 먼저 숫자를 박지 않는다.

# B. 챌린지 기간 정책

> 멘토 2가 직접 답을 준 항목이며, 명확히 기획 영역이다.

## B-1. 결론

**월 단위 고정 + 기사용액 차감 방식을 채택한다.**

> **멘토 2**: "일할 계산보다는 월 단위로 관리하는 것이 유저 플로우상 자연스러울 수 있다. 이미 결제 이력이 있으니 목표에서 기사용액을 빼고, 남은 기간 동안 남은 금액을 쓸 수 있습니다로 하면 되지 않나."

## B-2. 검토한 안과 판단

| 안 | 내용 | 판단 |

| ① 가입일 기준 30일 | 7/15 가입 → 7/15~8/15 | 기각 — 월말 리포트 주기와 어긋남 |

| ③ 다음 달 합산 | 7/25 가입 → 7/25~8/31 한 덩어리 | 기각 — 멘토 2: "40일은 계산하기 어렵다" |
| ④ **월 단위 + 기사용액 차감** | 7월 목표는 그대로, 1~14일 실사용액을 뺀 나머지 | **채택** |

## B-3. 화면에 보여야 할 것

```
7월 지킬 돈        300,000원
이미 쓴 금액       −112,000원   (7/1~7/14)
─────────────────────────────
남은 지킬 돈        188,000원
남은 기간              17일
```

"이미 쓴 금액"을 숨기지 않는다. 이게 없으면 사용자는 자기 목표가 왜 30만이 아니라 18.8만인지 이해할 수 없다.

## B-4. 엣지 케이스 — 기획 결정 필요

| 케이스 | 제안 |
|---|---|
| **기사용액 > 목표** (이미 초과) | 남은 지킬 돈 0 표시 + "이번 달은 패턴을 보는 기간이에요. 8월 1일부터 본격 시작합니다" + 다음 달 목표 자동 생성 |
| **월 25일 이후 가입** | 첫 달을 **관찰 기간**으로 두고 성과 판정·리포트 없음. 다음 달 1일 정식 시작 |

| 거래 취소·환불 | 남은 지킬 돈 복구 ([03_솔루션/01_핵심설계결정](../03_솔루션/01_핵심설계결정.md) · [03_솔루션/02_솔루션컨셉](../03_솔루션/02_솔루션컨셉.md) 기존 결정) |

**관찰 기간을 두는 이유**: 가입 3일 만에 "당신은 실패했습니다"가 첫 경험이 되면 안 된다. 성과 판정이 사실상 불가능한 구간에서는 판정하지 않는다.

## B-5. 월 갱신

# C. 리포트 정보구조

## C-0. 원칙 — 두 멘토가 같은 말을 했다

> **멘토 2**: "지출 통제라는 목표에 대한 리포트가 가장 중요한 정보. 상위 노출. 그 외는 우선순위를 낮춰서."
> **멘토 1**: ①목표 진행률 ②절약 현황 ③소비 분석 ④금융상품 ⑤카드

두 안이 같은 구조다. 이를 주기별로 분리해 정리한다.

## C-1. 주간 리포트 — 행동 교정용

목적은 지난주를 돌아보는 것이 아니라 **다음 주를 바꾸는 것**. 짧게.

| 순서 | 내용 |
|---|---|
| 1 | 남은 지킬 돈 · 남은 일수 · 방어율 |
| 2 | 이번 주 평소보다 많이 쓴 건 Top 3 |
| 3 | 다음 주 고비 예고 (요일·시간대 패턴) |

**금융상품·카드 추천을 넣지 않는다.** 주간은 행동 교정 채널이며 여기에 상품을 얹으면 광고로 읽힌다.

3번은 프로토타입의 "금요일 밤 배달 참기 / 매주 금·일 반복" 카드가 이미 구현한 형태다.

## C-2. 월간 리포트 — 성과 정산 + 브릿지

| 순서 | 내용 | 노출 조건 |
|---|---|---|
| 1 | 최종 방어율 · 지킨 돈 · 목표 대비 달성률 | 항상 |
| 2 | 카테고리별 절약 현황 + 전월 대비 | 항상 |
| 3 | 소비 성격 분석 | 항상 |
| 4 | **지킨 돈, 어디에 둘까 → 금융상품 Top 3** | **지킨 돈 > 0일 때만** |
| 5 | 소비 패턴 기반 카드 추천 | 항상 |
| 6 | 다음 달 추천 목표 금액 | 항상 |

### 4번의 노출 조건이 핵심이다

[04_스펙/07 §4.5 저축 상품 매칭(FP-01)](../04_스펙/07_취향분석및추천_Agent_설계.md)의 브릿지 서사는 "네가 지킨 21만원, 이 통장에 넣으면 이자 X"였다. **지킨 돈이 0이면 이 문장이 성립하지 않는다.** 지킨 돈이 없는 달에 상품을 추천하면 맥락 없는 일방향 추천이 되고, 이는 RFP가 지적한 "공급자 중심 일방향 데이터의 한계" 그 자체가 된다.

조건부 노출은 브릿지 논리를 지키기 위한 설계이며, 발표에서 설명할 가치가 있다.

## C-3. 연간 리포트 — 이벤트성

취향·라이프스타일 요약형. ("올해 미술관 12번 다녀오셨네요")

두 멘토링에서 논의되지 않은 팀 자체 아이디어. **중간발표 스코프 밖.**

# D. 개발 영역 — 기획이 정하지 않는 것

아래는 상현님이 판단하며, 기획 문서에 기준을 박지 않는다.

- 낭비·과소비 판정 알고리즘과 임계값
- 무엇을 '평소'로 볼 것인지의 기준 (관측 기간, 대표값 등)
- 모델 구조 · 재학습 주기 · 학습 데이터 구성
- 업종코드 × 가맹점명 매핑 및 보정 로직
- 반복 제외 시 자동 제외로 전환되는 기준 횟수
- 더미 마이데이터 생성 규칙

## 다만 개발에 요청하는 것 두 가지

기준을 정하자는 게 아니라, **나중에 설명할 수 있게 해달라는 요청**이다.

| 요청 | 이유 |
|---|---|
| **판정 근거를 함께 기록** — 어떤 결제를 왜 그렇게 판정했는지, 판정 시점의 기준값을 함께 남겨주기 | 나중에 "왜 이 알림이 갔는지" 설명할 수 없으면 사용자 테스트 결과를 해석할 수 없고, 발표에서 질문에 답할 수 없다 |
| **재학습 전후 비교 수치** | 과다 판정을 발견하고 고친 과정이 발표의 핵심 소재다. 숫자가 있으면 이야기가 강해진다 |

---

## 기획 결정 필요 항목

> 개발 기준이 아니라 **사용자에게 보이는 것**에 대한 결정이다. 오늘 슬랙 비동기 확정 권고.

- [ ] 성역 카테고리의 소비를 리포트에 표시할 것인가, 아예 보이지 않게 할 것인가
- [ ] 자동 제외가 일어났을 때 사용자에게 알릴 것인가
- [ ] 월 25일 이후 가입자의 '관찰 기간' 채택 여부
- [ ] 주간 리포트 발송 시점 (일요일 저녁 vs 월요일 아침)
- [ ] 용어 통일 — `지킬 돈 / 보호율` vs `지킨 돈 / 방어율`

> **실시간 알림 하루 상한**은 상현님과 함께 정한다. 기획이 원하는 방향(적게)만 전달하고 숫자는 협의.
