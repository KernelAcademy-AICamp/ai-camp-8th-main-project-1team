## 0. 두 지표를 구분한다

마스터 §5 가 요구한 구분이다. **이름이 비슷해 섞이기 쉬우므로 여기서 못박는다.**

| | `shortTermDeviationScore` | `longTermVolatilityIndex` |
|---|---|---|
| 무엇 | **이번 달 이 결제가** 평소보다 튀는가 | **이 사람이** 달마다 얼마나 들쭉날쭉한가 |
| 단위 | 결제 한 건 | 사용자 한 명 |
| 방법 | Modified Z-score | 월 지출 변동계수(CV) |
| 창 | 평가 1개월 / 기준선 3개월 | 전 기간(최소 3개월) |
| 쓰는 곳 | 이상소비 경고(**주인공**) | 상품 추천 · 소비건전성지수 |
| 성격 | 사건 탐지 | 성향 측정 |

**하나를 다른 하나로 대체할 수 없다.** 매달 일정하게 많이 쓰는 사람은 변동성이 낮지만 특정
결제가 튈 수 있고, 반대로 달마다 들쭉날쭉해도 개별 결제는 다 평범할 수 있다.

---

## 1. 단기 — `shortTermDeviationScore`

### 1-1. 정의

Modified Z-score. 평균·표준편차가 아니라 **중앙값·MAD** 를 쓴다.

```
        0.6745 × (x − median)
  Z  =  ─────────────────────
                MAD
```

`MAD` 가 0 이면(값이 거의 같으면) 평균절대편차로 갈아탄다:
`Z = (x − median) / (1.253314 × meanAbsDev)`. 둘 다 0 이면 `Z = 0`.

**왜 평균이 아니라 중앙값인가.** 이상거래를 찾는데 그 이상거래가 평균을 끌어올린다. 소수의 큰
결제가 기준선을 밀어 올리면 정작 잡아야 할 것이 "평범"해진다. 중앙값·MAD 는 그 오염에 강하다.

**금액에 로그를 취한 뒤** Z 를 낸다. 소비 금액은 오른쪽으로 길게 꼬리를 끄는 분포라
원 단위 그대로 쓰면 큰 금액이 늘 이상으로 잡힌다.

> **취소·환불(음수)은 이 계산에서 제외한다.** 로그를 취하므로 음수가 섞이면 NaN 이 되어
> 그 카테고리의 기준선이 통째로 망가진다 — 예외도 경고도 없이 판정만 어긋난다.

### 1-2. 기준선을 어디서 뽑나

| | 값 | 설정 키 |
|---|---|---|
| 평가 창 | 최근 **1개월** | `analysis.fds.evaluation-window-months` |
| 기준선 창 | 그 앞 **3개월** | `analysis.fds.baseline-window-months` |
| 최소 표본 | 카테고리당 **10건** | `analysis.fds.min-samples-per-category` |

기준선은 **같은 카테고리** 를 먼저 본다(`BaselineSource.CATEGORY`). 표본이 10건에 못 미치면
**전체 소비**로 대체한다(`GLOBAL`). 어느 쪽을 썼는지는 결과에 담아 내려보낸다 — 근거를
숨기면 사용자가 판정을 의심할 때 답할 말이 없다.

### 1-3. 임계

| 축 | 임계 | 설정 키 | 근거 |
|---|---|---|---|
| **금액 이상** | `Z ≥ 3.5` | `fds.modified-z-threshold` | 잠정값. 페르소나 확정 후 *"100건 중 3~5건"* 으로 재역산 |
| **심야** | 00–06시 **그리고** 평소의 1.69배 | `fds.night-start-hour`·`night-end-hour`·`night-amount-multiplier` | 시간만으로는 근거가 약하다 — 금액과 **AND** 로 묶는다 |
| **신규 카테고리** | 기준선에 2건 이하 | `fds.new-category-max-baseline-count` | 안 쓰던 곳에서 갑자기 쓴 것 |
| **빈도 이상** | 평소의 1.69배 | `fds.frequency-multiplier` | 같은 카테고리를 평소보다 자주 |

**1.69 라는 숫자.** 원래 2.0 이었다. 생성기가 고액 구간을 지수 압축(α=0.77)하면서
'평소 대비 배수'가 m → m^0.77 로 바뀌어, 임계를 2.0^0.77 = 1.69 로 옮겨야 이상으로 잡히는
거래가 그대로 유지된다. **비율 기반 임계**(`ratio-threshold`·`modified-z-threshold`)는
스케일 불변이라 손대지 않았다.

### 1-4. 규칙과 ML 의 관계

규칙 FDS 는 **비교 기준선(baseline)으로 보존**한다. 프로덕션 판정은 해석가능 ML(EBM)이
맡되(§D24 3장), 규칙이 없으면 모델이 학습되기 전·근거가 없는 구간에서 화면이 빈다.

`AlertService` 는 `shortTermDeviationScore` **와** 규칙을 **AND** 로 묶는다. 하나만으로는
오탐이 많다.

### 1-5. 사람이 판정을 되돌릴 수 있다

임계는 사람마다 다르다. 사용자가 *"이 가게는 원래 이만큼 쓴다"* 고 알려 주면 반영한다.

| 성향 | 뜻 | 효과 |
|---|---|---|
| `NORMAL` | 기본 | 임계 그대로 |
| `LENIENT` | 이 가맹점은 관대하게 | 임계 +0.20 (`stance.lenient-threshold-shift`) |
| `EXCLUDED` | 아예 보지 마라 | 판정에서 제외 |

`NORMAL → LENIENT` 는 1회, `LENIENT → EXCLUDED` 는 누적 3회로 올라간다
(`stance-to-lenient`·`stance-to-excluded`).

## 2. 장기 — `longTermVolatilityIndex`

### 2-1. 정의

월별 지출의 **변동계수**(CV = 표준편차 ÷ 평균). 값이 클수록 달마다 들쭉날쭉하다.

안정성 점수로 옮길 때:

```
  stability = clamp( 1 − CV / cv-cap , 0, 1 )
```

| | 값 | 설정 키 |
|---|---|---|
| 최소 관측 | 3개월 | `analysis.volatility.min-months` |
| CV 상한 | **1.5** | `analysis.volatility.cv-cap` |

**1.5 인 이유.** 예전 0.6 에서는 재생성 데이터의 시작월이 부분월(가입 말일)이라 CV 가
과대계상돼(≈0.59) `stability` 가 0 으로 뭉개졌고 전원이 C/D 등급으로 몰렸다. 1.5 로 완화해
필수비율이 높은 사용자가 A/B 에 도달한다.

### 2-2. 쓰이는 곳

- **상품 추천** — 성향점수 + `overspendingCategories` + `longTermVolatilityIndex` → Top3
- **소비건전성지수** — 저축 0.4 · 안정성 0.3 · 계획성 0.3 가중합, A ≥ 85 · B ≥ 70

---

## 3. 과소비 판정

카테고리 지출 ÷ 전체 지출이 임계를 넘으면 그 카테고리를 `overspendingCategories` 에 담는다.

| 임계 | 설정 키 |
|---|---|
| **> 0.30** | `analysis.overspending.ratio-threshold` |

월평균을 낼 때는 최근 **3개월**만 본다(`analysis.baseline-months`). 창이 없으면 오래전에
고친 습관이 계속 평균에 남는다.

**카테고리별 관측 개월수는 따로 센다.** 전체 관측 개월수로 나누면 최근 시작한 습관이
과소평가된다.

## 4. 데이터 신뢰도 게이트

판정을 내려도 되는지부터 가른다. 표본이 얇으면 어떤 임계도 의미가 없다.

| 상태 | 조건 | 설정 키 |
|---|---|---|
| `ESTIMATED` | 아래 미달 | — |
| `CONFIRMED` | **30건 이상 그리고 14일 이상** | `analysis.confirmation.min-records` · `min-days` |

**건수와 기간을 AND 로 묶는 이유**: 건수만 보면 하루에 몰아 쓴 사람이 통과한다.

`카테고리없음` 소비는 **어느 판정에도 참여하지 않는다.** 무엇을 샀는지 모르는 결제를
"이상하다"고 말할 근거가 없기 때문이다.

## 5. 프록시 가정과 그 한계

이 명세서가 **가정 위에 서 있다는 것을 숨기지 않는다.**

| 가정 | 실제 | 영향 |
|---|---|---|
| 결제 시각 = 소비 시각 | 명세서에 시각이 없다. **정오(12:00)로 채운다** | 심야 축이 실데이터에서는 **작동하지 않는다**. 0시로 채우면 모든 결제가 심야가 되므로 정오가 안전한 쪽이다 |
| 사업자 등록 업종 = 실제 판매 품목 | 국세청은 **주업종만** 등록한다 | 등록이 '떡류 제조업'인데 실제로는 떡집 소매일 수 있다 → 사전에 넣지 않고 LLM·사용자 확인에 맡긴다 |
| 가맹점 = 소비처 | PG 를 거치면 어긋난다 | 번호를 버리고 이름으로 본다(§D24 1-3) |
| 카테고리 = 소비 성격 | 등록 업종과 갈리는 곳이 있다 | 배달앱(통신판매업 → 실제는 식비) — 사람이 사전에 확정으로 박는다 |
| 월 지출 CV = 소비 안정성 | 부분월·계절성을 구분하지 못한다 | `cv-cap` 으로 완화. 근본 해결은 아니다 |

**임계값은 전부 잠정이다.** 페르소나가 확정되고 실사용자 표본이 쌓이면
*"100건 중 3~5건이 이상으로 잡히는가"* 로 재역산한다. 지금 값은 그 재역산이 가능하도록
설정으로 빼 둔 것이지, 검증된 값이 아니다.

## 6. 재현성

- 엔진은 `now()` 를 직접 읽지 않는다. `Clock` · `referenceTime` 을 주입받는다(마스터 §4-3).
- 조회 정렬을 고정하고 Map 은 `TreeMap` 을 쓴다.
- 같은 데이터를 두 번 넣으면 같은 판정이 나와야 한다 — 이것이 임계를 논의할 수 있게 하는
  전제다.
