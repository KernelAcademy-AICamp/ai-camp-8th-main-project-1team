# 실사용자 자체 주입 — 최종 설계 (4판)

> **구축 완료 (2026-08-12).** 이 설계대로 전부 구현했다. 실제로 켜고 쓰는 순서는
> `reference/실사용자-자체주입-운영절차.md` 에 있다.
>
> 시험: 본체 **578건** · 제공자 **109건** · KWCAG **33/33** · 보안 회귀 **6건** — 전부 통과.
> 운영 반영: `.env` 권한 `600` · `TSA_ENABLED=true` · EBS 계정 기본 암호화 `true`.
>
> 설계와 다르게 간 것 하나 — **제공자의 신원 컬럼 암호화는 남겼다.** `matchIdentity` 의
> 정확일치 조회를 블라인드 인덱스로 옮기고 11M 행을 배치 변환해야 해서 별건으로 크다.
> 본체 쪽(intake·TOTP 비밀)은 설계대로 암호화했다.

실제 사람이 **신원 3값 + 1년치 카드 명세서**를 신청 페이지에서 내면, admin 이 승인해
마이데이터 서버에 반영되고, 그 사람이 앱에 로그인해 자기 데이터로 서비스를 쓴다.

> **4판(최종).** 1판 적재 통로 → 2판 인증 부재 발견 → 3판 보안 전면 → **4판 화면·API·파이프라인
> 포함.** 전례: 2026-08-05 실제 사람 1명 750건 운영 반영(마스터 §13-12·§13-13).

## 1. 무엇을 만드는가 — 한 장 요약

**화면 4개** (전부 사용자 앱과 **별도 번들**)

| # | 화면 | 누가 | 인증 |
|---|---|---|---|
| ① | **신청** — 신원 3값 + 명세서 업로드 | 실사용자 | **없음**(초대코드로 게이트) |
| ② | **칸 지정** — 자동 인식 실패 시 폴백 | 실사용자 | 없음 |
| ③ | **admin 로그인** | admin | — |
| ④ | **admin 대기 목록·승인** | admin | HttpOnly 쿠키 |

**기존 앱 화면은 하나도 고치지 않는다.** `Auth.tsx` 도 그대로다.

**API 6개**

```
POST /api/apply                        신청 접수      (초대코드 · 비로그인)
GET  /api/apply/{ticket}               내 신청 상태   (접수증 번호로)
POST /api/admin/login                  admin 로그인
GET  /api/admin/intake                 대기 목록(요약)
POST /api/admin/intake/{id}/approve    승인 → 반영
POST /api/admin/intake/{id}/reject     거부
```

**핵심 결정 — 승인은 한 번이다.** 신원 등록과 명세서 적재를 **한 배치**에 담는다.
사용자가 로그인하려면 제공자에 신원이 있어야 하는데, 신원 등록이 승인을 기다리면 로그인을
못 해 업로드도 못 한다. **그래서 로그인 전에 둘을 한꺼번에 받는다.**

## 2. 조사로 확인된 사실

전부 실측이다.

| 항목 | 현재 | 판정 |
|---|---|---|
| **API 인증** | 없음. `?userId=999999` → **404**(401 아님) | **치명** |
| **admin 계정** | 없음. 비밀번호·역할 개념 자체가 없음 | 신설 |
| **SQL Injection** | `nativeQuery=true` **0건** · `createNativeQuery` **0건** | **양호** — 회귀만 막으면 된다 |
| **포트 노출** | 80·443 공개 · 22 는 `121.138.185.112/32`(KT 사무실) · **8082 미발행**(`internal:true`) | **양호** |
| **번들 노출** | 화면 id 가 그대로 보인다(`boot`,`walk`,`auth`,…). 소스 문자열도 minify 후 그대로 | **별도 번들 필요** |
| **컬럼 암호화** | 없음(`AttributeConverter`·`Cipher`·`AES` 검색 0건) | 필요 |
| **EBS 볼륨** | `Encrypted: False` · `KmsKeyId: None` (40GB). 계정 기본값도 `false` | 필요 |
| **덤프** | `mysqldump \| gzip -1` — 압축이지 암호화가 아니다 | 필요 |
| **S3 덤프 버킷** | `AES256` · 퍼블릭 차단 `True` | 양호 |
| **`/opt/finntech/.env`** | **`644 root:root`** — 서버의 아무 사용자나 읽는다. `MYSQL_ROOT_PASSWORD` 포함 | **즉시 `600`** |
| **본체↔제공자** | 평문 HTTP | TLS 필요 |
| **레이트리밋** | 없음 | 필요 |
| **감사 계층 1·2** | `AuditService`+`Hashing`+`CanonicalJson` 있음 | **재사용** |
| **감사 계층 3** | `TsaClient` 있으나 운영 **`TSA_ENABLED=false`** | **켠다** |
| **앵커 외부 사본** | 없음. TSA 토큰이 **위조 대상과 같은 DB** 에 있다 | **필요** |
| **KMS** | `alias/finntech*` 없음. 인스턴스 역할은 `finntech-ec2-ssm`(SSM 전용) | 신설 |
| **저장소 유출** | `.gitignore` + 스크립트 가드 + CI `check_no_real_numbers.py` | **양호** |

**요약**: 망과 SQL 계층은 튼튼하다. 뚫려 있는 것은 **인증**, 없는 것은 **암호화**,
그리고 **감사 계층 3이 꺼져 있다.**

## 3. 전체 흐름

```
[실사용자]  ① 신청 페이지 (비로그인)
              초대코드 · 이름 · 주민앞7 · 전화 · 명세서 파일
              └ 브라우저에서 파싱 → 미리보기 → 제출     원본 파일은 전송하지 않는다
                     │ HTTPS
                     ▼
[본체]      ② 권위 검증(양식 화이트리스트·상한)
              ③ KMS 로 암호화해 intake 에 저장
              ④ 감사 기록  INTAKE_RECEIVED
              ⑤ 사용자에게 접수증 번호 발급
                     │
                     ▼
[admin]     ⑥ /ops-xxxx/ 로그인 (Argon2id + TOTP)   ← URL 직접 입력만
              ⑦ 대기 목록 — 요약만 본다
              ⑧ 승인
                     │
                     ▼
[본체]      ⑨ 복호화 → 재검증 → 감사 INTAKE_APPROVED
              ⑩ 내부 TLS + 공유 시크릿
                     ▼
[제공자]    ⑪ 또 검증 → mydata_user(신원) + mydata_payment(결제)
                     │
                     ▼
[본체]      ⑫ 감사 INTAKE_IMPORTED → intake 행 **삭제**
                     │
                     ▼
[실사용자]  ⑬ 앱에서 평소대로 본인인증 → 이제 통과한다
              ⑭ 카드사 연결 → 분류 사슬 → 리포트
              ⑮ 미분류 정리(기존 화면) — 본인이 확정
```

**세 번 검증한다.** 브라우저는 UX 용이라 신뢰하지 않고, 제공자는 본체도 신뢰하지 않는다.

## 4. 화면 설계

### 4-0. 번들을 가른다 — 이것이 전제다

번들을 열어보니 화면 id 가 그대로 보인다(`boot`,`walk`,`auth`,…). 같은 SPA 에 라우트를
추가하면 **모든 방문자의 JS 에 그 이름이 들어간다.** 그래서 진입점을 셋으로 나눈다.

```
dist/index.html  + assets/index-*.js    사용자 앱      (지금 그대로)
dist/apply.html  + assets/apply-*.js    신청 화면 ①②
dist/admin.html  + assets/admin-*.js    admin 화면 ③④   ← 사용자에게 전달되지 않는다
```

Vite `rollupOptions.input` 에 진입점 셋을 넣으면 된다. 지금 `vite.config.ts` 가 6줄이라
손댈 것도 적다. **데모가 끝나면 nginx 에서 그 두 `location` 만 빼면 사라진다.**

### 4-1. ① 신청 화면 (실사용자 · 비로그인)

```
┌─────────────────────────────────────────────┐
│  내 카드 명세서로 MOA 써보기                 │
│                                             │
│  초대코드   [____________]                  │
│  ─────────────────────────────────          │
│  이름       [__________]                    │
│  주민번호   [______] - [_]  앞 7자리만       │
│  휴대폰     [___-____-____]                 │
│                                             │
│  명세서 파일  [ 파일 선택 ]  CSV            │
│      카드사에서 받을 때 **사업자번호 칸을    │
│      포함**해 주세요 — 없으면 분류가 안 돼요 │
│                                             │
│  ☐ 개인(신용)정보 수집·이용에 동의  [전문]   │
└─────────────────────────────────────────────┘
```

파일을 고르면 **브라우저 안에서 파싱**하고 아래에 미리보기를 편다.

```
┌─ 이렇게 읽었어요 ───────────────────────────┐
│  날짜 ← "거래일"      가맹점 ← "가맹점명"    │
│  금액 ← "이용금액"    사업자번호 ← "사업자번호"│
│                            [칸이 틀렸어요 →] │
│  ─────────────────────────────────          │
│  결제        1,247건                        │
│  기간        2025-08-01 ~ 2026-07-31        │
│  합계        18,432,100원                   │
│  취소·환불   23건  −1,204,000원             │
│  사업자번호  1,101건 (88%) · 고유 312곳      │
│  못 읽은 줄  3건                            │
│     12행  날짜를 못 읽음: 2025.13.45        │
│     88행  금액을 못 읽음: -                 │
│    903행  칸이 3개 미만                     │
│                                             │
│              [ 신청하기 ]                   │
└─────────────────────────────────────────────┘
```

**설계 근거**

- **자동 인식이 성공했을 때도 무엇을 어느 칸으로 읽었는지 보여준다.** 조용히 맞히는 것과
  조용히 틀리는 것이 화면에서 똑같아 보이면 안 된다(§8-U).
- **못 읽은 줄을 줄 번호와 사유로** 보여준다. 조용히 건너뛰면 "다 들어갔다"와
  "절반만 들어갔다"가 구분되지 않는다.
- **사업자번호 비율을 크게 띄운다.** 없으면 전 건이 '카테고리없음' 이 되어 ML 판정에서
  빠진다. 낮으면 제출 전에 다시 받아오게 해야 한다.
- **원본 파일은 전송하지 않는다.** 5칸으로 줄인 텍스트만 보낸다. 받지 않은 것은 지울 필요도 없다.
- 동의는 `legal/privacy-policy.md` **3항 전문**을 편다(카드 승인 상세·가맹점명·사업자등록번호·거래내역).

**제출 후**

```
접수됐어요.  접수증  A7F3-2K91
검토 후 반영되면 문자로 알려드릴게요.
이 번호로 진행 상태를 볼 수 있어요.   [상태 보기]
```

접수증 번호로만 상태를 조회한다(`GET /api/apply/{ticket}`). **계정이 아직 없으므로 로그인이 없다.**
상태는 `접수됨 → 반영됨 / 반려됨` 셋뿐이다.

### 4-2. ② 칸 지정 화면 (폴백)

자동 인식이 실패했을 때만 뜬다. **지금 `import-realperson.py` 는 머리글을 못 찾으면
`sys.exit` 로 끝나는데, 사용자에게는 그것이 막다른 길이다.**

```
┌─ 어느 칸이 무엇인지 알려주세요 ─────────────┐
│                                             │
│      A          B         C         D       │
│  ┌─────────┬─────────┬────────┬──────────┐  │
│  │2025.08.01│스타벅스…│  5,600 │123-45-…  │  │
│  │2025.08.01│GS25 …   │  3,200 │234-56-…  │  │
│  │   …      │   …     │   …    │   …      │  │
│  └─────────┴─────────┴────────┴──────────┘  │
│         (첫 30줄)                           │
│                                             │
│  날짜       [ A ▾ ]                         │
│  가맹점     [ B ▾ ]                         │
│  금액       [ C ▾ ]                         │
│  사업자번호 [ D ▾ ]  (없으면 '없음')         │
│                                             │
│              [ 이대로 읽기 ]                │
└─────────────────────────────────────────────┘
```

**고른 배치를 별칭표에 되먹이지 않는다.** 한 사람의 파일 사정을 전체 규칙으로 승격시키면
다음 사람에게서 엉뚱한 칸을 집는다. 별칭표는 사람이 검토해서 넓힌다.

별칭표는 **JSON 한 벌**로 두고 Python(`import-realperson.py`)과 TS 가 같이 읽는다.
베껴 쓰면 두 벌이 갈라진다.

### 4-3. ③ admin 로그인

**접근은 URL 직접 입력만.** 앱 어디에도 링크·버튼·매직 문자열이 없다.

> **매직 문자열은 채택하지 않는다.** 온보딩 이름 칸에 `MOAdmin` 같은 값을 넣어 이동시키는
> 방식은 ⓐ 그 문자열이 **모든 방문자의 JS 에 들어가고**(minify 해도 리터럴은 남는다 — 실측으로
> `"한국통신사업자연합회"`·`"link-synthetic"` 이 번들에서 그대로 검색된다) ⓑ **CI 를 만드는
> 인증 경로에 특수 케이스**를 심으며 ⓒ 같은 번들이라야 하므로 **번들 분리가 무너진다.**

```
┌─────────────────────────┐
│  MOA 운영                │
│                         │
│  계정   [___________]   │
│  비밀번호 [___________] │
│  인증번호 [ ______ ]    │
│           앱의 6자리     │
│                         │
│        [ 로그인 ]       │
└─────────────────────────┘
```

**비밀번호와 TOTP 를 한 화면에서 같이 받는다.** 단계를 나누면 *"비밀번호는 맞았고 TOTP 만
틀렸다"* 를 알려주는 셈이고, 그것은 비밀번호를 확인해 주는 것이다.

실패는 **무엇이 틀렸든 같은 문구** — *"로그인할 수 없습니다."* 계정 열거를 막는다.

> **함정**: 지금 `server.error.include-message: always` 라 서버 메시지가 화면에 그대로 나간다
> (2026-08-06 에 403 원인을 알려고 의도적으로 켰다). **이 경로만은 메시지를 고정한다.**

nginx 는 한 블록이다.

```nginx
location /ops-xxxxxxxx/ {
  add_header Cache-Control "no-store";
  add_header X-Robots-Tag "noindex, nofollow";
  limit_req zone=adminlogin burst=5 nodelay;
  try_files $uri /admin.html;
}
```

**경로 값은 저장소에 적지 않는다** — `.env`·배포 설정에 둔다(`INDUSTRY_LOOKUP_URL` 을
저장소에 안 적은 것과 같은 이유). 그리고 **경로 숨김은 방어가 아니라 소음 감소**로만 계산한다.
API 는 어차피 열려 있고, 방어는 Argon2id·TOTP·지연·쿠키·감사가 진다.

### 4-4. ④ admin 대기 목록 — 요약만 본다

```
┌─ 대기 중 2건 ──────────────────────────────────────────┐
│                                                        │
│  #7   홍○동   접수 2026-08-12 14:03   [초대코드 OK]     │
│       신원      제공자에 없음 → 신규 등록 필요           │
│       결제      1,247건 · 2025-08-01~2026-07-31         │
│       합계      18,432,100원   취소 23건 −1,204,000원   │
│       사업자번호 1,101건 (88%) · 고유 312곳              │
│       사전 예측  씨앗 겹침 214건                        │
│       못 읽은 줄 3건                                    │
│       기존 적재  0건                                    │
│                              [ 승인 ]   [ 반려 ]        │
│  ────────────────────────────────────────────────────  │
│  #8   김○수   접수 2026-08-12 15:20   [초대코드 OK]     │
│       …                                                │
└────────────────────────────────────────────────────────┘
```

**건별 목록을 보여주지 않고, 원문 열람 경로를 아예 만들지 않는다.** 승인이 판정하는 것은
*"이 배치가 정상적인 명세서인가"* 지 *"이 사람이 무엇을 샀는가"* 가 아니다. 남의 소비내역
전체를 admin 이 열람하는 것은 **그 자체가 개인정보 처리**다.

이름도 마스킹한다(`홍○동`) — 승인에 필요한 것은 "누구인지"가 아니라 "어떤 배치인지"다.

**반려 사유도 기계적 지표로만** 고른다(못 읽은 줄 과다 · 기간 이상 · 건수 이상 · 사업자번호 부족).
자유 입력을 두지 않는다 — 내용에 관한 사유를 쓰면 내용을 봤다는 뜻이 된다.

**승인 후 결과 화면**

```
  결제   신규 1,224건 · 거부 23건 · 사업자번호 실림 1,101건
  감사   seq 41,882  INTAKE_IMPORTED
  ※ 사용자가 앱에서 본인인증 후 카드사 연결을 해야 화면에 보입니다.
```

## 5. API 계약

### 5-1. 신청 (비로그인)

```
POST /api/apply
  { inviteCode, name, social7, phone, csv, consent:true }
  → 201 { ticket:"A7F3-2K91" }
  → 404  초대코드 불일치           ← 401 이 아니다. 경로의 존재를 알리지 않는다
  → 422  { problems:[{line,reason}] , accepted, rejected }

GET /api/apply/{ticket}
  → { status:"RECEIVED"|"IMPORTED"|"REJECTED", reason? }
```

`ticket` 은 무작위이며 **신원을 담지 않는다.** 그 번호를 아는 사람만 자기 신청 상태를 본다.

### 5-2. admin

```
POST /api/admin/login      { id, password, totp }
  → 200  Set-Cookie: admin_session=…; HttpOnly; Secure; SameSite=Strict; Path=/api/admin
  → 401  { "message":"로그인할 수 없습니다." }     ← 항상 같은 문구

GET  /api/admin/intake                    대기 목록(요약만)
POST /api/admin/intake/{id}/approve       → 아래 §6
POST /api/admin/intake/{id}/reject        { reasonCode }
POST /api/admin/logout                    쿠키 폐기 + 토큰 행 삭제
```

**admin 토큰은 HttpOnly 쿠키다.** 실사용자 토큰(`X-Auth-Token` 헤더 + localStorage)과 다르다 —
XSS 가 있어도 `document.cookie` 로 못 꺼낸다. `Path=/api/admin` 이라 사용자 API 요청에는
아예 실리지 않는다.

## 6. 승인 → 마이데이터 반영 (핵심 파이프라인)

```
POST /api/admin/intake/{id}/approve
 │
 ├ 1. intake 행을 잠근다 (SELECT … FOR UPDATE)      두 admin 의 동시 승인 방지
 ├ 2. KMS DEK 로 CSV 복호화
 ├ 3. 재검증 — 양식 화이트리스트를 여기서 또 돌린다   저장 시점과 별개다
 ├ 4. 감사  append("INTAKE_APPROVED", {intakeId, adminId, rows, ci8})
 │
 ├ 5. 제공자 호출 (내부 TLS + X-MyData-Token)
 │      POST /self/person        신원 → mydata_user(CI, dataSplit=SERVICE, persona=null) + 카드 1장
 │      POST /self/payments/csv  결제 → mydata_payment (id = real-<ci8>-<yyyymmdd>-<줄번호>)
 │
 ├ 6. 결과 수신 {ci, cardId, accepted, rejected, backfilled, withBusinessNumber}
 ├ 7. 감사  append("INTAKE_IMPORTED", {결과})
 └ 8. intake 행 **삭제** (암호문 포함).  대기열은 창고가 아니라 통로다
```

### 6-1. 왜 제공자에 넣어야 하는가 — 우회로가 없다

`MyDataLinkService.linkCardCompanies` 는 연동할 때마다
`userPaymentRepository.deleteByUserId(userId)` 로 **결제를 통째로 지우고 다시 만든다.**
본체에만 넣으면 사용자가 카드 연결을 한 번 다시 하는 순간 **1년치가 증발한다.**

### 6-2. 제공자 입구의 성질을 가른다

**`/admin/realdata` 는 계속 닫아둔다**(`MYDATA_REALDATA_ENABLED=false`). 인증이 없고 본문의
CI 를 그대로 믿는 무방비 입구다. 새 입구는 다르다.

| | `/admin/realdata`(닫힌 채) | `/self/**`(새로) |
|---|---|---|
| 인증 | 없음 | **공유 시크릿 + 내부 TLS** |
| 호출자 | 아무나 | **본체만**, 그것도 **승인된 intake 만** |
| 대상 CI | 본문 — 아무 사람이나 | intake 의 소유자 |

- **`MyDataSharedSecretFilter` 의 경로를 넓힌다** — `startsWith("/bank/")` → `/bank/` **또는**
  `/self/`. 지금 `/admin/realdata` 가 필터 밖이라 무방비인 빚도 같은 자리에서 갚는다.
- 본체 → 제공자 **쓰기는 3개로 고정**(등록·적재·파기). 늘리지 않는다 — 늘어나는 순간
  "본체는 제공자에서 읽기만 한다"(`MyDataClient` 14개 전부 `client.get()`)는 성질이 사라진다.
- **프록시는 통과가 아니라 번역이다.** 검증·정규화한 5칸만 넘긴다. 원문을 그대로 흘리면
  그건 프록시가 아니라 터널이다.

### 6-3. 재시도가 안전한 이유

결제 id 가 `real-<ci앞8>-<yyyymmdd>-<줄번호>` 로 **결정론**이라, 같은 배치를 두 번 넣어도
행이 두 배가 되지 않는다. 이미 있으면 건너뛰되 **사업자번호가 비어 있으면 채운다**(backfill) —
그냥 건너뛰면 번호를 붙여 다시 올려도 `accepted=0` 만 뜨고 영영 `null` 로 남는다.

### 6-4. 반영 후 — 사용자가 할 일

적재는 **제공자까지**다. 본체 화면에 보이려면 사용자가:

1. 앱에서 평소대로 **본인인증** — 이제 제공자에 신원이 있으니 통과한다
2. **카드사 연결** — `linkCardCompanies` 가 결제를 당겨오며 분류 사슬을 태운다
3. **미분류 정리**(기존 `m-unclassified`) — 본인이 확정한다

### 6-5. 분류가 죽지 않게

- **사업자번호가 생사를 가른다.** 없으면 전 건 '카테고리없음' → ML 판정 제외.
  업종코드가 없는 것은 정상이지만(실 명세서엔 대개 없다) 사업자번호는 있어야 사전이 붙는다.
- **한 번의 연동으로 다 안 붙는다** — ②-b 등록업종조회가 `max-per-sync: 40` 이다.
  1년치 × 여러 명이면 처음 보는 가맹점이 수백 곳이다. 적재 직후 자동 반복하거나 상한을 올린다.
- 운영은 `INDUSTRY_LOOKUP_ENABLED=true` 지만 **로컬 `.env` 에는 그 키가 없다** →
  로컬 검증은 ②-b 가 꺼진 채로 돈다. 운영보다 분류가 나쁘게 나오는 것을 알고 봐야 한다.

## 7. 보안 설계

### Phase 1 — 인증·인가

**실사용자** — 비밀번호를 만들지 않는다. `AuthService.verifyAssumed` 가 이미 신원을 확인하고
`userId` 를 돌려주므로, 거기서 **토큰을 하나 더 돌려주면 그것이 로그인**이다.

- 불투명 랜덤 32바이트. JWT 는 안 쓴다(폐기가 어렵고 시크릿 관리가 는다)
- **DB 에는 토큰이 아니라 토큰의 해시(SHA-256)를 저장한다.** DB 가 유출돼도 그 값으로는
  로그인할 수 없다
- 만료 30일 · 로그아웃 시 행 삭제(이미 만든 로그아웃 버튼과 맞물린다)

**admin**

| 층 | 조치 |
|---|---|
| 비밀번호 | **Argon2id** (OWASP: m=19456 KiB, t=2, p=1) |
| 의존성 | `spring-security-crypto` **단독**. 전체 스타터는 안 들인다. Argon2 가 요구하는 BouncyCastle 은 **이미 있다**(`bcpkix-jdk18on`, RFC 3161 용) |
| 2단계 | **TOTP**(§7-1). IP 허용목록을 쓰지 않으므로 **유일한 2차 방어** |
| 세션 | **30분** + 활동 시 갱신. HttpOnly 쿠키 |
| 무차별 대입 | **IP 단위 지연**(§7-2). **계정을 잠그지 않는다** |
| 계정 수 | **2개 이상**. 단일 계정은 단일 실패점. 공용 계정 금지 — 누가 승인했는지가 남아야 한다 |
| 복구 | 백업 코드 8개 + **SSM 우회 경로** |

> **IP 허용목록은 채택하지 않는다.** 지금 SSH 에 열린 `121.138.185.112` 는 AWS 가 아니라
> **KT(KORNET) — 사무실 IP** 다. 사무실 고정이라 쓸 수는 있으나 admin 이 다른 곳에서
> 승인해야 할 때 잠긴다.

**인가 — 컨트롤러 43개를 고치지 않는다.** `userId` 를 받는 엔드포인트가 43개(컨트롤러 19개)
지만 `OncePerRequestFilter` 한 겹이면 된다.

```
1. X-Auth-Token(사용자) 또는 admin_session 쿠키(admin) → 토큰 해시로 조회
2. 만료·미존재 → 401
3. role=USER  : 요청의 userId 파라미터·경로변수와 대조, 다르면 403
   role=ADMIN : /api/admin/** 만 허용
4. 화이트리스트 통과: /actuator/health · /api/privacy/** · /api/mydata/verify
                     · /api/mydata/companies · /api/analytics/track
                     · /api/apply · /api/apply/{ticket} · /api/admin/login
```

프론트는 `api.ts` 의 `request()` **한 곳**에 헤더를 추가하면 끝이다(`fetch` 호출 지점 2곳).

#### 7-1. TOTP 상세

**원리**: 서버와 폰이 **통신하지 않고** 각자 계산한다. 같은 비밀 + 같은 시각(30초 단위) →
HMAC-SHA1 → 6자리. 폰이 비행기모드여도 코드가 나온다.

**등록(1회)**: 서버가 무작위 20바이트 생성 → `otpauth://totp/MOA:admin1?secret=…&issuer=MOA`
를 QR 로 표시 → 인증 앱으로 스캔 → **지금 뜬 6자리를 입력해 동작을 확인한 뒤** 확정 →
**QR 은 다시 보여주지 않는다**

**검증(매 로그인)**: 비밀번호 확인 → 6자리 확인(시계 오차 대비 **앞뒤 1구간 ±30초** 허용) →
**성공한 구간 번호를 저장**한다. 이게 빠지면 어깨너머로 본 코드를 30초 안에 재사용할 수 있다.

**비밀의 보관**: 검증에 원문이 필요하므로 **해시가 아니라 양방향 암호화**다.

```
admin 비밀번호  →  Argon2id (단방향 — 되돌릴 필요가 없다)
TOTP 비밀       →  AES-GCM  (양방향 — 계산에 원문이 필요하다)
인증 토큰       →  SHA-256  (단방향)
```

Phase 2 의 KMS envelope 으로 감싼다. **이 비밀이 새면 2FA 가 무력화되므로 비밀번호 해시와
같은 무게로 다룬다.**

**복구 코드**: 없으면 폰 분실이 곧 영구 잠금이다. 일회용 8개를 종이로 보관하게 하고
DB 에는 **해시만** 저장한다. 하나 쓰면 그 행을 지운다.

**구현 비용**: HMAC-SHA1 은 JDK 표준(`javax.crypto.Mac`)이라 계산은 30~50줄.
QR 주소에 필요한 **Base32 만 JDK 에 없다**(Base64 는 있다) — BouncyCastle 에 있는지 확인하고
없으면 20줄쯤 직접 쓴다. **새 의존성 없이 가능할 것으로 본다.**

#### 7-2. 무차별 대입 — 계정을 잠그지 않는다

**잠금은 그 자체가 공격 수단이다.** 공격자가 admin 계정에 일부러 틀린 비밀번호를 반복하면
계정이 잠기고 **승인이 멈춘다.**

| | 잠금 | **지연** ← 채택 |
|---|---|---|
| 동작 | N회 실패 → 계정 사용 불가 | N회 실패 → 그 **IP 의 응답만** 느려짐 |
| 무차별 대입 | 막음 | 막음 |
| **DoS** | **가능** | **불가능** |

- **대상은 계정이 아니라 IP.** 계정 단위로 세면 아무 IP 에서나 남의 계정을 잠글 수 있다.
- IP 를 바꾸면 카운터가 초기화되지만 문제되지 않는다 — Argon2id 가 한 번에 50~100ms 를
  쓰므로 전체 속도가 이미 느리다.
- **타이밍 공격 차단**: 계정이 없어도 **더미 해시를 계산**해 응답 시간을 맞춘다.
  건너뛰면 빨리 응답해 계정 존재가 드러난다.
- 실패는 **감사에 남긴다.**
- nginx `limit_req` 로 애플리케이션에 닿기 전 한 겹 더.

### Phase 2 — 개인정보 암호화

**경계를 흐리면 서비스가 성립하지 않는다.**

| 대상 | 처리 | 이유 |
|---|---|---|
| 이름 · 주민앞7 · 전화 · `app_user.nickname` | **양방향**(AES-256-GCM) | 신원 식별자. 유출 시 즉시 사람을 특정한다 |
| admin 비밀번호 · 인증 토큰 · 복구 코드 | **단방향** | 되돌릴 필요가 없다 |
| TOTP 비밀 · intake 의 CSV | **양방향** | 계산·적재에 원문이 필요하다 |
| **가맹점명 · 금액 · 일시** | **하지 않는다** | 분류·집계·ML 이 전부 이 값을 읽는다. 암호화하면 서비스가 불가능하다 |
| 사업자번호 · 업종코드 · 카테고리 | 하지 않는다 | 가맹점의 것이거나 일반 데이터다 |

거래내역은 대신 **접근 통제(Phase 1) + EBS·전송·덤프 암호화(Phase 4)** 로 보호한다.

**Envelope encryption (KMS)**

```
KMS CMK  alias/finntech-pii
   │ GenerateDataKey
   ▼
 DEK (AES-256) ──암호화──▶ 컬럼 값
   │
 암호화된 DEK 는 설정에 · 복호화된 DEK 는 메모리 캐시(TTL)
```

키가 코드·저장소·`.env` 어디에도 평문으로 없다. 회전이 되고 CloudTrail 에 사용 기록이 남는다.
인스턴스 역할 `finntech-ec2-ssm` 에 `kms:GenerateDataKey`·`kms:Decrypt` 를 **그 키 하나에만**
붙인다.

**검색이 깨지는 문제 — 블라인드 인덱스**

`MyDataService.matchIdentity` 는 정확일치로 조회한다.

```java
userRepository.findByPhoneNumber(normalized);
userRepository.findByNameAndSocial7(name, social7);
```

암호화하면 **본인인증이 통째로 못 돈다.** 그래서 조회용 컬럼을 따로 둔다 —
`HMAC-SHA256(pepper, 정규화값)`. 그 컬럼에 인덱스를 걸고 조회는 그것으로, 원문은 AES-GCM
(랜덤 IV)으로 따로 저장한다. **결정론 암호화(고정 IV)는 쓰지 않는다** — 같은 값이 같은
암호문이 되어 빈도 분석에 노출된다. 정규화 규칙은 `Ci.of` 와 **같은 것**을 쓴다.

**마이그레이션**: ① 새 컬럼 추가(암호문·블라인드 인덱스) ② 배치로 채움 ③ 읽기 전환
④ **확인 후** 평문 컬럼 삭제 — 별도 마이그레이션으로. **규칙 3**: 적용된 마이그레이션은
고치지 않는다. 전부 새 번호로 추가한다.

### Phase 3 — 양식 강제

**정해진 양식 외에는 어떤 것도 DB 에 닿지 않는다.**

| 칸 | 규칙 | 위반 시 |
|---|---|---|
| 날짜 | 6표기만(`yyyy-MM-dd` `yyyy.MM.dd` `yyyy/MM/dd` `yyyyMMdd` `yy-MM-dd` `yy.MM.dd`). 미래 거부. 과거 상한 3년 | 줄 거부 + 사유 |
| 가맹점 | 길이 ≤ 60. 제어문자 거부. 앞뒤 공백 제거 | 줄 거부 |
| 금액 | 정수(음수 허용 — 취소·환불). 절대값 상한 | 줄 거부 |
| 업종코드 | 숫자 6자리 또는 빈칸 | 빈칸 처리(`642004`) |
| 사업자번호 | 숫자 10자리 정확히 | **버린다**(`null`) — 잘린 번호는 사전을 엉뚱한 사업자에 붙인다 |
| 이름 | 한글·영문, 길이 ≤ 40 | 접수 거부 |
| 주민앞7 | 숫자 7, 날짜로 유효 | 접수 거부 |
| 전화 | `Msisdn` 국번 실존 검사 | 접수 거부 |

**전체 상한**: 행 수 · 총 바이트 · 초대코드당 1일 신청 횟수.

**취소·환불(음수)은 그대로 받는다.** 버리면 안 쓴 돈이 소비로 잡힌다 — 한 명세서에서만
59건 246만원이 그렇게 부풀려져 있었다(2026-08-05 실측). 짝을 찾아 원결제를 지우지 않는다.

### Phase 4 — 인프라 암호화

| 항목 | 방법 | 비고 |
|---|---|---|
| **`.env`** | **즉시 `chmod 600`** → 이후 SSM Parameter Store(SecureString) | 지금 `644` 라 서버의 아무 사용자나 `MYSQL_ROOT_PASSWORD` 를 읽는다 |
| **EBS** | ① 계정 기본 암호화 켜기 → 이후 생성분 자동 ② 기존 볼륨: 스냅샷 → **암호화 복사** → 교체 | **다운타임**. 인스턴스 교체와 묶는다 |
| **본체↔제공자** | TLS(자체서명 + 본체가 CA 신뢰), 나아가 mTLS | 지금 평문 HTTP |
| **덤프** | `gzip` 뒤에 암호화 한 겹 | 복원 절차에 복호화 한 줄 |
| **S3** | 이미 `AES256` + 퍼블릭 차단. SSE-KMS 로 올리면 키 사용 감사까지 | 선택 |

### Phase 5 — 감사·공격 대응

| 위협 | 조치 |
|---|---|
| SQL Injection | 지금 표면이 없다. **CI 검사로 고정** — `nativeQuery=true`·`createNativeQuery`·문자열 연결 SQL 이 들어오면 빌드 실패 |
| 계정 탈취 | Argon2id · TOTP · IP 지연 · 세션 30분 · HttpOnly 쿠키 |

| 권한 상승 | 필터가 role 강제. admin 은 사용자 API 를 못 부른다 |
| 대량 주입 | 행 수·용량·1일 횟수 상한 |
| 정보 노출 | admin 로그인 경로는 **메시지 고정**. 계정 열거·단계 확인 차단 |

#### 7-3. 감사 사슬을 진짜로 못 고치게 만든다

**지금 뚫려 있는 것.** 계층 1(해시체인)은 한 줄 수정을 막지만 **전체 재작성**은 못 막는다.
그것을 막는 계층 3(TSA 앵커)이 —

1. 운영에서 **`TSA_ENABLED=false`** 다. 안 돌고 있다.
2. 켜도 TSA 토큰이 `audit_batch`, 즉 **위조 대상과 같은 DB** 에 있다. 공격자가 DB 를 갈아엎고
   **새 ROOT 로 도장을 새로 받아 바꿔치기하면 통과한다.**

> **타임스탬프는 "존재 증명"이지 "유일성 증명"이 아니다.** *"이 데이터가 이 시각에 있었다"* 는
> 증명하지만 *"이것 말고 다른 버전은 없었다"* 는 증명하지 못한다.
> 다만 **과거로 되돌리는 위조는 원천적으로 불가능하다** — 시각은 TSA 가 자기 시계로 찍고
> 그것을 바꾸려면 TSA 의 비밀키가 있어야 한다. 공격자가 할 수 있는 것은 "전부 오늘 것으로
> 새로 만들기"뿐이라, **밖에 옛 도장이 남아 있으면 즉시 드러난다.**

**조치 넷**

| # | 조치 | 효과 |
|---|---|---|
| 1 | **`TSA_ENABLED=true`** | 계층 3을 실제로 돌린다 |
| 2 | **앵커 사본을 S3 Object Lock 에** | 아래 |
| 3 | 앱 DB 계정에서 감사 테이블 `UPDATE`·`DELETE` 회수(`INSERT` 만) | 앱을 통한 위조 차단 |
| 4 | EC2 역할에 앵커 버킷 **`s3:PutObject` 만** | **서버가 털려도 자기가 쓴 것을 읽지도 지우지도 못한다** |

```
전용 버킷(신설) — 배포용과 섞지 않는다
  버저닝      필수(Object Lock 의 전제)
  모드        Compliance   ← Governance 는 권한자가 지울 수 있어 내부자에게 안 통한다
  보존기간    N년          ← 되돌릴 수 없다. 신중히
  기본 암호화 SSE-KMS
```

넣는 것(배치당 수십 KB): `batchId` · `fromSeq`/`toSeq` · `batchRoot` · `prevBatchRoot` ·
`tsaGenTime` · `tsaName` · **`tsaResponse` 원문**. 원문을 넣어야 우리 코드 없이
`openssl ts -verify` 로 독립 검증이 된다.

**감사에 남길 사건**: `INTAKE_RECEIVED` · `INTAKE_APPROVED` · `INTAKE_REJECTED` ·
`INTAKE_IMPORTED` · `ADMIN_LOGIN` · `ADMIN_LOGIN_FAILED` · `SUBJECT_ERASURE`(기존).
`AuditService.append()` 호출 한 줄이면 같은 사슬에 들어간다.

## 8. 만드는 순서

```
Phase 1  인증·인가            ← 지금 실제로 뚫려 있는 유일한 구멍. 나머지의 전제
Phase 2  개인정보 암호화       ← intake 에 실 개인정보를 담으려면 선행
Phase 3  신청·승인 파이프라인   ← 1·2 위에 선다. 화면 4개 + API 6개
Phase 4  인프라 암호화         ← 재기동이 필요해 다른 재기동과 묶는다
Phase 5  감사·공격 대응        ← 상시. `chmod 600` 과 `TSA_ENABLED=true` 는 지금 당장
```

**Phase 1 을 앞에 두는 이유는 신청 기능 때문이 아니다.** 운영에 실제 사람 750건이 이미
`?userId=N` 으로 열람되는 상태다. 신청과 무관하게 지금 열려 있다.

**Phase 4 를 뒤에 두는 이유**: 디스크·내부망 암호화는 서버 침투를 전제한 방어인데, 지금은
443 으로 걸어 들어와 `?userId=` 만 바꾸면 된다. **가장 쉬운 경로를 먼저 막는다.**

**지금 당장 할 수 있는 둘**: `chmod 600 /opt/finntech/.env` · `TSA_ENABLED=true`.

## 10. 열린 결정

1. **거래내역 암호화 경계** — 이 문서는 가맹점명·금액을 평문으로 둔다(암호화하면 분류·ML 불가).
2. **xlsx 지원** — CSV 만 받고 시작할지(프론트 의존성 지금 `react`·`react-dom` 둘뿐),
   처음부터 브라우저 파서를 들일지.
3. **초대코드 vs 허용 명단** — 5명을 넘어가면 명단이 낫다.
4. **Object Lock 보존기간** — 되돌릴 수 없으므로 먼저 정한다.
5. **EBS 교체 시점** — 다운타임을 언제 낼 것인가.
6. **admin 경로 문자열** — 저장소에 적지 않고 `.env` 에 둔다. 값을 정해야 한다.
7. **신청 결과 통지 수단** — 문자(SOLAPI)인지 화면 조회(접수증)만인지.

**정해진 것**: admin 승인 모델 · 승인은 **배치 단위 한 번**(신원+명세서 함께) ·
2FA 는 **TOTP**(IP 허용목록 미채택) · **잠금 아닌 IP 지연** · admin 계정 **2개 이상** ·
**별도 번들 3개** · admin 접근은 **URL 직접 입력만**(매직 문자열 미채택) · `TSA_ENABLED=true`.

## 11. 검증

**Phase 1** ① 남의 userId 조회 **403** ② 토큰 없이 **401**, 화이트리스트 **200**
③ 로그아웃 후 같은 토큰 **401** ④ admin 토큰으로 사용자 API **403**
⑤ 같은 TOTP 코드 재사용 → **거부** ⑥ 한 IP 반복 실패 → **그 IP 만** 느려지고 다른 IP 의
admin 은 정상 ⑦ 없는 계정과 있는 계정의 **응답 시간이 같은지** ⑧ 로그인 실패가 감사에 남는지
⑨ 복구 코드는 **두 번째부터 거부**

**Phase 2** ⑩ DB 를 직접 열어 이름·주민·전화가 **읽히지 않는지** ⑪ 본인인증이 그대로 통과하는지
(블라인드 인덱스) ⑫ KMS 권한을 뺐을 때 **기동이 실패하는지**(조용히 평문으로 돌지 않는지)

**Phase 3** ⑬ 양식 위반 행이 전부 거부되고 **줄 번호와 사유**가 오는지 ⑭ 같은 배치 두 번 승인 →
행이 두 배가 되지 않고 사업자번호만 backfill ⑮ 초대코드 없이 신청 → **404**
⑯ 두 admin 이 동시에 같은 intake 승인 → **한 번만 반영** ⑰ 승인 후 intake 행이 **삭제**되는지
⑱ 머리글 없는 파일 → 막다른 길이 아니라 **칸 지정 화면** ⑲ 사용자 번들에 `admin` 문자열이
**없는지**(`grep` 으로 확인) ⑳ 파기 → 결제 0건

**Phase 4** ㉑ `.env` 가 `600` 인지 ㉒ 새 볼륨 `Encrypted: True` ㉓ 본체↔제공자가 TLS 인지
㉔ 덤프가 복호화 없이 안 열리는지

**Phase 5** ㉕ `nativeQuery` 를 새로 넣으면 **CI 가 실패하는지**
㉖ `demo-tamper.sh regenerate` **+ TSA 토큰까지 갈아끼운 뒤** S3 사본과 대조 → **드러나는지**
(지금 그 시연이 잡히는 것은 토큰을 안 건드리기 때문이다 — 진짜 공격자는 거기까지 손댄다)
㉗ 앱 DB 계정으로 `audit_log` `DELETE` → **권한 거부** ㉘ EC2 역할로 앵커 객체 `Delete`·`Get`
→ **거부**
