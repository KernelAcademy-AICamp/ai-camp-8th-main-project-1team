# 배포 — 컨테이너 스택과 AWS 적합성

Capacitor 앱이 바라볼 **공개 주소**를 만드는 것이 목표다. 앱은 기기 안에서 실행되므로
`localhost`가 개발 PC가 아니라 기기 자신을 가리킨다 — 실제 도메인이 있어야 앱을 만들 수 있다.

순서는 **로컬 총연습 → AWS**다. 배포 파이프라인 자체의 실패가 시연을 죽이면 안 되므로(D-03),
컨테이너 구성은 로컬에서 전부 검증한 뒤 클라우드로 옮긴다.

---

## 1. 파일 구성

| 파일 | 쓰임 |
|---|---|
| `docker-compose.yml` | **개발용**. 8080·8082·3306을 전부 발행해 디버깅이 쉽다. |
| `docker-compose.prod.yml` | **운영/총연습**. 밖으로 열리는 포트는 `127.0.0.1:5173` 하나뿐. |
| `docker-compose.prod.local-db.yml` | 컨테이너 MySQL을 쓸 때 겹쳐 쓰는 오버레이(의존 관계만). |
| `deploy/.env.example` | 운영 스택 환경변수 템플릿. `deploy/.env`는 커밋 금지. |
| `deploy/mysql-init/01-create-databases.sql` | 두 DB(`finntech`, `finntech_mydata`) 생성. RDS는 수동 1회. |
| `scripts/smoke.sh` | "떴는가"와 "닫혔는가"를 함께 본다. |

### 운영 스택이 지키는 것

1. **문은 하나** — 프론트 nginx가 `/`는 SPA, `/api/`는 본체로 프록시한다. 브라우저가 보는
   오리진이 하나라 CORS가 발생할 일 자체가 없다. `actuator`는 `/api` 밖 경로라 이 프록시로
   도달할 수 없어 내부 헬스체크 전용이 자동 보장된다.
2. **마이데이터(8082)는 완전 비공개** — compose 포트 미발행 + `internal: true` 망(아웃바운드조차
   없음) + 방화벽 규칙 부재의 3중. 이 격리는 일정이 밀려도 자르지 않는 항목이다.
3. **`container_name`을 박지 않는다** — blue-green으로 두 벌 띄울 때 이름 충돌로 새 쪽이 못 뜬다.

## 2. 로컬 총연습

```bash
cp deploy/.env.example deploy/.env       # DB_PASSWORD·MYSQL_ROOT_PASSWORD·MYDATA_SHARED_SECRET 채우기
docker compose -f docker-compose.prod.yml -f docker-compose.prod.local-db.yml \
  --profile local-db --env-file deploy/.env up -d --build
./scripts/smoke.sh
```

합격 기준: 4서비스 healthy + 스모크 전 항목 통과(8082·8080·3306 도달 불가 포함).

RDS 등 외부 DB를 쓸 때는 `deploy/.env`의 `DB_HOST`를 엔드포인트로 바꾸고 오버레이·프로파일 없이
기동한다 — 그러면 MySQL 컨테이너가 아예 뜨지 않아 인스턴스 메모리를 잠식하지 않는다.

## 3. AWS 적합성 — 실측 기준

### 3-1. 계정: 신규 가입은 이제 '프리 플랜'이다

AWS는 2025-07-15부로 프리티어 정책을 바꿨다. **그 이후 만든 계정은 12개월 무료 인스턴스가 아니라
크레딧 기반**이다 — 가입 시 $100, 온보딩 과제 5개(EC2 기동·종료, RDS 구성, Lambda 배포,
Bedrock 프롬프트, Budgets 설정)를 마치면 $100 추가. **최대 6개월.** 일부 상시 무료 서비스는 그대로다.

**중요 — 무료 플랜에서는 청구 자체가 없다.** AWS 안내문 그대로 "유료 플랜을 선택하지 않는 한
요금이 청구되지 않습니다". 크레딧이 떨어지면 요금이 나가는 게 아니라 **서비스가 멈춘다.**

그래서 관리 대상은 "예상치 못한 요금"이 아니라 **"필요한 시점까지 서비스가 살아 있는가"**다.
사양을 무리해서 낮출 이유는 없되, **소진 속도가 곧 서비스 수명**이라는 뜻이다.

### 3-2. 메모리 — 컨테이너 실측 (2026-07-28, 로컬 총연습)

한도를 걸고 4서비스를 실제로 띄워 잰 값이다.

| 서비스 | 실사용 | 한도 | 비고 |
|---|---|---|---|
| backend | **363 MiB** | 1280m | 분석 엔진·EBM 스코어러가 있어 가장 크다 |
| backend-mydata | **327 MiB** | 768m | 조회 응답만 만든다 |
| mysql | **476 MiB** | 1g | 버퍼풀 512M 명시. 위 수치는 빈 DB 기준 |
| frontend | **4.7 MiB** | 128m | 정적 서빙 + 프록시 |
| **합계** | **약 1.17 GiB** | **3.1 GiB** | 한도 합계 기준으로 사이징한다 |

**한도를 반드시 걸어야 한다.** Dockerfile의 `-XX:MaxRAMPercentage=60`은 *컨테이너* 한도를 읽는데,
한도가 없으면 **호스트 전체**를 한도로 본다. 한도 없이 4GB 인스턴스에 올리면 JVM 두 개가 각각
2.4GB를 요구해 OOM Killer가 온다. 총연습에서 한도 없이 띄웠을 때 backend가 559 MiB,
mydata가 445 MiB까지 늘어나는 것을 확인하고 넣었다.

| 인스턴스 | 메모리 | 판정 |
|---|---|---|
| t3.micro / t4g.micro | 1 GB | **불가** — 한도 합계 3.1 GiB에 한참 못 미친다 |
| t3.small / t4g.small | 2 GB | **불가에 가깝다** — DB를 외부로 빼도 JVM 둘의 한도만 2 GiB다 |
| **t4g.medium** | **4 GB** | **선택** — 한도 3.1 GiB + OS·Docker 0.9 GiB. MySQL까지 한 대에 |

**ARM(Graviton)을 고른다.** t4g.medium은 t3.medium과 같은 2vCPU/4GB인데 20% 싸다. 위험은
추측이 아니라 이미 확인됐다 — 이 총연습 자체를 Apple Silicon(arm64)에서 돌렸고 세 이미지 모두
arm64로 빌드·기동·스모크를 통과했다. 문제가 생기면 t3.medium으로 바꾸는 비용은 월 $7.6다.

### 3-3. 데이터 — 6.17 GB / 13.6M 행 (전체 이전)

`finntech_mydata` 실측 6.17 GB(13,665,475행), `finntech`는 0.01 GB. **전체를 그대로 올린다**
(사용자 결정) — 11M 규모의 서사를 유지한다. 그래서 EBS를 40 GB로 잡는다: 데이터 6.17 +
덤프 임시본 + 도커 이미지 약 1.3 GB(backend 595 MB · mydata 577 MB · frontend 94 MB) + 로그 여유.

MySQL 버퍼풀은 512 MB다. 6.17 GB를 전부 캐시하지는 못하므로 처음 닿는 구간은 디스크를 읽는다 —
조회가 전부 인덱스를 타므로 시연 수준의 트래픽에서는 문제되지 않지만, 콜드 캐시 첫 응답이
느린 것은 정상이다. 축소본(1/10)은 실행 계획의 포기 순서 6번으로 남겨 둔다.

### 3-4. 구성과 수명 — 단일 EC2, 24시간 가동

**단일 EC2 한 대에 4서비스 전부**를 올린다(RDS 미사용). 과금 대상이 하나라 크레딧이 오래 가고,
목표는 "앱이 바라볼 공개 주소"이지 인프라 과시가 아니다. compose가 외부 DB도 지원하므로
나중에 RDS로 옮기는 비용은 `DB_HOST` 한 줄이다.

요금 API 실조회(ap-northeast-2, 2026-07-28):

| 항목 | 단가 | 월(730h) |
|---|---|---|
| t3.medium (x86) | $0.0520/hr | $37.96 |
| **t4g.medium (ARM)** | **$0.0416/hr** | **$30.37** |
| EBS gp3 40 GB | $0.0912/GB·월 | $3.65 |
| 공인 IPv4 1개 | $0.005/hr | $3.65 |

**t4g.medium 합계 ≈ $37.7/월.** 크레딧 $200이면 **약 5.3개월** 24시간 가동된다
(t3.medium이면 $45.3/월 → 4.4개월). 무료 플랜 자체가 6개월 상한이므로 사실상 플랜 기간 전체를 덮는다.

> 크레딧 $100만으로는 약 2.7개월이다. **온보딩 과제 5개로 $100을 추가 적립해야** 위 수명이 나온다.
> 소진이 곧 서비스 종료이므로 **Budgets 알림을 먼저 건다**(그 자체가 과제 하나다).

### 3-5. 시각 설정 — 배포에서 반드시 비운다

`FINNTECH_DEMO_TODAY`와 `MYDATA_NOW`는 **비워서** 실시간으로 돌린다. 발표 리허설로 고정할 때만
**두 값을 같은 날짜로 함께** 넣는다. 한쪽만 고정하면 데이터 공급과 판정의 시계가 어긋나
소비가 0건이 된다(`_archive/tech_log.md` §8-D의 사고가 정확히 그것이다).

## 5. 백업 복원 리허설 (DoD 9)

> **복원해 보기 전까지는 백업이 아니다.** 덤프 파일이 생겼다는 것과 그것으로 서비스를 되살릴 수
> 있다는 것은 다른 얘기다. `scripts/backup-drill.sh`가 실제로 되살려 본다.

```bash
bash /opt/finntech/app/scripts/backup-drill.sh          # 끝나면 임시 자원 정리
bash /opt/finntech/app/scripts/backup-drill.sh --keep   # 남겨서 들여다볼 때
```

**운영을 건드리지 않는다.** 운영 DB는 읽기(mysqldump)만 하고, 복원은 이름이 다른 임시 컨테이너
(`finntech-drill`)의 임시 볼륨에서만 이뤄진다. 임시 컨테이너는 **포트를 발행하지 않는다** —
리허설이 외부에 열리면 그게 사고다.

### 다섯 단계

| | 하는 일 | 실측 (2026-07-29) |
|---|---|---|
| 1 | 덤프 (`--single-transaction`이라 서비스 중단 없음) | `finntech` 404K / 0초 · `finntech_mydata` **859M / 68초** |
| 2 | 임시 MySQL 기동 (같은 도커 망, 포트 미발행) | — |
| 3 | 복원 | 31테이블 / 2초 · 9테이블 / **359초** |
| 4 | **복원본만 바라보고 백엔드 기동** | validate 통과 |
| 5 | 감사로그 확인 | 항목 6건 · 배치 3건 |

**4단계가 핵심이다.** 덤프가 '열리는지'가 아니라 **서비스가 뜨는지**를 봐야 백업이라 할 수 있다.
운영은 `ddl-auto=validate`라 스키마와 엔티티가 한 칸이라도 어긋나면 여기서 죽는다.

**감사로그는 복원으로만 되살아난다.** 나머지 더미 영역은 시드 재생성으로 복구할 수 있지만
(결정론), `audit_log`·`audit_batch`는 재생성하면 해시 사슬과 TSA 앵커가 달라진다 —
`demo-tamper.sh regenerate`가 보여주는 논리와 같다.

### 시간 계획

전체 약 **7~8분**이고 대부분이 마이데이터 복원(6분)이다. 시연 직전에 돌린다면 그만큼을 잡아둔다.
디스크는 덤프 0.9G + 복원본 약 5G가 잠시 필요하다(리허설 후 회수).

### 덤프 옵션이 두 곳에 있다

`scripts/dump-mydata.sh`(로컬·호스트 mysqldump)와 `scripts/backup-drill.sh`(서버·컨테이너 경유)가
같은 옵션을 쓴다. **한쪽만 고치면 리허설이 실물과 달라진다** — 고칠 때 둘 다 본다.
